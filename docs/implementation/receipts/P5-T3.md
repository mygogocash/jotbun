- **Calls made for this task (the plan is silent; the planner's answers, for the reviewer):**
  1. (C1) Dates are real Gregorian dates from 1970 (`TRACKING_START_MIN`) to 9999-12-31, checked with `validateOccurredOn`, as `slips.ts` checks its dates. This covers `starts_on`, `ends_on`, a summary day, a rate's `date` and `rate_date`, `as_of`, and a quote's `day`.
  2. (C2) A trip's length is checked backward: `addDays(ends_on, 1 - TRIP_MAX_DAYS) <= starts_on`, which is `addDays(ends_on, -365) <= starts_on`. Counting forward would ask `addDays` for a year past 9999 for a trip that starts in December 9999, and `addDays` throws a `RangeError` outside years 0001 to 9999. Counting back from a date in 1970 or later never leaves year 1, so the validator never throws.
  3. (C3) `deleted_at` is null, or instant text of at most 40 characters that `Date.parse` reads (`slips.ts`'s `isInstant`).
  4. (C4) A trip's budget is canonical text for `parseMinor` with `allowZero: false`, `allowNegative: false` and `max: MINOR_AMOUNT_MAX`: 1 to 99,999,999,999 minor units of the trip currency. A JSON number or a leading zero is refused.
  5. (C5) Summary sums are canonical text of 0 or more with no cap (`parseMinor` with `allowZero: true`, `allowNegative: false`), since several records can add up past one record's cap. `count` is a safe integer of 0 or more. `as_of_revision` has `sync.ts`'s revision shape.
  6. (C6) A rate used passes `parseRate` (positive canonical text, at most 12 significant digits; X1, Q11). `rate_date` is null or a real date, with no order against `date`: a date older than the history takes the earliest quote, which is later (spec 6.10).
  7. (C7) `isTripSummaryDto` checks each field's shape and exact keys. It does not check P5-T12's ordering, uniqueness or arithmetic (days ascending, categories by home amount, totals equal to the day sums, rates outside the home currency, a live trip). Those are P5-T12's rules and tests.
  8. (C8) Today's `rates` is a plain object, not an array, whose own keys are ISO codes other than `base`. Each `per_base` is text that `canonicalQuote` returns unchanged, so `150.0`, a JSON number and more than 15 significant digits are refused. An empty `rates` object is valid by shape.
  9. (C9) The settings id is any UUID that `isUuid` accepts. P5-T13 derives it with `derivedUuid(accountId, 'account-settings')`, a version 8 UUID that `isUuid` accepts (the planner checked this).
  10. (C10) Each new module keeps its own private helpers (`isObject`, `hasExactly`, a date helper), as `slips.ts`, `push.ts` and `sync.ts` do. `validation.ts` is unchanged.
  11. (C11) The typed stubs leave `sync.ts` unchanged, so the RED sync case fails on its first assertion. The stub already carries the final `TRIP_MAX_DAYS` constant.
  12. (C12) The six export lines sit directly after the `./v1/sync.ts` type export line, apart from the export lines that P5-T2 edits in place.
  13. (C13) The API: ruling R83's pattern covers the change, in a test file only. After `slip_inbox`, `trip` and `settings` are left out, and the remaining keys are exactly the seven entities the API registers with `defineEntity`.
