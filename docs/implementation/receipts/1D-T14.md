- **What changed** (plan 1D, Task 14, with the controller's ruling R125):
  - **`signIn`** (`apps/app/src/auth/credentialProvider.ts`, 1C-T5's). An active result sends one account event: `signed_up` with the request's method when the server says it created the account, otherwise `signed_in`.
    - `created` is the server's (1C's K23): the merged port carries it as `ServerSession.created` and `SignInResult.created`, so the plan's fallback (every method `signed_in`) does not apply. The request's `signUp` never decides: a returning Apple user may send it too.
    - The event is tracked inside the sign-in flow, right after the `bootstrapped` dispatch and before anything else is awaited. So a joined sign-in sends it once, and a cancelled, refused, superseded or failed one sends none.
    - It comes after the session change: by then `AnalyticsUpkeep` has dropped the previous account (R120), so on an account switch the new account's sign-in is never captured under the previous account's identity. It waits for the new account's answer (1D-T1).
  - **`signOut`.** From an active session it sends `signed_out` with `account()?.method` first, before the session change.
    - First: so it is captured under the account signing out, before `AnalyticsUpkeep` resets the identity. Tracked after the change, it would be held and sent with the next account's yes (the followups' note from 1D-T7's second confirming review, `zzConfirm2Order` cases 3 and 4).
    - Only from an active session (the planner's guard, brief ruling P4). For any other state, `AnalyticsUpkeep` sees no binding and has already dropped the account. That covers a session locked because a token read found it gone, and one the vault ended (D37). A `signed_out` tracked then would be held, and the next account's yes would send it. Settings lets such a session in, and its Sign out calls `signOut()`. The plan says a sign-out from elsewhere and a session that ends by itself send nothing, and these are those sessions.
  - **R125: two sign-outs send no `signed_out`.** `signOut` takes an optional `SignOutOptions` (`{ event?: boolean }`, exported from the provider), and `event: false` skips the event.
    - **Settings' sign out everywhere.** After a confirmed sign-out everywhere (or Try again's resend), Settings signs this phone out with `{ event: false }`: the plan sends nothing for sign out everywhere in phase 1. Its plain Sign out passes `{ event: true }` and sends `signed_out` as before.
    - **Privacy's Done after an accepted deletion** passes `{ event: false }`. An event under the deleted account's analytics id could bring back the PostHog person that deletion step 6 (1D-T13) removes, against the Global Constraints and Q11.
    - The option travels through the screens' services (`AccountServices.signOut` and `PrivacyServices.signOut` take it) and the app's `signOutOfThisDevice`, which hands it to the installed provider. `accountServices.ts` and `privacyServices.ts` already wire `signOut: signOutOfThisDevice` and are unchanged. The catalogue's fakes take no options and still fit.
  - `passkey_created` stays unsent (the plan defers it). A fresh sign-in ("Confirm it's you") and a launch's restore send nothing either: the plan names only `signIn`.
  - The provider imports the emitters relatively (`../analytics/events.ts`), as the plan says.
