- **What it does:** `GET /v1/sync/live` goes through the vault Worker's front door (route, gates, client version, token), then the Worker hands a fresh internal request carrying only the verified claims (`x-vault-claims`) to the caller's UserVault. `UserVault#fetch` refuses an erased vault, runs `call()`'s account, budget and session checks in one block, and accepts the socket with the Hibernation API (tag: the session id; attachment: session, iat, opened-at). After every call and alarm the vault compares `sync_state.revision` as BigInt: when it grew, every other session gets `{"revision":"<n>"}`; then, whatever the call answered, sockets whose session ended close with 4401. One socket per session (4409), at most 20 open sockets per vault (4409 to the oldest open one), `ping`/`pong` answered by the runtime without waking the vault, any other message closed with 1008. Sockets never carry record data (spec §6.5).

- **Deviations and calls:** deviation 1 is accepted by the controller (8 November 2026). Deviations 2 to 7 are the six smaller calls the brief lists, recorded as made.
  1. `webSocketClose` answers the phone's close (`ws.close(code, reason)`, 1000 when that code cannot be sent back) instead of doing nothing. The plan relies on the runtime answering a Close frame itself from compatibility date 2026-04-07 (`web_socket_auto_reply_to_close`). The workerd these tests run (1.20261019.1, `@cloudflare/vitest-plugin` 1.4.7, compatibility date 2026-10-01) does not: in the planner's probe the server-side handler ran with the socket in CLOSING and the phone's close event never came until the vault called `close`. Cloudflare's WebSocket page says calling `close()` there stays safe. Mutant M10 pins it. Accepted by the controller (8 November 2026).
  2. A refused open is built in the vault as the v1 problem (`problemResponse`, with the vault's own request id) and the Worker returns it unchanged, as the plan says; its `request_id` is not the Worker's.
  3. A missing or malformed `x-vault-claims` is 400 `VALIDATION_FAILED`; only a wrong method, URL or a missing upgrade is 404.
  4. `live.ts` exports helpers beyond the plan's list, so the vault and the Worker share one definition each: `LIVE_VAULT_URL`, `closeSocket`, `afterVaultWork` (the body of `UserVault#afterCall`), `wantsWebSocket`, `liveRequest`, `isLiveRequest`, `liveClaimsOf`, `liveRefusal`.
  5. `cloudflare-workers.d.ts` does not redeclare `readyState`: the DOM's `WebSocket` already has it.
  6. Tests: "A has received nothing 200 ms later" is proven without a wait (A's ping is answered after anything the vault sent it before). Beyond the plan: 9 to 10 compared as a whole number; a phone's own close answered; a send to a closing socket skipped; `closeEndedSessions` with `erased`; only the Worker's internal request reaches the checks, and `parseLiveClaims`' cases; a socket closing in the same turn does not count toward 20; the read budget bounds opens (429). The erased case also deletes the marker row, because with the marker present `ensureAccount` answers the same 403 (the plan's "500, the tables are gone" predates 1B-T2's marker).
  7. The runtime drops a closed socket from `getWebSockets()` at once, so in the plan's 20-socket scenario a client-closed socket is not listed either way. The "a closing socket does not count" rule is pinned by the same-turn case (M6).
