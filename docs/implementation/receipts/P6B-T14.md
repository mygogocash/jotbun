- **What changed** (plan P6B, Task P6B-T14, with X5 and B25):
  - **The request** (`apps/app/src/analytics/remoteFlags.ts`, new and pure). `fetchRemoteFlags` posts `{ api_key, distinct_id }`, and nothing else, to `${posthogHost}/flags/?v=2`, which is 1D-T2's proxy. It sends `redirect: 'error'`, as the v1 client does, so a redirect fails the request instead of taking the phone to PostHog itself.
    - Each flag reads as its variant when it has one, else as `enabled`. A payload is JSON text, and is parsed.
    - The answer is null on: a network failure; a status outside 2xx; a timeout (5000 ms by default; the request is aborted, and the call settles even if the fetch ignores the abort); a malformed answer (not JSON, no `flags` object, a flag without a boolean `enabled`, or a payload that is not JSON); a partial answer (`errorsWhileComputingFlags`); and an answer over the flags quota (`quotaLimited` holding `feature_flags`).
    - `parseKeptFlags` reads the kept answer back; one that cannot be read counts as none.
  - **The controller** (`controller.ts`, 1D-T1's). `PostHogLike` gains `updateFlags` and `getFeatureFlag`. `AnalyticsDeps` gains an optional `flags` (`load`, and `kept`, the account's store). `Analytics` gains `flag(key)`.
    - **In yes:** entering yes pushes the account's kept flags at once, so a launch, offline included, shows the last rollouts. Then, under the analytics id the client was identified with, a load pushes and keeps its answer; a failure keeps the old. Each `refresh()` in yes (every foreground, through `AnalyticsUpkeep`) loads again. Every push is heard by the controller's subscribers.
    - **Never outside yes:** a no, never asked, signed out and loading ask for nothing. Nothing is asked without a client, nor without an analytics id; the kept flags still show in that second case.
    - **What drops the flags:** applying a no (also a stored no at a launch, and a no read from the server), opening the question, and the end of an account's session (a sign-out or a switch). Each erases that account's kept flags; 1D-T1's `reset()` has emptied the client's. A kept read or a load still on its way when the flags drop is never pushed or kept.
    - **What keeps them:** `loading`, and the launch's first account change.
    - **Flag work** runs outside the consent queue, so no consent call waits for the network.
    - **`flag(key)`** reads the client only in yes and after a push since the client's last reset. So PostHog's `$feature_flag_called` is only made after yes, never for a flag not yet loaded.
  - **The gate** (`gate.ts`). `$feature_flag_called` passes only with consent, as every allowed event does. `$feature_flag_payload` and `$feature_flag_bootstrapped_payload` are removed from every event's properties. An exposure keeps the flag, its value and PostHog's bootstrap fields, and loses the device name, `$set` and `$set_once` as every event does.
  - **The wiring** (`appAnalytics.ts`, 1D-T6's). The load goes through `fetchRemoteFlags` with `posthogHost` and `posthogKey`. The kept flags live in `walletAccountStore(accountId)` under `remote-flags` (P2-T3), so a confirmed deletion's `eraseAccountKept` erases them with the rest.
  - **The real client** (`posthogClient.ts`) forwards both new methods to PostHog. The client is still built with `disableRemoteFeatureFlags: true` and `preloadFeatureFlags: false` (1D-T6, unchanged), so it never asks for flags itself.
  - **The rollout layer** (`apps/app/src/rollout/`):
    - `rollout.ts` (pure) holds `ROLLOUT_FLAGS` (`rollout-bun-ai`, `rollout-slip-import`, `rollout-travel`), `ROLLOUT_DEFAULTS` (all off, default pending owner Q10) and `rolloutOn`. Undefined reads the default; true, or a variant but `control`, reads on.
    - `experiments.ts` holds `EXPERIMENTS` (`exp-budget-question`: `no_presets`; `exp-save-celebration`: `still`; `exp-reminder-time`: `later`; default pending owner Q11), `variantOf` (a listed variant of that experiment, else `control`) and `readExperiment`: one read of the installed controller's flag, which is the exposure.
    - `useRollout.ts` follows the controller's subscription, so it reads again at every push and every change of the answer.
  - **The recorder** (`testing/recordAnalytics.ts`). Its signature and fields are unchanged, so every caller compiles and runs as before. Its client takes pushes, answers `getFeatureFlag` from the last one, and `reset()` empties them. A new `flags` option is what the load answers after a yes. The new `pushed` and `flagReads` record the pushes and the reads; pushes never enter `sent`. `fakeConsent.ts` gains the two methods as no-ops.
- **With no PostHog key (plan 1D's Q5, today):** there is no client. The controller asks for no flags, keeps none and pushes none, and `flag()` reads undefined. Every rollout reads its default (all off) and every experiment reads `control`. The web build and every test without a client behave the same.
