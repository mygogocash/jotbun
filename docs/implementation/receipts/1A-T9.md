## Fix round (R92): snapshots in the API's key order

- **CI result:** run 42476668840 on `6ed0ed6`: `test:edge:db` failed only in `vault-parity.db.test.ts`, at steps 44 (sync, two groups) and 45 (sync, everything). Every other step was green (`test:db` 694, `test:ops` 107, `test:edge` 163, workers 371 + 3 todo).
- **Cause:** key order only. NestJS keeps each change snapshot in `entity_changes.snapshot` (`jsonb`), which orders an object's keys shortest first (in UTF-8 bytes), then bytewise. The vault served them in build order. Values and statuses matched on all 49 steps.
- **Fix (controller ruling R92):** `jsonbOrder` in `apps/edge/src/vault/reads/sync.ts`, applied in `changeOf`. The normalizer and the money session are unchanged. The two new sync cases pin the order. The summary golden-month case is now exact (review minor 1), in the API's category order.
- **Files:** `apps/edge/src/vault/reads/sync.ts`; `apps/edge/test/workers/sync.test.ts` (two cases); `apps/edge/test/workers/summary.test.ts` (one exact assertion); this receipt.
- **Mutants:** five, each restored from a saved copy and confirmed with `cmp`.
  - M1, `changeOf` serves the parsed snapshot unchanged: `sync.test.ts` `Tests 1 failed | 14 passed | 3 todo (18)`; the route case `serves each snapshot with its keys in the API's order` fails.
  - M2, `jsonbOrder` does not recurse into nested objects: `sync.test.ts` 1 failed, the pure case `orders keys as jsonb does ...` fails. The route case still passes, because the only nested object it serves (`budget.category_limits[]`) is already in jsonb order.
  - M3, the sort drops the length rule (bytewise only): `sync.test.ts` 2 failed, both new cases.
  - M4, `summary.ts` `ORDER BY t.type, t.category_id DESC`: `summary.test.ts` `Tests 1 failed | 6 passed (7)`; the golden-month case fails.
  - M5, `summary.ts` `ORDER BY t.type DESC, t.category_id`: `summary.test.ts` 1 failed; the golden-month case fails.
