## 2. Scope of each plan

### P3: Photos and Bun AI (spec §8 item 3)

In:
- **Model routing on the edge** (§6.7, D25, D28): a Haiku 5.5 request base (no `betas`, no `fallbacks`, no `budget_tokens`, no prefill, no non-default sampling; a refusal handled in code) and an Opus 5.5 base (the fallback beta and `fallbacks: "default"`, as today). Tell Bun: the phone's rules parser first, Haiku when the rules cannot read the sentence. Read a slip: Haiku, then an Opus re-read in the same request while the image is still in memory, when the amount does not parse, the date is implausible, a required field is missing, Haiku declines or Haiku returns no draft. Daily note: Haiku. Ask Bun: Haiku, escalating to Opus on a failed grounding check, a decline or the tool loop's step limit; the escalation starts a fresh Opus conversation with the same question (never Haiku's turns replayed under a changed system prompt or tool list); plain facts if Opus also fails; an escalated question counts once. Each AI route states one server deadline that ends before the phone's timeout for that route, and the phone's AI calls use that timeout.
- **AI results carry `model` and `escalated`** (contract change in place, C2), with the app's exact-key validators changed in the same task.
- **AI Gateway transport:** the SDK's `baseURL` is `ANTHROPIC_BASE_URL` (the gateway URL); every request sends `cf-aig-collect-log: false` and `cf-aig-skip-cache: true`; an optional `cf-aig-authorization` comes from a new secret (default pending owner).
- **The `ai` gate** (§4, C12): the edge's own scope list gains `ai` (no edit to `apps/api`). The config reader accepts `ai` before any config writes it. The gate covers every route that calls a model (`/v1/ai/parse`, `/v1/ai/slip`, `/v1/ai/note`, `/v1/ai/ask`, and P4's `/v1/slips`) and answers 503 `AI_PAUSED`; AI preferences stay ungated (default pending owner).
- **Quotas** stay in the vault's `ai_usage` (parses 30, live slip reads 10, notes 3, questions 20 a Bangkok day). An escalation spends one use. A use is given back when the model call fails with a rate limit, a 5xx or a timeout (B5).
- **LLM analytics** (§7): one `$ai_generation` event per model call (Haiku and Opus), sent through 1D-T3's server analytics module with plain `posthog-node` (B6): model, provider, input, output and cache tokens, latency, status, error class, feature, escalated, a trace id per request; never the prompt, the answer, the tool schemas or the gateway URL; only when the vault's analytics consent is yes and the analytics id exists (1D-T11's rule).
- **`source` on records** (capability `P3:source`): see section 3.
- **Photos** (§5.2 Daily capture, bw-attach, bw-tray-confirm): the add tray's attach step (camera or album through the installed `expo-image-picker`, with its config plugin and Thai permission text); the confirm step's photo row; "ให้บันอ่านยอดจากสลิป", which sends the photo to Bun only when AI is on (otherwise the consent sheet comes first); the slip-or-receipt rule (B3); a kept receipt goes through 1B's image import path and retain command (1B-T5, 1B-T9, 1B-T10); the photo row is unavailable offline (B4).
- **The receipt viewer, rc-view:** zoom, delete photo (final; restoring the record does not restore it), share (iOS shares the image through React Native's Share; Android hides share until a sharing package is approved).
- **Tell Bun with several drafts, ai-tell:** each draft edited or removed on its own; one save sends one `transaction.create` per draft, each with its own command id, offline-safe through the outbox; one `ai_draft_reviewed` per draft.
- **A single slip read, ai-slip:** "from slip" and "Bun's guess" marks; "use this" fills the confirm step; es-slip-unreadable; es-ai-unavailable keeps the draft with a retry.
- **Ask Bun, ai-ask:** the figures card with record counts, follow-up chips, uses left today; the chart and "see all" only if the answer's figures carry what they need (a contract addition the plan may make).
- **AI consent and settings, ai-consent and ai-settings:** copy that names exactly what is sent (including wallet and merchant names while prompts still carry them, B8), `AI_NOTICE_VERSION` bumped so everyone answers the new notice (default pending owner), Bun's presence (full, quiet, off), uses left today (sentences 30, slips 10, questions 20), the daily note switch, haptics.
- **The daily note on the wallet Home,** shown once a day in full mode as ai-settings says (this revises P2's W33; default pending owner).
- **`ask_bun_rated`** from a small helpful or not helpful control under each answer, two buttons and no free text (default pending owner).
- **The phone's slip QR module** (capability `P3:slip-qr`): see section 3.
- **The 100-slip evaluation** (D25): a development-build-only screen, compiled out of release builds as 1C compiles out the local code log. The tester picks slips from their own albums; each goes through the production single-read path; the tester marks each field right or wrong. Only booleans, the model, escalated, declined, latency and token counts leave the phone. Results are aggregate counts; labels and images are never written to the repository, R2, logs or PostHog. CI tests use the fake model. Thresholds come from the owner (default pending owner).
- **Bun AI events** through 1D's API (`trackAiConsentChanged`, `trackTellBunSent`, `trackAiDraftReviewed`, `trackAskBunAsked`, `trackAskBunRated`, `trackAiUnavailable`), and `record_saved` with the real `source` and `has_photo`.

## 5. Controller calls (the owner may overturn any; each plan cites the ones it applies)

- **B1. One plan per phase for 3, 4 and 5; three plans for phase 6.** Phases 3 to 5 each change the contract, the vault and the app together, so one writer per phase keeps their names in step; phase 6's three parts touch different code.
- **B2. `source` arrives in phase 3,** not phase 5 (§6.6 lists it with phase 5's fields), because Tell Bun, photos and slips need it first; older records stay NULL.
- **B3. Slip or receipt.** A photo the person asks Bun to read is kept as a receipt only when `readSlipImage` says `receipt` and the person keeps it attached; `slip` or `unreadable` drops it, so it never reaches R2. A photo attached without asking Bun is the person's receipt. Once `P3:slip-qr` has a native decoder, any photo whose QR parses as a Thai slip is never uploaded, and the app says why.
- **B4. No photo offline.** The photo row is unavailable offline, with a note, because receipts are never written to the phone's storage and C16 adds no outbox kinds.
- **B5. A failed model call gives its use back** (rate limit, 5xx or timeout); a completed read, a decline and an escalation each spend one.
- **B6. LLM analytics without `@posthog/ai`.** Its Anthropic wrapper does not support the repository's SDK 1.2.0 and never sees beta calls, so P3 builds the `$ai_generation` event itself on `posthog-node`, with the same privacy result.
- **B7. AI copy stays baht until P5** changes Ask Bun's facts and Tell Bun's amounts to the right currency.
