## Interfaces (as `real/` has them)

```ts
// src/vault/files/jobs.ts
export type FileJob = 'start_work' | 'delete_objects' | 'prune_files'
export const FILE_JOBS: readonly FileJob[]          // ['prune_files', 'delete_objects', 'start_work']: the alarm's order
export type FilePrune = (c: FileContext) => void
export const FILE_PRUNES: readonly FilePrune[]      // pruneUploads, pruneExports, pruneSnapshots, pruneAttachments, pruneImports
export type FileJobOptions = { maxBatches?: number; prunes?: readonly FilePrune[] }
export const MAX_DELETE_BATCHES = 10
export function fileJobsDue(c: FileContext, lastStartAttemptMs: number | null): Map<FileJob, number>   // empty unless active
export function runFileJobs(v: UserVault, options?: FileJobOptions): Promise<FileJob[]>               // the jobs that threw (P5)

// src/vault/retention.ts (1A-T8b's, widened)
export function reschedule(c: FileContext, lastStartAttemptMs: number | null): number | null

// src/vault/user-vault.ts
export const CALL_ALARM_DELAY_MS = 60_000
// UserVault
fileJobOptions: FileJobOptions        // {} by default; tests set it, as they set `clock`
alarmAt: number | null                // the alarm this instance set; memory only
rearm(c: FileContext, delayMs: number = CALL_ALARM_DELAY_MS): void
```

What each does:
- `fileJobsDue(c, last)`: nothing for a vault that is not active; otherwise `start_work` at `startDueAt(c, last)`, `delete_objects` at `objectsDueAt(c)`, `prune_files` at the earliest of `uploadsDueAt`, `exportsDueAt`, `snapshotsDueAt`, `attachmentsDueAt` and `importsDueAt`. A job with nothing to do is absent. No deadline is derived here (R37).
- `runFileJobs(v, options)`: nothing for an erased vault, one that is not active, or while another run is in progress (P6). Each prune of `options.prunes ?? FILE_PRUNES` on one clock reading, each in its own `try` (`file_prune_failed`); then `deleteDueObjects` with at most `options.maxBatches ?? MAX_DELETE_BATCHES` batches, the bucket read inside its own `try` (P7; `file_delete_failed` for anything else); then, unless an erase landed during the R2 wait, `startPendingWork()` when `start_work` is due (`file_start_failed`). Returns the jobs that threw; never throws them.
- `reschedule(c, last)`: upserts the `schedule` rows of `nextDue(c)` and `fileJobsDue(c, last)`, deletes every other retention or file job's row, and returns the earliest `due_at` or null.
- `UserVault#rearm(c, delayMs)`: nothing in an erased vault. `due = reschedule(c, this.lastStartAttemptMs)` in its own block; `at = max(due, c.now + delayMs)`; when `at` is above `due` and an alarm is already set sooner (`alarmAt < at`), `at = alarmAt`; when `at` differs from `alarmAt`, `void setAlarm(at)` or `void deleteAlarm()` outside every block, and `alarmAt = at`. A failure is logged (`vault_alarm_unset`), never thrown.
- `UserVault#alarm()`: nothing in an erased vault. `alarmAt = null` first (the runtime deleted the alarm that fired); then `runDue`, then `await runFileJobs(this, this.fileJobOptions)`; any failure among them is caught and logged; then, unless an erase landed meanwhile, `rearm(fresh context, failed ? RETENTION_RETRY_MS : 0)`; then the live pokes, as before.
- `call()` rearms after its block with the call's context when that context was touched; `runCommand` touches on commit. `background()` (the short-block methods: the parse steps, `failExport`, `failSnapshot`) rearms with its context when it wrote. `writeExport`, `buildSnapshot` and `startPendingWork` read through `rearming()`, which rearms with a fresh context when any context they read was touched, also when they threw.

## Planner rulings (the calls this brief makes, with the reason for each)

- **P1. A stale snapshot keeps its row; its chunk rows go and its keys are due at once (1B-T8's review m-1, the controller's first note).**
  - **Why:** deleting the row lets a resend of the same key insert a pending row under an id whose SnapshotWorkflow instance has already completed. `createOnce` counts that instance as started, nothing builds the row, and every later request, even with a fresh key, shares it until it fails a day later (the review's probe D).
  - **What it does instead:** `pruneSnapshots` makes the stale snapshot's chunk keys due (`delete_after = 0`) and deletes its `snapshot_chunks` rows, in its one block. The row stays `ready` below the watermark, so its status and a resent request read `expired`: 202 `{ snapshot_id, status: 'expired' }`. That is what the API answers while it keeps the job (`snapshot.repository.ts:64-65`; `SyncController.request` answers 202 for anything not ready), and what 1B-T12's parity session expects (the 1B-T8 review's note for 1B-T12). The row then goes with the existing week-past-expiry rule, since a stale snapshot is a ready one.
  - **The due time:** `snapshotsDueAt` answers "now" only while a stale snapshot still has chunk rows (`STALE_CHUNKS`), so a released one is not due again at once (R37). A failed R2 delete's minute-later retry is not undone by the next prune either.
  - **Residual, accepted:** a resend of the same key more than a week past its snapshot's expiry (the row gone) still makes a pending row under the old id. The app takes a fresh key for each resync (`apps/app/src/sync/reconcile.ts:9`), and only a transport resend of a lost response repeats a key, within seconds. The review's other option, a starter that notices a finished instance, would change 1B-T6's `createOnce` and the instance naming that 1B-T8's K5 pins.
  - **For fix-download-aborts**, which edits the same two files: this task's `snapshots.ts` edit is at the end of the file (the new `STALE_CHUNKS` after `BELOW_WATERMARK`, `pruneSnapshots` and `snapshotsDueAt`), and its `snapshots.test.ts` edits are inside three existing cases: `tombstones reach delta readers, ...` (the block after the second `requestSnapshot`), `after pruneSnapshots at snapshotsDueAt, ...` (the seed and the expected times) and `pruneSnapshots fails a snapshot left pending for a day, ...` (its last block).
  - Pinned by the resend case and the three changed cases (mutants S1 to S3).
- **P2. A write never sets the alarm sooner than a minute ahead, and never before its clock; an alarm already set sooner is kept.** The plan's `rearm` sets the alarm to the earliest due time as it is. This task adds `delayMs`: `CALL_ALARM_DELAY_MS` (60,000) for `call()` and the background methods, 0 for the alarm itself.
  - **Why a floor at all:** workerd refuses an alarm at or before 0 ("setAlarm() cannot be called with an alarm time <= 0", the planner's first run). Every release writes `delete_after = 0`: B20's trigger, `releaseObject`, `pruneAttachments` and the stale-snapshot rule. So `objectsDueAt` answers 0, and a rearm without a floor leaves the release unscheduled, with `alarmAt` wrong besides.
  - **Why a minute for writes:** in the Workers tests an alarm due at once fires on its own. The planner's probe purged a record within two seconds with no `runDurableObjectAlarm` (`logs/probe-autofire.log`). With 1B-T11 wired, about 40 existing file cases arm such an alarm: a release, a given-back copy, a backdated row (`logs/explore-near.log` lists them).
    - With only the clock as the floor, all four of the planner's runs of these files failed 6 to 8 cases each (`logs/explore-att-*.log`, `logs/explore-near.log`). Six `attachments.test.ts` cases assert a state that the self-fired alarm had already moved on.
