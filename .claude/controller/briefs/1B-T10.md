## Planner rulings (the calls this brief makes, with the reason for each)

- **P1. A confirmation is two vault steps, each one block.** The API runs `receiptAllowed` (read-only checks), `AttachmentService.prepare`, then `executor.run`, then `outcome`, each in its own transaction. The vault runs `imports.confirmPrepare` (the read-only checks, then 1B-T9's `prepareReceipt` without a record, in one block) and `imports.confirm` (the command, then the outcome read from durable progress, in one block). Reading the outcome in the command's block is safe: a replay mutates nothing, and a fresh command just checked its selection in the same block, so the outcome read cannot refuse and roll it back. Without a receipt, `imports.confirm` is the request's only (charged) call.
- **P2. The prepare step answers `refused` when the batch's read-only checks would refuse it.** The plan types `confirmPrepare` as `PreparedCopy`; this brief widens it to `ConfirmPrepared = PreparedCopy | { kind: 'refused' }`, because the command needs the API's distinction between "no receipt was prepared" (`prepared` null: the checks refused, or the batch has no receipt) and "nothing was copied" (`{ kind: 'none' }`: the receipt exists, the command is a resend, or no image is left). With null, a batch whose image row is saved now answers the API's 503 with a one-second retry (the state moved between the steps) and never saves the image's record without its receipt; with `none`, 1B-T9's `ready` decides (an existing receipt is attached; otherwise 422 `errors.attachment_expired`). The command step's `prepared` is the API's `PreparedReceipt` shape: null, `{ kind: 'none' }` or `{ kind: 'copied', key, bytes, sha256 }`. 1B-T9's Worker loop `prepare` now takes its step route, body and params and returns `'refused'`; `withReceipt` maps that to null (a receipt's prepare step never refuses). Pinned by the planner's race case (a freeze lands between the two steps; mutants C32 and W3) and `a confirmation whose receipt was never prepared ...` (C33).
- **P3. A batch with a receipt takes a copy slot before its prepare step, as 1B-T9's P3 does** (the loop is shared). The API decides `receiptAllowed` before `acquire()`, so here a batch whose checks refuse also needs a free copy slot for the instant its prepare step runs; only an isolate with four copies running sees it, and that request is told to retry in 5 seconds. The slot rules are pinned by 1B-T9's own cases (`a busy process answers 503 ...`, `a process never has more copies running than its limit`), which run in the gate.
- **P4. A confirmation prepares a copy whatever its command schema, as the API's `confirm` does** (only `withReceipt` checks `SCHEMA_VERSIONS` first). A copy made for an unsupported schema is released once the command refuses (422 `COMMAND_SCHEMA_UNSUPPORTED`).
- **P5. The plan's type names.** `ImportPreviewDto` is the contracts' `ImportPreview`; `ImportPreviewPaging` is `PreviewPaging = NonNullable<ReturnType<typeof parseImportPreviewPaging>>` (the API's own `PreviewPaging` sits in `preview-query.ts`, beside its PostgreSQL query), and null reads the whole preview. `previewOf`, `selectionProgress`, `pruneImports` and `importsDueAt` take a `FileContext` (a `VaultContext` is one), so the route handlers and the retention tests share them.
- **P6. Every answer keeps the API's key order, and ruling R92 has nothing to reorder.** The candidates follow `PreviewQuery`'s column list, then the summary, image, page, advice, progress, correction and batch results as the API builds them. An issue is rebuilt in code as `{ code, source_row_id, field }` (as `PreviewQuery` does) and the file-level issues are strings, so the stored JSON's key order is never served (1B-T5's note asked for `jsonbOrder`; it would change nothing).
- **P7. Duplicate advice without PostgreSQL's array window.** One read of the vault's active records (`row_number()` per date, type and amount, at most 5, only for the keys the file names) and one pass over the candidates through the cursor, grouping same-file twins by their six fields in code (a null matches a null, as `PARTITION BY` groups it). It is linear: the 5,000 identical rows against 5,000 identical records answered in about 130 ms here, under the API's 2-second bound. The API's self-join reference is rewritten for SQLite inside the test.
- **P8. The freeze writes its frozen rows in one statement, with `CROSS JOIN`; a confirmed row is one statement.** The frozen rows are one `INSERT ... SELECT` from one JSON parameter (ruling R57's "or select from `json_each`"). `CROSS JOIN` keeps the JSON list as the outer loop: with a plain `JOIN`, SQLite scanned the list once per candidate and the 5,000-row case took 6.2 seconds (0.15 seconds with it).
