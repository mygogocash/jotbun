## Planner rulings (the calls this brief makes, with the reason for each)

- **P1. A writer never publishes past its own deadline, and the check answers 422, not 500 (the 1B-T4 follow-up).** The copy's PUT runs in the Worker; its publish runs in the command step, a later vault call whose clock is read when its block starts, so the publish context is always read after the PUT. `ready` then requires the copy's reservation to be this receipt's own (`receipt/<vault id>/<attachment id>/`), still `reserved`, with `delete_after` ahead of now **and** `created_at + RECEIPT_COPY_GRACE_MS` ahead of now, even when a failed R2 delete moved `delete_after` a minute on. Anything else is 422 `errors.attachment_expired`, decided before `publishObject` (which would throw a plain error, a 500: the follow-up's note for 1B-T9). Pinned by `a retain whose copy outlived its own reservation ...` (M14, M15) and the routine case's past-deadline attempt (M15).
- **P2. The R-B race cannot happen in the vault, and the cases pin why** (see Readiness). `prepareReceipt` decides "receipt exists" and "copy in flight" in one block, and the command publishes the copy and records the receipt in one block. Pinned by the planner's `a second prepare waits for a copy in flight, and needs none once the receipt exists ...` (a reserved copy answers `wait`; once its command committed, `none`, never a second copy: M5, M6) and by the ported `two records retaining one image at once ...`, which here holds the first copy until the second request has asked, so its `wait` and its poll are exercised every run (M5, M38). The API's version fires both at once; the hold makes the vault's run deterministic.
- **P3. The copy slot is taken before the prepare step, as the API's `acquire()` precedes its reservation.** The plan's Step 4 reads "For `copy`: take a `COPY_SLOTS` slot, then copy", which would reserve first and then refuse; a busy isolate would then spend the vault's daily copy budget on requests it turns away, and the ported `a busy process answers 503 ..., before it reserves anything` forbids that. Each attempt holds its slot from before `attachments.prepare` until its copy ends; `none`, `wait` and a 429 give it back at once. The one difference from the API: a request that needs no copy (a resend, an existing receipt, a record the command refuses) also needs a free slot for the instant its prepare step runs, where the API decides those first. Only an isolate with four copies running sees it, and that request is told to retry in 5 seconds. Pinned by the busy case (M31) and `a process never has more copies running than its limit` (M30).
- **P4. The limits are one object read at use time, as the API's `ATTACHMENT_LIMITS` is; the slot counts stay fixed.** `RECEIPT_LIMITS` (receipts.ts) is a copy of `DEFAULT_ATTACHMENT_LIMITS`; the copy (`copyDeadlineMs`, also the poll's deadline) and the download (`downloadIdleMs`, `downloadTotalMs`) read it when they run, and only tests change it. `COPY_SLOTS` (4) and 1B-T4's `RECEIPT_SLOTS` (8 per isolate, 2 per account) are `DownloadSlots` from `src/server/http/files.ts`, reference code fixed at construction, so where the API spec lowers a slot limit the tests take the other slots with `take()` and return them after.
- **P5. The copy is `R2ObjectStore.copy` then `head`, under one deadline that also cuts off a call that never answers.** The R2 binding has no server-side copy, so `copy` reads the import image through the Worker (it is at most 12 MiB) and writes the receipt create-only with the source's SHA-256. One `AbortSignal.timeout(copyDeadlineMs)` goes to both calls and is raced against them (`beforeAbort`), because the store checks a signal only between its binding calls. A failure gives the reservation back and answers 503 with 5 seconds, never the failure's text; a source gone by then gives it back and lets the command answer 422 `expired`. Changed-form ports: `copies inside the store, registered before the copy, ...` asserts one read of the import image, one write of the receipt (already `reserved` at the write) and the HEAD; `gives one deadline to the whole copy ...` asserts the behaviour (each step alone inside the deadline, both together past it: 503 at once, the reservation given back) where the API compares the two calls' signal objects, which the bucket cannot see. Pinned by M32, M33, M34.
- **P6. `attachments.release` runs after the session ended (`anySession`), as 1B-T5's cleanup steps do; the other four receipt steps check the session.** Release only makes the request's own unused copy due sooner. Pinned by the planner's `a retain whose session ends during its copy ...` (M47); the download step's session check by the plan's `a receipt grant is bound to the session that asked` (M48).
- **P7. Ported, changed and not-applicable cases.** The spec has 45 `it`. 40 are ported by name, 5 are not applicable (one receipt line each):
  - `the erasure step stops the purge while a receipt object is still live`: the deletion worker's step; a vault's erase deletes its storage whole (B22), and 1C's final sweep lists the prefixes.
  - `the global sweep lists receipts only for accounts with recent reservations, a page at a time` and `a sweep of one account lists that account whatever its history`: B19, per-vault tombstones replace the orphan sweep.
  - `counts released receipts whose object is still stored an hour after its deadline, and failed deletes`: the worker's cross-account alert; the vault's alarm retries its own deletes (1B-T4).
  - `Drizzle definitions match the migrated tables`: 1B-T2's column test in `vault-schema.test.ts`.

  Ported in changed form (the receipt lists each): the API's `publication.sweep` is `deleteDueObjects` (1B-T4), its `purgeExpiredRecords` is the vault's alarm (1A-T8b, `runDurableObjectAlarm`) and its `attachments.obsolete` step is `pruneAttachments`; the routine case drives the `attachments.retain` step with forged copies and has no generation half; an image's window is `expiresInMs` (its `attachable_until` is 1B-T10's preview); the "busy" and "at most" slot limits fill the isolate's slots (P4); account erasure is `purgeVaultObjects` then `erase()` (1C's deletion); `a grant verifies only for the session it was issued to` has no generation half (a vault has none; sign-out is the plan's case); the privileges case keeps only its schema half (only a published receipt has no deadline; the logins and row-level-security halves do not apply); `serializes reservations` sends five prepare steps at once, which the vault runs one at a time.
- **P8. A release is stamped by `pruneAttachments` only (B20).** The trigger releases without a time, and the remove and replace commands do not stamp either; the plan gives the stamp to `pruneAttachments` (1B-T11 runs it on the alarm, and `attachmentsDueAt` answers now while a release waits). So where the API asserts `released: true` right after a replace, the port asserts `status: 'released'` with no stamp at once, and `released: true` after `pruneAttachments`. Pinned by M29.
- **P9. A released receipt's 30 days count only once its object is gone.** The row drop needs the object out of the registry's live states (`reserved`, `published`), as 0017's prune does, and `attachmentsDueAt` uses the same condition, so the alarm never comes back for a row it cannot drop yet (R37).
