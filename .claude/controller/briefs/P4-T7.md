## Planner rulings (the calls this brief makes, with the reason for each)

- **P1. Ready.** Every "Starts after" task has merged; the routes lane waits for #463 only (Readiness); nothing hosted is needed.
- **P2. `createTransaction` shares `createTransactionRow`'s check and insert rather than calling it.** The plan says `createTransaction` "takes `source` out of the input and passes it" to `createTransactionRow`, with "its answers unchanged". Calling it inside the command would move the body's checks after the command's replay lookup and digest the raw body: P3-T2's pinned digest (a create without a source digests the checked record, `transaction-source.test.ts`) would break. So `parseCreate(c, body, withSource)` holds the checks in their R41 order, `insertCreated(c, draft, extras)` is the one insert path, `createTransaction` runs them as before (checks, then the command) and `createTransactionRow` runs both inside its caller's command. `parseCreate(..., false)` refuses a `source` key, and `slip_ref_id` is never a known field, so both are 422 `UNKNOWN_FIELD` (`createTransaction` still refuses `slip_ref_id` too).
- **P3. Confirm reads its headers, then its body, then runs the command.** The plan writes `commandInput(call, 'slip_draft.confirm', { id: SLIP_INBOX_ID, drafts }, 'forbidden')`, which needs the body parsed first; R41 puts the headers first, as `createTransaction` does. So `commandInput(call, SLIP_CONFIRM_KIND, null, 'forbidden')`, then `parseSlipConfirmRequest(call.body)`, then `runCommand(c, { ...command, payload: { id: SLIP_INBOX_ID, drafts } }, ...)`. The digest covers the request's drafts as sent, in canonical JSON (key order does not matter); a record holding a number that is not a safe integer is refused by the digester (422 `INVALID_COMMAND` on `payload`) before the records are checked.
- **P4. Inside the confirm.** The drafts are read with one JSON parameter (R57); any draft gone is 409 `VERSION_CONFLICT` with no `current` (the phone reloads the list), nothing written. Then each record, in the request's order, through `createTransactionRow` wrapped by `asDraft(index, ...)`: a `ContractValidationError`, or a `ProblemException` with `fields` (`stateProblem`'s), is thrown again with each field named `drafts[<i>].transaction.<field>`; a 409 or 410 from the record's own id passes through.
