## Planner rulings (the calls this brief makes, with the reason for each)

- **P1. Four upload steps run after the session ended (`anySession`).** In the API only `begin` and `finish` re-check the session and the policy, under the account lock; `reservePart`, `abort`, `discarded` and `bytesWait` run in plain owner transactions. In the vault every step goes through `call()`, which checks both. Without an exemption, a person who signs out while uploading leaves the upload `receiving` with its parts in R2 until the deadline, and the ported case `an upload whose session ended while it streamed is not accepted and leaves nothing` cannot hold. So `VAULT_STEP_ROUTES` entries get `anySession?: true` (`VaultStepRoute`), and `call()` skips `assertSession` and `assertPolicyAccepted` for those steps only: `imports.reservePart`, `imports.abort`, `imports.discarded`, `imports.bytesRetry`. `ensureAccount` and the erased check still run. Step ids have no HTTP route; they are reachable only from a Worker route that already verified the token. `reserveUploadPart` checks itself that the account is active, as `gogospend_reserve_import_part` does.
- **P2. Ports and not-applicable cases.** `upload-intake.integration.spec.ts` has 33 `it` (the plan says 32; the `it.each` is counted once). 27 are ported by name and assertion. Six are not applicable, one receipt line each: `the app login only reads its own rows; ...` (PostgreSQL roles and row-level security), `Drizzle definitions match the migrated import_uploads columns` (covered by 1B-T2's column test in `vault-schema.test.ts`), `the HTTP server lets an upload use its whole receive bound before Node ends the request` (Node's HTTP server timeout), `a lifecycle generation that moved while the body streamed refuses the finish and leaves nothing` and `imports of an account being deleted or at another lifecycle generation are expired at once; ...` (a vault has no lifecycle generation; deletion erases it whole, 1C), and `counts quarantine objects whose deletion is overdue, for the worker alert line` (the worker's cross-account alert; the vault's alarm retries its own deletes, 1B-T4). `after an error reply the server closes the connection instead of reading an endless body` is ported as the Worker's analogue: once the intake refuses, the body is cancelled and read no further. The 17 cases of `import-preview.integration.spec.ts` the plan lists are all ported; where the API reads `GET /v1/imports/:id/preview` (1B-T10's route), the test reads the stored `import_previews` and `import_candidates` rows instead.
- **P3. The workerd test rig.**
  - `@api/imports/fixtures/synthetic-parse` imports `sharp` and cannot load in workerd (the planner's probe: "Could not load the sharp module"). Its `csvRows` is copied into `support/files.ts` with a comment saying why; `SYNTHETIC` and `meteredStream` from `synthetic-uploads` load and are imported.
  - The API's legacy CSV samples are files on disk, which workerd cannot read: `SYNTHETIC.csv` and `csvRows(6)` stand in. Workbooks are `SYNTHETIC.xlsx` (a ZIP header), because the parse is faked.
  - `getQueueResult` in `@cloudflare/vitest-plugin` 1.4.7 records a retry but not its delay (`dist/worker/lib/cloudflare/test-internal.mjs`, line 782: `retryMessages.push({ msgId: message.id })`). `parseBatch` therefore wraps each message's `retry` to record `delaySeconds`, and `outcomeOf` reports `{ acked, retried, delaySeconds }`.
  - A client that goes away mid-stream: the API's test sees status 0 (its socket is gone). The Worker's own answer, `400 UPLOAD_INCOMPLETE`, is asserted instead; the stored outcome is the API's.
- **P4. The parse starter also re-sends an import left `parsing` (R32, strengthened).** The plan's condition names `queued` imports. A consumer that dies mid-parse leaves its job `parsing`; if the queue then discards the message, the job would read `parsing` forever, which is Review Focus 4. The starter's condition is `status = 'accepted' AND parse_state IN ('queued', 'parsing')` with `enqueued_at` null or at least `PARSE_RESEND_MS` old. `parseSource` sets `enqueued_at` on every parse start, so a running parse is never re-sent within the hour, and the consumer's 15-minute limit is far inside it. Pinned by the `crashed` import in the stopped-arriving case (mutant M16).
- **P5. A held message puts the job back to `queued`.** `parseSource` answering `held` sets `parse_state = 'queued'` (and `enqueued_at`), so a job held after a dead attempt does not read `parsing` while it waits. It spends no attempt.
- **P6. Deadlines a writer must keep (PR #348's notes).**
  - `finishUpload` publishes its parts in its own set-based statement over the job's `import_parts` rows, with `AND status = 'reserved' AND delete_after > now`, as `publishObject` does; if fewer rows than parts are published, it throws, and the call's transaction rolls back (mutant M7). It also refuses outright once the upload's receive deadline has passed, which is earlier than any part's own deadline (the receive deadline plus `RESERVATION_GRACE_MS`).
  - `recordPreview` is a separate vault call made after the image PUT, so its context (and `c.now`) is read after the PUT, never before. It publishes the image only while the reservation is this job's, still `reserved`, `delete_after > now`, **and** inside its own deadline, `created_at + RESERVATION_GRACE_MS > now`. A failed R2 delete moves a given-up reservation's `delete_after` a minute on (1B-T4's failure path), so `delete_after` alone could let a writer publish past its own deadline (mutant M8).
- **P7. Due times act at their own instant.** Every rule in `pruneUploads` is inclusive (`<=`), as 1A-T8b ruled for retention, so `uploadsDueAt` moves past each one (ruling R37; mutant M21). The row drop is `gogospend_prune_import_uploads`: a row that is not `receiving` goes 30 days after `coalesce(finished_at, expires_at)`. The API's extra condition `created_at < now - 24 hours` is implied (both times are at or after `created_at`), so it is left out, and `uploadsDueAt` stays exact. `pruneUploads` also clears file names 8 days after acceptance (the API's import maintenance), which the ported retention-hook case needs.
- **P8. An expired import.** `pruneUploads` ends an accepted import that was not parsed at its 24-hour expiry, as `gogospend_end_import`: a `queued` or `parsing` job becomes `cancelled`, the upload `expired` with its name and digest cleared, and its raw parts are due now. A parsed import keeps its rows; its parts expire on their own 24-hour deadline.
- **P9. `parseSource` names only published parts.** It reads each part's size and SHA-256 from the registry (`vault_objects`), as `gogospend_import_parse_source` reads `object_publications`. If fewer parts are published than `part_count`, the job fails `quarantine_missing` there, the API's count check in `readQuarantine`.
- **P10. The vault functions take a `FileContext`.** The plan writes `beginUpload(c: VaultContext, ...)`; a `VaultContext` is a `FileContext`, so the handlers pass theirs, and the tests call the functions directly inside `runInDurableObject` with a chosen clock.
- **P11. The isolate limit.** `uploadRoute` checks the `ocr` gate for an image first (before any byte is read, as the API's controller), then takes one of `MAX_UPLOADS_PER_ISOLATE` (16) slots, answering 503 `SERVICE_UNAVAILABLE` with `retry_after_seconds` 5 when none is free. `uploadsInFlight()` is a test seam for the case that proves it (mutant M15).
- **P12. Sizes leave SQLite as text.** Upload sizes, part sizes and the quota's byte sums are read with `CAST(... AS TEXT)` and turned into numbers in code (Global Constraints, Exactness); every one is at most 50 MiB.
- **P13. A reply from the container is checked for its shape** (`isParseServiceReply`) before the consumer uses it; anything else counts as `parser_unavailable`. A message that does not name a vault id (64 hex) and an import (a UUID) is acknowledged and logged `parse_message_malformed`, since retrying cannot help.
- **P14. A record the tables refuse throws.** `recordPreview` relies on the table CHECKs for the candidate rules, as the API's routine does. A throw rolls the block back; the consumer then retries with the attempt spent, so three attempts bound it.
- **P15. `header_fingerprint` is not stored.** `PreviewRecord` carries it (P4-T10), but neither the API's `import_previews` nor the vault's has a column for it. P4-T11 owns its storage.
- **P16. The Docker proof (plan Step 8) is SKIPPED:** Docker is stopped by the controller's order.
- **P17. An import sent twice is parsed once (B6, the 1B-T4 follow-up).** `markStarted` is not an at-most-once guard, so two `startPendingWork` runs that overlap (a request's `waitUntil` and the alarm) can both send one import. The consumer runs one message at a time (`max_concurrency` 1), and `parseSource` skips a job that is no longer `queued` or `parsing`, so the second message is acknowledged, the parser is not called again, no attempt is spent and nothing is recorded twice. Were two deliveries ever to overlap, the later `recordPreview` would find the job no longer `parsing` and record nothing. Pinned by `an import sent twice by overlapping starts is parsed once; ...` (added by the second planner) and mutant M27. A duplicate that arrives after a retryable failure is a real attempt and spends one, as any delivery would; three attempts still bound the job.
