## Planner rulings (the calls this brief makes, with the reason for each)

- **P1. `writeExport` takes the vault's context as a function, not a context.** The plan writes `writeExport(c: FileContext, deps: { bucket; active(c) }, id, options?)`. Its context would carry one clock reading from before the PUT, and `publishObject`'s deadline check trusts `c.now` (the 1B-T4 follow-up: build the publish context after the PUT). So the signature is `writeExport(v: ExportWriter, id, options?)` with `ExportWriter = { context(): FileContext; bucket: VaultBucket; active(c: FileContext): boolean }`, the shape `deleteDueObjects` already takes. The read and the key's reservation are one block on one `v.context()`; the PUT runs outside every block; the publish is a second block on a fresh `v.context()`. `UserVault#writeExport(id)` passes `{ context: () => this.fileContext(), bucket: this.bucket, active: (c) => this.isActive(c) }` and returns only `{ outcome }` over RPC. Tests pass a context function with a chosen clock (`writerOf` in the test file). Pinned by mutant M7.
- **P2. ExportService's two names and `parseExportFilter` are restated in `exports.ts`, and a Node test pins them to the API's.** The plan says to import `parseExportFilter` and `EXPORT_REQUEST_KIND` from `@api/exports/export.service`. That module cannot load in workerd: its database imports (`database/owner-transaction.ts`) reach `drizzle-orm/node-postgres` and `pg`, and the planner's first workers run failed with `SyntaxError: Cannot use import statement outside a module` in `pg/lib/connection.js`. So `exports.ts` defines `EXPORT_ENTITY = 'export'`, `EXPORT_REQUEST_KIND = 'export.request'` and `parseExportFilter` (the API's one line, over `parseHistoryRequest` from `@api/history/history-query`, which the vault already loads), and the registry imports the two names from there. `test/exports-port.test.ts` runs in Node, where `export.service` loads, and checks that the names are equal and that both period parsers answer twelve inputs the same, refusals included (mutant M25). The precedent is 1B-T5's P3 (`csvRows` copied because `synthetic-parse` imports `sharp`). `@api/exports/csv-writer` and `@api/exports/export-handler` (`exportRowCells`) load in workerd and are imported, not copied.
- **P3. A writer never publishes past its own deadline; past it the write throws, so the step retries.** The publish block reads the export key's reservation and refuses it once `created_at + RESERVATION_GRACE_MS <= now`, even if a failed R2 delete moved `delete_after` a minute on (the 1B-T4 follow-up; 1B-T5's P6 does the same in `recordPreview`). It throws rather than answering `skipped`: a skip would leave the export `pending`, already started, until `pruneExports` fails it a day later, while a throw makes ExportWorkflow's step retry under a fresh key (B4), as the API retries `export_not_recorded`. `publishObject` still checks `delete_after > now` itself. Pinned by `a write whose PUT ends past its own reservation deadline publishes nothing, even when a failed delete moved it on` (mutants M7, M8).
- **P4. An export started twice is written once (the 1B-T4 follow-up: overlapping runs may start an item twice).** The Workflow instance's id is the export's id, so `createOnce` turns a second start into a no-op (`create` throws, `get` finds the instance). Two writes that do overlap (a retried step whose first attempt is still running) each read and store under their own key; the publish block rechecks that the export is still `pending`, so the second answers `skipped` and its reserved key is deleted at its deadline. Pinned by `an export started twice by overlapping runs is written once` (mutant M10).
- **P5. The vault refuses an account that is not active before any export route, in place of the API's lifecycle generation.** `call()` answers 403 `ACCOUNT_UNAVAILABLE` for a `deleting` vault, so `exportStatus` has no `expired`-for-another-generation branch, and the ported case `a ready export cannot be granted or downloaded once the account is deleting or locked` asserts 403 for the status, the grant and the download (a vault has no `locked` or `disabled` status and no lifecycle generation). Background work checks the vault itself: `writeExport` answers `skipped` for a vault that is not active, at the read and again at the publish (Review Focus 1, mutant M4).
- **P6. Ported, changed and not-applicable cases.** `export.integration.spec.ts` has 22 `it`. 19 are ported by name; 3 are not applicable, one receipt line each: `an export cancelled by an account lifecycle transition mid-read publishes nothing` (a vault has no lifecycle generation, and its read is one synchronous pass that nothing can interrupt), `leased export reads are limited to the export lease, its account and its stored period` (PostgreSQL roles and leases; the period's edges are pinned by the fields case), and `the exports table's own policy hides another account's rows` (row-level security; a vault holds one account). Ported in changed form: the fresh proof is the token's `auth_time` (B7) and `proof_id` is never consumed (B8), so the wrong-purpose and other-command halves go and a second request with the same proof id is another export; the concurrent edit commits its three edits while the file is being stored, after the one-pass read; the failed-cleanup case keeps its "a later sweep deletes the file" half (the vault's failed delete stays due a minute later, 1B-T4), and the cross-account overdue count is the API worker's alert; `recording a file needs ...` becomes a write that is skipped for a ready or failed export; the runtime-log case drops `lines.length > 0` (the vault Worker writes no request log lines); `a too-large export ... is not an operator alert` asserts that the write answers `too_large` with no error logged. The API retention spec's `export requests are purged 30 days after the request; the receipt stays compact` (1A-T8b listed it as 1B's) is folded into the plan's `pruneExports purges an export 30 days after its request ...` case (404 after the purge, the command's status reads `purged`, one purged change). `jobs.db.test.ts`'s `writes a requested export, streamed back with its length, and never serves a tampered file` is ported whole.

Pinned by `an account can have at most two exports open; a third waits` (mutant M24).
