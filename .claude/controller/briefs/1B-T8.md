## Planner rulings (the calls this brief makes, with the reason for each)

- **P1. `buildSnapshot` takes the vault as a writer, not a context (1B-T6's P1, as the controller asked).** The plan writes `buildSnapshot(c, deps: { bucket; active(c) }, id, options?)`; its context would carry one clock reading from before the PUTs, and `publishObject`'s deadline check trusts `c.now` (the 1B-T4 follow-up: build the publish context after the PUT). So the signature is `buildSnapshot(v: SnapshotWriter, id, options?)` with `SnapshotWriter = { context(); bucket; active(c) }`, the shape `writeExport` and `deleteDueObjects` take. The read and the chunk keys' reservations are one block on one `v.context()`; the PUTs run outside every block; the record is a second block on a fresh `v.context()`. `UserVault#buildSnapshot(id)` passes `{ context: () => this.fileContext(), bucket: this.bucket, active: (c) => this.isActive(c) }` and returns only `{ outcome }` over RPC. Pinned by S16.
- **P2. The build checks that the vault is active when it reads and when it records** (the controller's note, from 1B-T6's review m-1). Either check answers `skipped`: before the read nothing is read, reserved or stored; at the record nothing is recorded, and the reserved chunk keys are deleted at their deadline. Pinned by S13 and S14.
- **P3. A build never publishes past its own deadline (the 1B-T4 follow-up).** The record requires every chunk key still `reserved` with `created_at + RESERVATION_GRACE_MS > now` (one statement over one JSON parameter, ruling R57), even when a failed delete moved its `delete_after` a minute on. Past it the build throws, so the step retries under a fresh attempt token (B4). This is the vault's form of the API's `a build that runs out of time publishes no manifest`. Pinned by S16, S17 and S28.
- **P4. A view read below the purge watermark (or the retention line) throws; the plan says `skipped`.** The plan's record writes "otherwise `skipped`", and its ported purge case says the build "answers `skipped`". A skip would leave the snapshot `pending` with its Workflow complete: a client polls it and gives up, its next request reuses it as the open build, and it stays stuck until `pruneSnapshots` fails it a day later. The API retries this case (`handlers.ts`: "Not published but still held: the manifest was refused - retry", `snapshot_not_recorded`). So the record throws, SnapshotWorkflow's step retries with a fresh read after the purge, and the ported case asserts the rejection, then that the retry is recorded without the purged note. The other two refusals stay `skipped`, as in 1B-T6: a snapshot no longer pending (another attempt recorded it, or it failed) and a vault no longer active. Pinned by M4 and S29.
- **P5. The purge watermark is read from the change log, in SQL.** The API stores `purge_revision`; the vault reads `max(revision)` of its `purged` changes, which is the same number (a purge writes them, and a purged head never moves again), so `retention.ts` and the schema are unchanged. `purgeWatermark` answers it as text (`Revision`), not the plan's `number`, because revisions leave SQLite as `CAST(... AS TEXT)` (Global Constraints); every other use compares it inside SQL. The API's purge deletes the snapshots built before it; the vault's purge (1A-T8b's) does not, so each read checks the watermark: `snapshotStatus` answers `expired` below it, `snapshotChunk` answers null (404), a request never reuses a snapshot below it (the plan's reuse rule, plus this), the record refuses a view below it (P4), and `pruneSnapshots` deletes such a snapshot and makes its chunk keys due at once. Pinned by M4, S5, S9, S12, S31, S34, S35 and S37.
- **P6. A chunk download streams with a slot, as `serveExportFile` does (the controller's R96 and R97 notes), not the PostgreSQL edge's whole-body `get`.** `SNAPSHOT_SLOTS = new DownloadSlots(4)`: the export download's number per isolate, in a pool of its own. The API counted none because it read a chunk whole (at most about a mebibyte); the vault streams it, so it takes a bound. A device downloads its chunks one at a time (`apps/app/src/sync/reconcile.ts`), and a 503 carries `retry_after_seconds` 5 into the app's sync backoff. `matchingObject` refuses an object whose size or recorded digest no longer matches its record (404), and `verifiedChunks` checks the digest as it streams. **R97:** a client that goes away mid-download keeps its slot in workerd; this task adds no abort fix, and the follow-up fix-download-aborts must cover `serveSnapshotChunk` (`GET /v1/sync/snapshot-chunks/:grant`, `SNAPSHOT_SLOTS`) with the others. Pinned by D1 to D5.
- **P7. The ten-times memory proof, and how it runs.** `seedLedger(user, 50_000_000)` writes one wallet, one category, then records with a Thai note and merchant (each with its change row and head, under a revision of its own) 1,000 per `transactionSync` until `ctx.storage.sql.databaseSize >= 50_000_000`. In the planner's runs that is 33,000 records and a 50.1 MB file; the snapshot holds 33,002 entities in 19 chunks, 19.6 MB stored. The build runs inside the vault on SQL whose entity read refuses `toArray` and counts its rows. **Time** (the planner's three final runs: `proof/green.log`, `gate-focused.log` and `memory-run.log`): seeding takes 2.4 to 3.2 seconds, the build about 0.6 and the export about 0.3; the whole case 3.3 to 4.2 seconds, with a 300-second timeout. **Memory** (what the case asserts): the build holds at most what it stores plus one chunk and the longest line (`peakHeldBytes` at most 20,644,143 in those runs, against a bound of 20,644,976), and the export at most twice its CSV (29,730,452 for 14,865,226 bytes). The planner also sampled resident memory with `run-memory.sh`: the workerd processes of a run of the ten-times case alone peaked at 385 MiB, against 158 MiB for a run of the empty-account case alone (`proof/memory-peak.txt`, `proof/memory-baseline-peak.txt`). That is the whole process (the runtime, the test runner's isolate, Miniflare's SQLite and R2 storage, and the vault's isolate), not the vault isolate that the 128 MB limit governs, so it is a record, not a check, and you do not repeat it. **Load:** the case runs only inside FOCUSED, which always holds the heavy lock, so no other workers suite runs beside it; every assertion compares bytes and counts, never time, so a slow machine only makes it slower; the record count is whatever reaches 50,000,000 bytes (SQLite's page fill varies by tens of kilobytes with the random ids, 50,130,944 to 50,167,808 bytes at 33,000 records in the planner's final runs, while one batch adds about 1.5 MB, so the variation can only add one more batch). The deployed isolate's 128 MB limit is not enforced in workerd: Step 7's named risk, SKIPPED.
