## Planner rulings (the calls this brief makes, with the reason for each)

- **P1. Switching the area for the catalogue.** `RecordScreen`, `HistoryScreen` and `useRecordActions` take an optional `conflictArea?: boolean`, defaulting to `isRedesignEnabled('conflict')`. The render tests switch the area the plan's way (`vi.stubEnv('EXPO_PUBLIC_REDESIGN', 'conflict')`); only the catalogue's six sections pass `conflictArea`. Why: `EXPO_PUBLIC_*` values are fixed at build time, and the catalogue's every-section and screen-reader tests draw all sections in one run with the area off, where `record-conflict` must keep today's panel. It follows the screens' existing `now` prop.
- **P2. The hook's open choice.** The hook keeps the open choice in a ref beside its state (`openRef`, `{ choice, kept }`), and `load` reads a stored one with `diary.getView()` at call time. `load` is an effect dependency, so it must not depend on the diary view (a re-kept choice would reload it in a loop), and a value read from the last render can be one render behind a `keepChoice` or `dropChoice`.
- **P3. Use yours is `submitEdit()` while a choice is up**, as P2-T6 made `submitEdit()` "Apply my change" during today's conflict. It sends `resendForChoice(choice, editing.conflict)` under slot `choice:<id>`; Try again calls `submitEdit()` again and so resends the same key.
- **P4. Frozen.** `ChoicePanelProps` has no frozen state, so while "Use yours" is unconfirmed the hook returns `choicePanel: null` and the screen shows only the "Not confirmed yet" notice with Try again (no Back, no cards, no Decide later), as today's frozen edit offers only Try again. The choice stays kept until the answer is known.
- **P5. `discardChoice`** is one field beyond the plan's `choicePanel` on `RecordActionsState`: "Discard my change" needs an action, and the screen draws it only where the record reads as deleted (the deleted branch) or missing (`not_found`/`deleted` load error).
- **P6. Offline** means the read failed with `network` or `unavailable`: the panel compares with the stored `server` and `canSendYours` is false. Any other failure (signed out, an update needed) shows today's load problem; the choice stays kept.
- **P7. Dropping never fails the flow.** A diary that refuses `dropChoice` keeps its copy; the next open finds it settled (and drops it) or offers it again. It never loses the person's change.
- **P8. `conflict_shown`** is sent from the rule, only in the area: once when an edit is refused with a usable record, and once more when "Use yours" meets yet another change (a new refusal shown). Never from a render, a reopen or a card change. Its properties are `reason_code: 'VERSION_CONFLICT'`, `screen: '/spend/record/[id]'` (the pattern, never the id) and the controller's `origin: 'app'`.
- **P9. The screen around the panel** follows the board: the stage title is "Edit entry" (แก้ไขรายการ), with Back while the phone keeps the choice (leaving keeps it, like Decide later). A phone that cannot keep the choice has no Back and no Decide later: it must choose now.
- **P10. Which choice the phone can keep.** Only with a diary whose phase is `ready`; a `keepChoice` that rejects counts as cannot keep. Then the choice lives on the screen only, the panel shows `cannotKeep` in place of `keptHere` (which would be untrue), and Use yours and Use the server's still work.
- **P11. History's caption** is a `ChoiceWaitingCaption` under the row, in `HistoryParts.tsx` as the plan says, ink and bold like RecordRow's own "needs a look". It is not inside the row's spoken sentence: that is `RecordRow`'s (the kit's), not this task's.
- **P12. No new copy key.** The board's hidden legend "เลือกแบบที่จะเก็บ" has no line in the plan's table, so the radio group is named by the heading. Every string in the panel, the caption and Discard my change is from `conflictCopy.draft.ts`; the screen's other words are existing catalog strings (`Edit entry`, `Back`, `Restore`, `Try again`).
- **P13. Extra tests** beyond the plan's names, each pinning a plan bullet: in `RecordScreen.render.test.tsx`, `use yours meeting yet another change ...`, `once use yours is acknowledged the choice is gone ...`, `an unconfirmed "use yours" is frozen ...` and `use yours refused without a usable record ...` (P2-T6's notice rule); in `ChoicePanel.render.test.tsx`, the Thai words and the stacking at large text; one History render case (the plan names the file but no case).
