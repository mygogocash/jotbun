## Findings

### Minor 1. M46 is not equivalent: the string guard is what refuses `per_base: null`, and no test pins it

`rates.ts:41` `typeof value.per_base === "string" && canonicalQuote(value.per_base) === value.per_base`. `canonicalQuote(null)` returns `null` (`currency.ts:128-130`, `typeof text !== "string"` gives null), so without the guard `null === null` is true and a null quote is accepted. The brief (line 115), the receipt (lines 19 and 22) and the commit body ("48 mutants killed, one equivalent") all say "`canonicalQuote(x) === x` is already false for any non-string `x`", which is false for `x = null`.

- `probes/m46.out`: committed code refuses `{ JPY: { per_base: null, day: '2026-11-02' } }`, the M46 mutant accepts it.
- `probes/review-m46.test.ts` (one case, run beside `trips.test.ts`): committed code 10 of 10 pass; with M46 applied, 1 failed, 9 passed (`expected true to be false`). `rates.ts` restored and `cmp`-identical to the worktree afterwards.
- Fix: add `{ rates: { ...today.rates, JPY: { per_base: null, day: '2026-11-02' } } }` to test 9's bad list, and correct the receipt's mutation line (49 mutants, all killed once that case is in). Same severity as P6A-T1's minor 1 and 4 (a wrong equivalence claim).

### Minor 2. C2's reason for counting backward is not pinned: a forward count passes all nine tests and makes `isTripSnapshot` throw in 9999

`trips.ts:136` counts back from `ends_on` so that `addDays` never leaves year 9999 (C2). Mutant R1, `endsOn <= addDays(startsOn, TRIP_MAX_DAYS - 1)`, gives the same answer everywhere else, and none of the planner's 49 mutants is it (M1 changes the length, not the direction).

- With R1, `trips.test.ts`: 9 of 9 pass.
- `probes/forward.out`: a one-day trip on `9999-12-31` throws `RangeError: addDays is outside years 0001-9999.` under R1; the committed code answers `true`. Any start in 9999 throws under R1 (9999 has 365 days).
- A throwing validator escapes the app's transport as a raw `RangeError`, not `invalid_response` (`apps/app/src/api/client.ts:416` calls `validate` unguarded).
- Fix: add `{ starts_on: '9999-12-31', ends_on: '9999-12-31' }` (and, if wanted, `'9999-01-01'..'9999-12-31'`) to test 6's accepted list.

### Nit 1. The receipt's notes for later tasks name keys only; the strict reader also needs the values right

A phone on this build now refuses a whole delta page over one bad trip or settings snapshot (probe: "page with a bad trip, this commit (skip): false"; the build before skips it). Two constraints are worth adding to the receipt's notes, or the integrator's:

- P5-T9 must apply the contract's value rules in its command, not just its keys. The `trips` table's checks (`0002_currencies_trips.sql:87-98`) are looser than `isTripSnapshot`: dates before 1970, any length, any three capitals, and `trim()` of spaces only, where the contract requires 1970 to 9999, at most 366 days, the ISO table and `normalizeName`'s output.
- P5-T6's `TodayRates = RatesTodayDto & { etag: string }` (plan line 377): `isRatesTodayDto` refuses extra keys, so `readTodayRates` must check the DTO without `etag`.
