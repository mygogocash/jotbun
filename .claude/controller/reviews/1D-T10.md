## The questions in the assignment

### Authentication
- **Only a valid token for a live session of this vault upgrades.** The Worker runs route, body, gates, client version and token before the branch (`handler.ts:130-133`); the vault's `fetch` then refuses an erased instance, parses the claims, and runs `ensureAccount`, the principal charge, `assertSession` and the read charge in one `transactionSync` before `acceptLive` (`user-vault.ts:171-198`), in `call()`'s order.
  - P1, expired token: `401 UNAUTHENTICATED`, `res.webSocket` null, the vault holds 0 sockets.
  - P2, another account's claims sent straight to the vault: `500 INTERNAL_ERROR` (the `VaultOwnerMismatch` path, as `call()` answers it), no socket, `account_state` unchanged.
  - P11, token issued before `not_before`: `401 SESSION_REQUIRED`. P10, account `deleting`: `403 ACCOUNT_UNAVAILABLE`, 0 sockets. Revoked session and erased vault: the task's own cases.
- **No session header needed or trusted (R78).** P3: opening with token sid A and `x-gogospend-session: <B>` binds the socket to A (attachment `sessionId` = A); B's logout leaves it open; A's logout closes it with 4401. The Worker forwards only `upgrade` and `x-vault-claims` (`live.ts:154-156`).

### Pokes
- After a commit every other session gets exactly one `{"revision":"<n>"}`; the caller's session gets none (task cases; P5: ten parallel creates gave exactly ten pokes, revisions 1 to 10 in order).
- Nothing is poked on a refused call, a read or a replay: P4, a 422 create, a 200 read, a 201 idempotent replay and a 409 duplicate id left B with only the original poke before its pong.
- Pokes survive hibernation (task case, with a marker proving a new instance); a send to a closing socket is skipped and the fan-out goes on (task case).
- Burst: neither the plan nor the spec asks for coalescing ("after each commit"), and the server does none. Load is bounded by the vault's budgets (`principal` 360 a minute per account, `write` 60 per session, `RATE_BUDGETS`), at most 19 other sockets, about 20 bytes each; the phone coalesces pokes into its `live` flush (1D-T5). Matches the plan.
- Revision moves only in `commands/change-log.ts:28` (through `call()`) and `retention.ts:122` (through `alarm()`), both wrapped, so no commit path escapes the poke.

### Session ends
- `call()` reads `before` after the erased refusal and runs `afterCall` in a `finally` (`user-vault.ts:113-149`); `alarm()` likewise with `null` (`:91-101`). A refused call still closes ended sessions (task cases M2, M12 to M14). P9: with `status = 'deleting'`, an alarm closed both sockets with 4401.
- `afterCall` never throws: P6a, `afterVaultWork` with an unparsable `before` returns and logs exactly `{"level":"error","event":"live_after_call_failed","failure":"SyntaxError"}`. P6b, `getWebSockets` made to throw during a committing create: the reply stays 201. Not pinned by the suite (minor 1).
- Sign-out closes that session's socket with 4401, which the app's channel treats as the end until the next `start()` (`liveChannel.ts:40, 74`). 4409 for replaced and over-limit sockets also stops the channel there, as the plan intends.
- P12: an erased instance (in memory) keeps its open sockets, because `call()` refuses before `afterCall`. That is the plan's order; the receipt hands closing them in `erase()` to 1D-T12. No finding.

### The implementer's flag: `before` outside the `try`
Acceptable, not a defect. The plan's order puts it there ("read `before` ... outside the transaction; run the transaction and its `catch` unchanged"). P7, with `sync_state` renamed away: a direct `call()` RPC rejects (`Error`) instead of returning a reply, and the Worker's `errorResponse` answers the same `500 INTERNAL_ERROR` that `toProblemReply` would, logging the class name only (`problem.ts:70`). No ended session can be missed, since nothing ran. The read is a one-row primary-key lookup on a table the constructor's migration guarantees, so only a storage failure (which would fail the block too) reaches it. Only the comment on `call()` ("Every error becomes a reply") is now slightly overstated: nit 2.

### webSocketClose answering the close (deviation 1)
- Correct for the installed workerd (1.20261019.1). F2: naming `web_socket_auto_reply_to_close` in `wrangler.vault.jsonc` makes workerd say it "became the default as of 2026-04-07 so does not need to be specified anymore", so the flag is already on at compatibility date 2026-10-01. Yet F3 (flag on, no reply in the vault) and F4 (default, no reply) both fail the same two cases as M10: the phone's close never completes. The runtime's auto-reply does not cover hibernatable sockets here, so the vault's reply is needed. F1 (`web_socket_manual_reply_to_close`) and F2 with the reply: 21 passed.
- Harmless if a later runtime also replies. P17: after a close the runtime completed (`readyState 3`), a raw `close()` does not throw and `webSocketClose` returns. P16: on a CLOSING socket, a second `close()` does not throw, and `webSocketClose(ws, 1005, '')` returns (fallback path). `closeSocket` catches anything a future runtime might throw.

## Findings

### Blocker

### Major

### Minor
1. **"`afterCall` never throws" is not pinned by any test.** Reviewer mutant G1 removes the `try/catch` in `afterVaultWork` (`live.ts:120-127`): `live.test.ts` still passes 21 of 21 (`logs/mut/mutant-G1.log`). The brief lists this rule first for the reviewer, and its failure mode is real. With G1 applied, probe P6b (a committing create while `getWebSockets` throws) gets **500** for a write that committed (`logs/G1-vs-P6b.log`), so the phone would retry or report a failure for a saved record. The code is right today (P6a, P6b pass), so this is a test gap only. Suggested case for `live.test.ts`: make `state.getWebSockets` throw through `runInDurableObject`, create a wallet, expect 201 and the revision moved (P6b's shape), and optionally spy `console.error` for `live_after_call_failed` with the failure name only (P6a). It can land with this PR or in 1D-T11, which reuses the same `finally`.

### Nit
1. **Other reviewer survivors (each correct by reading, untested):** G2, `fetch` without the `principal` charge (the 120-open test never reaches the 360 account budget); G3, `webSocketClose` without the 1000 fallback (no case closes with 1005); G4, `<=` for `<` against `not_before` (the test raises `not_before` by 60 s, so the boundary second is not checked; `assertSession` uses `<`); G6, the open's read budget keyed by account instead of session (one session in the test). G5 (keep sockets without an attachment) is equivalent: the attachment is written in the same synchronous turn as the accept.
2. **Comments that overstate.** `closeSocket` (`live.ts:46`) says a close on a socket already closing throws and is skipped; in this workerd it does not (P16: the second `close()` returns; P8: `closeEndedSessions` returned 3 when one of the three sockets was already closing). Only the return counts are affected, and nothing in this task reads them; 1D-T12 should not rely on them as "newly closed". Likewise `call()`'s comment "Every error becomes a reply" (`user-vault.ts:110`) no longer holds for a failed `before` read (see above).
3. `VaultRoute`'s comments (`routes.ts:9-11` and `:17`, "A route has this or `worker`, except the public policy list") were not updated for the live route; the new `live` field documents itself, so this is cosmetic.
