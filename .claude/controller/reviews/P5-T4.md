   - **`wallets` table_info.** Identical, except that `currency`'s `dflt_value` goes from `'THB'` to `null` (call 5, see below) and the three look columns are appended.

### `PRAGMA defer_foreign_keys` in workerd behaves as the comment claims

Inferred from the implementer's mutant logs, which match the two signatures:
- **Without `ON`** (M4): `DROP TABLE wallets` fails at once, and the migration rolls back with `DrizzleError: Rollback`.
- **Without `OFF`** (M5): the counted violations survive to workerd's implicit commit. The object resets with "left the database in a state where constraints were violated: FOREIGN KEY constraint failed".

So `OFF` does clear the count that the drop added. This matches SQLite's `pragma.c`, which zeroes `nDeferredImmCons` when the flag is turned off. The suite's first case proves that keys are enforced at once again after `OFF`: an unknown wallet throws `/FOREIGN KEY/`.

Clearing the count also forgives any real violation made inside the window. The suite's dangling-reference join is the only backstop against an incomplete copy. My mutant A shows that it works: a copy with `WHERE archived = 0` is killed by 3 cases, including `{ refs: 5, missing: 0 }`.

### Triggers and views naming wallets (the case the brief said to look at first)

- **Today.** No trigger or view in `0000` or `0001` names `wallets`. The case's `before` is `[]`, so today it only proves that the new trigger exists. It is a guard for migrations integrated before this one.
- **Is the guard effective?** Yes:
  - A trigger `ON wallets` from an earlier migration is **dropped silently** by `DROP TABLE wallets`. Probe: before `["wallets_name_guard"]`, after `["wallets_currency_immutable"]`. The case's comparison would fail, so the guard catches it.
  - A **view** selecting from `wallets`, or a **trigger on another table whose body reads `wallets`**, makes the rename fail (`DrizzleError: Rollback`). The upgrade is refused and the shape is unchanged. Every case catches that.
  - In both situations the integrator must add the drop in step 1 and the re-create after step 4, as the plan says.

## Upgrade safety

- **One transaction.** The durable-sqlite migrator runs every pending entry inside one `ctx.storage.transactionSync`. Its catch calls `tx.rollback()`, which throws `TransactionRollbackError`, so the original error is replaced by "Rollback" (see nit 8).
- **The suite's failure case** (a pre-existing `settings` table, so step 8 fails) leaves:
  - the old `wallets` columns;
  - `transactions` without the new columns;
  - no `wallets_next`, `trips`, trigger or index;
  - the same rows and the same journal.

  Retrying in the same instance then succeeds.
- **A real next wake** (`review-wake.test.ts`, passed). A vault written by the 1A routes before the migration gets an obstructing `settings` table, and the release "ships" (full journal, eviction):
  - Two calls answer `500 INTERNAL_ERROR`. Each wake's `blockConcurrencyWhile` rejects (workerd logs `brokennessReason = broken.inputGateBroken`).
  - The storage keeps the old shape (`wallets` 9 columns, journal 2 rows).
  - Once the cause is removed, the next wake upgrades. `GET /v1/wallets` answers exactly what it answered before.
  - So the receipt's "the object resets and the next wake retries; a vault whose upgrade keeps failing refuses calls" is accurate.
- **Idempotence.** The suite's first case migrates twice and the rows do not change. The golden probe's evict-and-wake is a no-op.
- **A vault mid-erase, or freshly created.**
  - `erase()` runs `deleteAll()`, then the full journal inside `blockConcurrencyWhile`. That is the fresh path, whose schema matches an upgraded vault.
  - `files-erase.test.ts` passes on the merged tree: every table is empty, `trips` and `settings` included.
  - A vault in `deleting` state that wakes is simply upgraded with its rows; the deletion workflow then erases it.
- **Journal ordering.**
  - `0002` has `when: 1761523200000`, one day after `0001`.
  - The new assertions in `vault-schema.test.ts` check three things: contiguous `idx`, keys `m0000`..`mNNNN`, and strictly increasing `when`. They also check that a fresh vault's `__drizzle_migrations.created_at` equals the journal's `when` list.
  - Mutant B (`when` equal to `0001`'s) is killed by 11 cases, including "a new vault has every core table, migrated once" (the order check).

## Performance

Measured in local workerd on this machine (`review-structure.test.ts`, size cases):
- 90% expenses and 10% transfers;
- notes and merchants on every row;
- 2% deleted.

| Records | Seed | Upgrade (inside the object) | Database before → after |
|---|---|---|---|
| 100,002 | 0.55 s | **1.03 s** | 44.5 MB → 49.0 MB |
| 500,002 | 3.5 s | **4.66 s** | 224 MB → 247 MB |

- **Scaling.** The cost is linear, about 9.5 µs per record. The planner's 576 ms for 90,100 records (6.4 µs per record, leaner rows) is the same order.
- **Against the limits.** The spec's ten-times ledger (50 MB) is about 110k such records, about 1.1 s. The 30 s `blockConcurrencyWhile` limit would be reached only around 3 million records, a database over 1 GB.
- **Write cost.** The upgrade is one write transaction that rewrites every `transactions` row (the backfill) and grows the database by about 10%.
- **Not measured.** I could not measure on Cloudflare itself. That caveat stays (SKIPPED: no hosted runs).

### Minor

**1. Two migration tests break when P3's or P4's vault migrations are integrated, in either order, and the receipt says a new referencing table "needs nothing".**

`currency-migration.test.ts` upgrades through every later journal entry and then asserts exact final shapes. Simulations, with a stand-in for P3-T2's `source` column and P4's `slip_accounts`:
- **Later** (`mutD`, the stand-in as `0003`): 2 of 10 fail.
  - "every table that references wallets keeps its rows": `references()` after includes `slip_accounts` (`expected [ …(4) ] to deeply equal [ …(3) ]`).
  - "a record, wallet or category the previous release writes...": the exact `toEqual` meets the extra `source` key.
- **Earlier** (`mutE`, the stand-in as `0002`, this as `0003`): 1 of 10 fails, the same exact-row case. The referencing-table case passes, but vacuously: `slip_accounts` has no seeded rows, so its counts are 0 = 0.

Neither P3-T2 nor P4 lists this test file, so whoever lands second gets a red suite on a file outside their brief. Suggested fixes:
- compare only the 1A columns and this migration's eight in that case (or use `toMatchObject`);
- in the referencing-table case, compare the `before` tables only, and fail when a referencing table has no seeded row;
- correct the receipt's integrator note.

These are cheap to do before the merge.

**2. The rebuild fires every child's `ON DELETE` action, and the guard test cannot see it on an empty table.**

The implicit `DELETE FROM` inside `DROP TABLE wallets` runs foreign key actions even under deferred keys. Probe: a child with `ON DELETE SET NULL` had `wallet_id` nulled, and a child with `ON DELETE CASCADE` lost its row. Today every key to `wallets` is `NO ACTION`:
- `0000`: three on `transactions`;
- `0001`: `import_selection_rows`;
- P4's planned `slip_accounts`.

So nothing is lost. But the only guard is the row comparison, which needs seeded rows. Suggested: one assertion that every `foreign_key_list` row naming `wallets` has `on_delete = 'NO ACTION'`, and a line in the SQL header comment.

### Nit

1. **The receipt's status line is stale.** It names `8f04a3b`; the head is `f33cdf0`. Nothing under `apps/edge` differs between `800680d` and `f33cdf0` (only `packages/contracts/src/v1/privacy.ts`, its export and `scripts/ops`), and the Workers suite passes 258 of 258 on the merged tree.
2. **The "Path proven" parenthetical understates the suite.** `PRAGMA index_list` rows include `name`, so the suite's `index_list(wallets)` equality does pin `sqlite_autoindex_wallets_1`. The golden probe confirms the name before and after.
3. **The integrator note says "the comment in `schema.ts`".** There are two (`schema.ts:87`, `:340`).
4. **The SQL header says an earlier trigger or view "is dropped in step 1 and created again after step 4".** That reads as if this file does it; it is a rule for whoever adds one ("must be").
5. **STRICT on `settings` is not pinned by any test.** Mutant C (STRICT removed from all three new tables) is killed by the drift and NULL-primary-key cases through `wallets` and `trips`. `settings.id INTEGER PRIMARY KEY` stays non-null either way, so STRICT on `settings` alone would survive.
6. **Both `eaedc63` and P5-T1 (#331) add "## P5: Travel and currencies"** and its intro paragraph to the ledger. Keep one heading when both merge.
7. **Not only "the previous release" writes null home amounts.** Every record the current 1A writers create, until P5-T10 changes them, has `home_amount_minor` null (golden probe). The coalesce rule in the receipt stays correct.
8. **Observations outside this task's files** (follow-ups, not fixes here):
   - **The deferred-keys flag stays on after a failure inside the window.** A failure between `defer_foreign_keys = ON` and `OFF` leaves the flag on for the rest of workerd's implicit transaction. Probes with a view, a trigger body and a pre-existing `wallets_next`: `PRAGMA defer_foreign_keys` reads 1, an expense naming an unknown wallet is accepted at once, and the object resets at commit. Today this is contained, because both callers (`constructor`, `erase()`) run `migrate` inside `blockConcurrencyWhile`, whose rejection resets the object. Never call `migrate` where a failure is caught and the instance keeps serving.
   - **A failed upgrade cannot be diagnosed.** Drizzle's migrator turns every error into "DrizzleError: Rollback", and the constructor logs nothing. A `logFailure('vault_migration_failed')` before rethrowing would make a failing upgrade visible.
