### Minor

**m1. "One run at a time, in order" (brief P7) has no test: a mutant that drops the chain survives.**
- **Evidence:** `PushHost.tsx:88` chains each run on `runs.current`.
  - Replace it with `void register(binding, language).catch(() => undefined);` (R1), and all 13 cases of `PushHost.render.test.tsx` still pass.
  - They pass because every fake `registerDevice` answers at once. H20 holds only the other half (a failed run does not stop the next).
- **Why it matters:** without the chain, two runs overlap when the language or the session changes while a PUT is out.
  - Each run finds no current record, so both send.
  - The record is whatever finished last. Suppose the server applies the two PUTs in one order and their answers come back in the other. The server then keeps the old language while the record says the new one.
  - Every later run answers `unchanged` for up to a week, and pushes come in the old language.
  - The code is right today; nothing pins it.
- **Fix:** add the order case from `probes/reviewOrderProbe.render.test.tsx` (about 25 lines in the existing file's style). It holds the first `registerDevice`, rerenders with `locale="en"` and asserts that only `['th']` was sent until the first answers. It then expects `['th', 'en']` and a record in `en`. It passes on `7cdb3d9f` and kills R1.

**m2. The permission hook reads iOS provisional (quiet) delivery as `granted`, so P4-T21 will not ask a person whose reminders got quiet delivery, and that person's pushes will arrive quietly.**
- **Evidence:**
  - `pushRegistration.ts:40` counts `answer.ios?.status === IOS_PROVISIONAL` as granted, and `notificationPermission.ts:24-31` passes that on as `status`.
  - The reminders ask iOS with `allowProvisional: true` (`notificationsPort.ts:53`). That request can leave the phone at provisional without a prompt.
  - P4-T21's binding for sl-done (plan line 1096 onwards) says: "Turning it on asks for notifications when undetermined; denied opens es-notifications-off."
- **What happens:** with `granted`, sl-done and sl-settings neither ask nor show es-notifications-off.
  - Slip, statement, export and recap pushes then go to the Notification Center with no banner, sound or lock-screen alert.
  - This undercuts P3 (b)'s own reason: "so the person sees iOS's prompt and a refusal is a real one".
- **What is fine:** registration should count provisional as granted, since quiet delivery beats none. The gap is only in what the hook tells the screens.
- **Open on a device:** whether `ask()` while the phone is provisional brings up iOS's prompt. Apple's documents do not say. Opening the phone's settings always works.
- **Fix, the controller's choice:**
  - let the hook report quiet delivery separately (for example a `quiet` flag, or `undetermined` for provisional, in the hook only); or
  - carry it to P4-T21 as a binding. P4-T21's Files do not list `notificationPermission.ts`.

**m3. P3 (c)'s premise is wrong: the plugin entry changes no native config, because `aps-environment: development` is already in the base.**
- **Evidence:** I introspected the base `app.json` and the head's (`logs/introspect-base.json`, `logs/introspect-head.json`).
  - The only difference anywhere in the output is the `plugins` array itself.
  - Both have `ios.entitlements = { "aps-environment": "development" }`, the same Android permissions and no `UIBackgroundModes`.
- **Why:** `@expo/prebuild-config` 58.0.14 applies expo-notifications' own plugin, with its defaults, whenever the package is installed and autolinked.
  - See `withDefaultPlugins.js:150-155` (`versionedExpoSDKPackages`) and `createLegacyPlugin.js` (`withStaticPlugin` on the package).
  - expo-notifications has been installed since the reminders. So the base and the head run the same plugin with the same defaults.
  - The planner's `logs/gate/config-introspect.json` is the head's alone. It has the entitlement too, and there is no base run beside it.
- **What follows:**
  - The PR body's "Its one native change is the iOS entitlement `aps-environment: development`" should say there is no native change, and so should the handover's P3 (c) line.
  - The entry is still worth keeping: it is where D33 and P6C will pass `mode`.
  - The signing warning ("a local iOS build signed by a team without the push capability will not sign") is already true at the base. It is not new with this PR.
  - The receipt itself makes no wrong claim.

### Nit

**n1. The order of the first two early returns is not observable.**
- R3 (the session checked before the project id) survives.
- Both returns come before any read, fetch or send. Only the return value differs when both are null, and the host ignores it.
- So "no project id first, then signed out" holds in effect either way. No test is needed.

**n2. A failed registration waits for the next trigger.**
- A run that fails at launch (offline, say) runs again only at the next mount, session change or language change. The weekly renewal (S8) also runs only on those triggers.
- The plan asks for no more.
- If a phone kept open for days should still renew, a later task could also run on the return to the front (AppState `active`). Each run asks Expo's servers for the token.

**n3. A run in flight at sign-out can write `push-device` after the erase.**
- `registerPushIfNeeded` writes the record after the PUT answers (`pushRegistration.ts:143-144`).
- If that write lands after `eraseDeviceSettings()` (`DeviceDiaryProvider.tsx:71`), the record survives the sign-out, holding the token and the old session's hash.
- It is harmless: the next sign-in's hash differs, so it registers again, and the record holds no binding.
- The window is narrow: logout revokes the session on the server, so a late PUT is refused.

## The controller's focus, answered

- **The session (P6): confirmed.**
  - The record is exactly `{ token, platform, language, slipNotices, session, at }`.
  - `session` is `sessionHash(binding)`, the lowercase hex SHA-256 of the binding's UTF-8, through `expoSha256` (`PushHost.tsx:65`). The render case asserts the record with `toEqual`, and that no stored value contains the binding.
  - The PUT body is exactly the four contract fields, and the Node case passes it through `parseDeviceRegistration`.
  - No new file has a console call or an analytics emitter, and the transport and the slip client log nothing. The privacy case spies all five console methods and `recordAnalytics()`, and H27 dies on it.
  - The binding is a Better Auth session id (`session.ts:6`), so an unsalted SHA-256 cannot be reversed in practice.
  - The sign-out erase removes `jotbun.wallet.push-device` (`eraseDeviceSettings`, which erases by prefix), apart from n3.
- **Registration (P5): confirmed.**
  - The order: no project id, then signed out (nothing is read), then the permission, then the token. The permission is read with `getPermissionsAsync` and never asked (`port.asked` is 0).
  - The record is written only after `registerDevice` resolves (G17 is killed).
  - A failed PUT, or a token fetch that throws, answers `failed`, keeps no record and does not break the host's chain (H20).
  - Two runs at once inside the host are chained, but no test holds the chain (m1).
  - Calls from two places, the host and P4-T21's screens later, are not serialized at all (see the notes).
- **The lock and the tap (P7): confirmed, no gap found.**
  - `<PushHost />` is the first child inside `<WalletRoot>`. With the `wallet` area on, that is inside `LockGate`, whose `hidden` is `!setting.ready || locked || covered`.
  - Probe 1 shows `hidden` true on every render until the unlock. React batches `setSetting` and the `start` dispatch into one render, so no frame shows the setting read but the lock not yet up.
  - The push goes once, with `hidden` false, and is then cleared. Going to the background and unlocking again does not route it a second time.
  - Each response is taken once per identifier, so a cold-start response that also reaches the listener goes once.
  - On iOS, `lastResponse` is set on every tap and reset by `clear` (`EmitterModule.swift:31,37`). That matches clearing after the route.
  - `router.push`, called from the host's passive effect, cannot hit expo-router's "unavailable before the first render" throw. The imperative router is bound in a layout effect of the container's bridge (`routingQueueContext.js:124-134`), and `push` only enqueues.
  - The device check of a cold-start push stays SKIPPED (P15).
  - I found no path where a route shows behind the lock, and none where it goes twice.
- **The routes (P8): confirmed.** The four literal paths are typed, and all four route files exist. Only data that passes `isPushData` opens a screen.
  - `isPushData` demands exactly the keys `kind` and `ref`, one of the four kinds, and a ref of the right form:
    - null for `slips_ready`;
    - a UUID for statements and exports;
    - `YYYY-MM` with a month from 01 to 12 for the recap.
  - The statement and export routes are fixed literals, so their refs cannot steer them. The month is the only value that reaches a route, and it is checked.
  - A malformed month, an unknown kind or an extra key all answer null, and the Node case covers each.
  - Real pushes pass the exact-keys check on both phones:
    - iOS takes `data` from `userInfo["body"]` (`NotificationRecords.swift:331`);
    - Android parses `data.body` (`NotificationSerializer.java:70`).
    - Both are exactly the server's `{ kind, ref }`.
- **The foreground handler (R126):** `presentation` is the app's only handler; no other code calls `setNotificationHandler`. What changes from today:
  - **Today:** `_layout.tsx` loads `useReminderUpkeep`, which loads `localReminders.ts`, which imports expo-notifications statically. That import installs the library's default handler, which shows banner, list, sound and badge (`NotificationsHandler.js:23-30` and `:100`).
    - So a reminder that fires while the app is open shows as a banner, goes to the Notification Center and plays its sound. The reminders set no badge number.
  - **After:** once the host has mounted on a phone, a reminder (it carries no push data) is silent while the app is open.
    - No banner, no Notification Center entry and no sound: it is not shown anywhere, and it does not wait in the list for later.
    - Reminders that fire with the app in the background or closed are unchanged. The handler is asked only while the app is in the foreground.
  - **Pushes while the app is open:** `slips_ready` goes to the list only; the other three show a banner and go to the list. None plays a sound or sets a badge.
  - In the moment before the host mounts at launch, the library's default still applies.
  - This matches the plan's sentence and its case. The plan's "as today" is what is untrue under SDK 58.
- **The permission (P3 (b), P10):**
  - The request is `{ ios: { allowAlert: true, allowBadge: false, allowSound: true } }`: no badge and no `allowProvisional`. The Node case and G30 pin it.
  - The hook reads at mount and again on each return to `active`. `ask()` is the only request.
  - A failed request counts as denied; a failed read leaves the status as it was. `openSettings()` is best effort.
  - Off the phone, the answer is denied and nothing is asked.
  - Reading provisional as granted: see m2.
- **The config (P3 (c)):** nothing in the native config changes (m3).
