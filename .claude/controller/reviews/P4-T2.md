### Minor

- **m1. Two halves of the plan's matching rule are correct in the code but unheld by the tests** (MY1 and MY2 survive all 10 cases).
  - The plan (line 205): "a pattern with a Thai character matches as a substring (Thai has no spaces between words); any other matches whole words"; the brief's P8 the same. The matcher case (`catalog.test.ts:262-270`) checks the end of a word (`Makrobiotic`) but not its start, and has no name that mixes Thai with a Latin pattern.
  - MY1 lets a Latin pattern end a longer word (`SUPERMAKRO` is `shopping`). MY2 chooses by the name's script, so any name with a Thai letter in it matches Latin patterns inside words (`ร้าน Makrobiotic` is `shopping`). Thai payee names often put a Thai prefix before a Latin brand, so MY2 is the regression a later edit could most plausibly make.
  - **Fix:** add the three rows above to the matcher case's table (`catalog.test.ts:262-270`). Proven to pass now and to kill both mutants on assertions. Only `catalog.test.ts` changes, a file no other task shares (P5-T9 builds on this task's `real/` for `routes.ts` and `protocol.ts`, not this file).

### Nits

- **n1. The cache hands out its own array** (`catalog.ts:34`, `38`, `41`). Probe 6: an item pushed onto the list one call returns appears in every later call's list until the hour ends. P4-T6's planned use, `matchMerchant(name, patterns)`, only reads (its parameter is `readonly`), so nothing is wrong today. Answering `readonly MerchantPattern[]` (or a frozen array) would make the hazard a type error; the plan's signature says `MerchantPattern[]`, so that is the controller's call. Also, two calls in flight on an empty or stale cache each query D1 (no shared in-flight read), which is harmless at this size.
- **n2. Byte order is stated (ruling P6, the controller's focus) but not pinned:** MY4 survives, because no two album names of one bank and platform in the seed or the tests differ in case. Adding `a slips` and `B Slips` for one bank and platform to the unknown-bank case pins it (probe 4 tells the two orders apart).
- **n3. Two `If-None-Match` readings are unpinned:** `*` answers 200 (ruling P6, and the doc comment at `catalog.ts:83`), and a list with no space after its comma is 304. MY5 and MY6 flip them and survive. Pin both, or drop the `*` sentence from the comment. For the record, RFC 9110 section 13.1.2 makes `If-None-Match: *` false whenever a representation exists, which for a GET means 304; ruling P6 chose 200 because the phone never sends `*`. Either answer is harmless.

## Notes for later tasks

1. **P4-T6 (`writeSlip`, the matcher's first consumer):** read `merchantPatterns(env)` once per request, outside every vault block, and pass it to `matchMerchant` for each side, as the receipt says; do not sort or change the list (n1). The matcher's semantics at the edges, from probe 5:
   - `.`, `-` and `'` are word characters, so `MAKRO.` and `BTS.` do not match `makro` and `bts`;
   - a Latin brand written against Thai with no space (`7-ELEVENสาขา`) does not match;
   - a curly apostrophe is a separator (`LOTUS’S` keys as `lotus s`; the receipt's note);
   - capitals beyond ASCII are not lowered (`CAFÉ AMAZON` does not match a stored `café amazon`);
   - NFC keeps U+0E33 (SARA AM) apart from U+0E4D U+0E32 (NIKHAHIT, SARA AA), so a name typed one way misses a pattern typed the other;
   - a zero-width space between Thai words becomes a space, and a Thai pattern still matches across it.
