## Findings

### Blocker

None.

### Major

**1. The port's JWT cache can still hand out the previous account's (or the previous session's) token after an account switch or a fresh sign-in.** `betterAuthPort.ts` clears `cached` when a sign-in succeeds (lines 169, 176). But `accessToken()` (line 251) and `refresh()` (line 263) write `cached` unconditionally when a `token()` call returns. A `token()` request sent under the old cookie that returns after the sign-in therefore re-installs the old JWT. Later reads reuse it for up to 9 minutes (the 10-minute JWT less the 60-second margin).
- Probe 1 (port): a token read in flight across a switch from A to B leaves `accessToken()` returning a JWT whose `sub` is A.
- Probe 2 (provider): after `signIn` as B while active as A, with a sync-style `getAccessToken()` in flight, the snapshot is B, yet `getAccessToken()` returns A's JWT and `requestCredentials()` returns `{ accessToken: <A's JWT>, sessionId: <B's session> }`.
- Probe 3 (fresh sign-in): a forced refresh in flight across `freshSignIn` leaves the old session's JWT (old `sid`, old `auth_time`) cached.
- All three fail on `7bc2fe1` and on the merged tree.
- Why it matters:
  - The transport's epoch check cannot catch this: the stale token is read after the epoch moved. The request is stamped with B's epoch and carries A's JWT, so the vault (which reads `sub`/`sid` from the token, R78) serves A's vault to B's session. B's outbox writes would land in A's vault, which is D37's "never replayed to another account" in reverse.
  - It also breaks the plan's `requestCredentials` contract ("One token and the session id, read together").
  - It breaks the receipt's note for Task 6 ("after `freshSignIn` the port has no cached JWT, so the next token names the new session and its `auth_time`"). Task 6's deletion and export send their own credentials, which are never refreshed, so they would fail with the revoked old `sid` or a stale `auth_time`.
- This is the planner's finding 4, fixed for the sequential case only. The new test `a sign-in drops the cached JWT` covers only that case.
- Fix: keep a counter in the port that moves on every accepted sign-in and on `signOut()`. Have `accessToken()` and `refresh()` capture it before calling `token()`, and write `cached` only if it has not moved. Add probes 1 to 3 as tests.

**2. The device calls fail on a 204, and the receipt says the opposite.** The plan's Task 4 answers `POST /jotbun/devices/sign-out` and `POST /jotbun/sign-out-everywhere` with **204**. Better Auth 1.6.33's client parses an empty body to `null` (`better-auth/dist/client/config.mjs` line 41: `jsonParser(text) { if (!text) return null; ... }`), so a 204 arrives as `{ data: null, error: null }`. `tools/no-content.mjs` confirms this on the installed client. `mapSensitive` (line 142) turns `data === null` into `AuthUnavailable`, so `signOutDevice` and `signOutEverywhere` (lines 271, 277) report an outage on every success against the planned server.
- The fake answers `ok({})` for both (`fakeAuthServer.ts` lines 203, 215), so no test sees it.
- Receipt deviation 7 states "a 204 reads as an empty string and passes". That holds for better-fetch's default parser, not for Better Auth's.
- Today only `freshFlow`'s best-effort `signOutDevice(...).catch(noop)` uses these calls. Task 6 (sign out everywhere) and Task 8 (devices screen) will inherit the bug, and the receipt misleads them and Task 12.
- Fix: for the calls whose answer carries no data (`signOutDevice`, `signOutEverywhere`, and also `link` and `unlink`), treat `{ data: null, error: null }` as success. Keep `AuthUnavailable` only where data is required (`devices`, `signOutOtherDevices`). Make the fake answer `{ data: null, error: null }` for the two 204 routes, add a test, and correct deviation 7.

### Minor

1. **`freshFlow`'s `committing` and post-save superseded check are untested.** The code is right (probe 4 passes: a sign-out while the fresh sign-in is saving waits, then leaves no record, and the result is `cancelled`). But mutants R14 (drop `committing = write` in `freshFlow`) and R15 (drop the superseded check after the save) both survive the suite. Probe 4 kills R14. The brief's M9 covers only the check before the save. Add probe 4 as a test.
2. **A sign-out that lands while the fresh sign-in call is answering leaves the old session alive** (probe 5). Once the server has made the new session, the phone's cookie is the new session's. `signOutFlow` then reads the new session's JWT and pairs it with the old session id (`credentialProvider.ts` lines 281, 287, 291), so the vault revokes the new `sid`. `port.signOut()` signs out the new session, and `freshFlow` returns `cancelled` at line 244 without ever calling `signOutDevice(oldSessionId)`. The old session's cookie is gone from the phone, so nothing can use it, but it stays live at Better Auth and the vault until expiry (a ghost device for up to 30 days). Fix: in that superseded branch, `await deps.port.signOutDevice(oldSessionId).catch(noop)` before `forgetLateSession()`.
3. **Body-less POSTs to the jotbun routes.** `jotbunAccountClient.ts` lines 15 and 16 send `POST` with no body and no `Content-Type` (`tools/no-content.mjs`: `content-type=null body=none`). Better Auth's own `/sign-out` sends `{}` as JSON. 1C-T1's `handleAuthRequest` (`apps/edge/src/auth/handler.ts` lines 39 to 43) answers 415 to a POST whose type is not JSON when `request.body` is non-null. Whether workerd presents an empty React Native POST as `body === null` is untested, and no T1 test sends a body-less POST. Passing `body: {}` removes the doubt; otherwise put it on Task 12's list.
4. **The lockfile-only core pin has no guard.** `@better-auth/expo` declares a required peer `@better-auth/core: ^1.6.33`. Nothing pins it in a manifest (by design: "No other package"). A later `npm install` in a shared lockfile task (Task 7 adds native sign-in) could re-resolve it to 1.7.x, as the first install did. Ask Task 7's brief to rerun the brief's one-line lock check, or add it to `test:ops`.

### Nit

1. **Two copies of `@better-auth/core` 1.6.33** (and of `@better-auth/utils` 0.4.2), under `node_modules/better-auth/` and `apps/app/node_modules/`. They are the same version and harmless: the Expo client imports only the stateless `@better-auth/core/utils/json` from its copy, and its online and focus managers are `globalThis` symbols taken from `better-auth/client`. The receipt's "one line" means one version.
2. **`sessionEnded` sets `reason` after `dispatch` has notified** (`credentialProvider.ts` lines 356 to 359). A synchronous subscriber calling `endedReason()` sees the previous value. `auth_denied` sets it inside `dispatch` (line 150). React consumers re-read later, so no current caller is affected. Setting `reason` first would make the two paths consistent.
3. **Mutant R16 survives.** Putting back the WIP's `getAccessToken` (returning null when the epoch moved) fails no test. The body is the base's verbatim apart from `deps.port` and a comment, so this is informational only.
4. **Local dev URLs.** `authUrl` defaults to `v1ApiUrl` = `http://localhost:8091`, which is the PostgreSQL API (`scripts/dev-v1.mjs` PORT 8091). T1's Worker serves `/api/auth` at 8092 (`apps/edge/scripts/dev.mjs`, `AUTH_BASE_URL`). This follows the plan ("one Worker serves both" after 1B-T13), but Task 12 must set `EXPO_PUBLIC_AUTH_URL` (or move v1) and the `.env.example` comment should say so.

- **Port rules:** 5xx, 0 and throws map to `AuthUnavailable`. 429 maps to `CODE_LIMIT` or `RATE_LIMITED`. ID-token sign-in maps `ACCOUNT_EXISTS` with `methods` (R54) and has the null-native guard. Fresh sign-in has the email and subject pre-checks and signs out a session that lands in another account. Link and devices map `REAUTH_REQUIRED`, `SIGNED_OUT` and `REFUSED`. `AuthRefused` assigns its fields in the constructor body (R53). `createdOf` accepts only `=== true`. `unsupportedBetterAuthPort` behaves as the plan says.
- **Provider rules:** sign-in stores only after the server accepted it, and a sign-out still wins. `freshFlow` saves under `committing` with superseded checks before and after (the "after" check is untested, minor 1). `getAccessToken` and `refreshAfterUnauthorized` are the base's bodies. `requestCredentials` compares epochs. `ACCOUNT_UNAVAILABLE` gives `reauth_required` with `account_unavailable`. `endedReason` clears on `bootstrapped` and `signed_out`. Every new session moves the epoch (K13).
- **Session store:** `isUuid` from contracts; keeps exactly four fields, a 320-character email cap and a known method; removes `gogospend.v1.session-binding` once per store instance.
- **Client:** `createAuthClient` with `expoClient({ scheme: 'gogospend', storagePrefix: 'jotbun', storage })`, `emailOTPClient`, `jwtClient` and `jotbunAccountClient()` (`satisfies BetterAuthClientPlugin`). The Expo client clears the stored cookie before it sends `/sign-out`, so an offline sign-out still forgets the cookie on the phone.
- **Screens and layout:** `signInThroughSession` sends Apple and Google with `signUp: true` and keeps email at `not_configured` (Task 9). `SignInAttempt = SignInOutcome | 'reauth_required'`, and `afterSignInAttempt`'s default keeps new outcomes on screen as a calm failure. `_layout.tsx` differs from the head by four lines: the import and one module-level `installAppAuth()` after the imports, which the RootLayout render test checks (M13 killed).
