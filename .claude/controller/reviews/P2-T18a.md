### Minor

**m1. Race B's render case holds the host's hand-off of the read's revision only in a shape reconcile never leaves standing, so passing the diary's revision instead survives (P4).**
- **Where:** `SavedMoment.render.test.tsx:671-676` (the diary at 9, the command acknowledged at 9, the read at 10) and `SavedToastHost.tsx:155` (`readRevision: page.as_of_revision`).
- **Why the shape matters:**
  - Reconcile resolves an acknowledged command once the diary has applied its revision, or makes it `uncertain` again (`reconcile.ts:69-71`).
  - So race B's command lingers only while the diary is behind its acknowledgement: applied < acked ≤ the read's revision. That is the shape Sonnet's original probe had (`scratch/p2-t17-second/probes/Probe.render.test.tsx:244-252`, with the diary at its default `'0'`).
  - The committed case moved the diary to 9 so that it kills H3 (revisions compared as text). With applied equal to acked, the read's revision and the diary's give the same answer.
- **Mutant R3:** `readRevision: now.phase === 'ready' ? now.appliedRevision : page.as_of_revision`.
  - It survives all 20 cases (`own-mutants.out`).
  - In the lingering shape it shows `บันทึกแล้ว · วันนี้ ฿132` where ฿82 is right: race B's overcount comes back (probe B1, `own-mutants-vs-probes.out`).
  - H6 (no revision handed on) is killed today, but handing on the wrong revision is not.
- **Fix (test only):** put the diary at `'8'` in that case and update its comment:
  ```ts
  raced([EARLIER], { outbox: [acknowledged], appliedRevision: '8' }, { appliedRevision: '8' })
  ```
  - This is probe B1. It passes on the commit and kills R3.
  - It still kills H3 (as text, "8" sorts after "10") and H6 (`planner-vs-probes.out`).

**m2. The closed diary is held only for a diary gone `unavailable`. One that locks or reopens mid-read is unpinned (P3).**
- **Where:** `SavedMoment.render.test.tsx:678-681` (`during: { phase: 'unavailable', outbox: [] }`) and `SavedToastHost.tsx:147`.
- **The ways an open diary closes while a toast is up:**
  - a sync that comes back signed out locks it and keeps its outbox and revision (`spendDiary.ts:176`, `{ ...view, phase: 'locked', lockReason: 'signed_out', ... }`);
  - a session switch reopens it (`:198`, `'opening'`);
  - a sign-out empties it (`:195`, `:340`, EMPTY, `'unavailable'`).

  The case covers only the last.
- **Mutant R1:** `const moved = now.phase === 'unavailable' ? openAtStart.current : BigInt(now.appliedRevision) > BigInt(page.as_of_revision);`
  - It survives all 20 cases (`own-mutants.out`).
  - With it, a diary that locked (probe C1) or reopened (probe C2) mid-read shows `บันทึกแล้ว · วันนี้ ฿82`, leaving out the save's own ฿50. That is the very error P3's closed-diary rule exists to prevent.
- **Fix (test only):** run the closed-diary case over all three closes:
  - `{ phase: 'locked', lockReason: 'signed_out', accountId: null }`, which keeps the outbox and revision as `onOutcome` does;
  - `{ phase: 'opening', outbox: [], appliedRevision: '0', accountId: null }`;
  - today's `{ phase: 'unavailable', outbox: [] }`.

  C1 and C2 pass on the commit, kill R1, and still kill H4 (`planner-vs-probes.out`).

### Nit

**n1. The corrected comment over the card's place misstates the mechanism the confirming review's m1 was about.**
- **Where:** `NewWalletFlow.tsx:388-390`, which says "a test id alone is flattened away on Fabric, a nativeID is not".
- **What RN 0.88 does:**
  - A view with a `testID` is mounted, not flattened away: it forms a view (`ViewShadowNode.cpp:64-66`; `isConcreteView` in `sliceChildShadowNodeViewPairs.cpp:114-118`).
  - What Fabric flattens is its children, which it hoists into the nearest stacking context (`areChildrenFlattened`, `:119-124`).
  - A `nativeID` forms a stacking context (`ViewShadowNode.cpp:47`).
- **The receipt already has it right:** `P2-T21-fix.md:35`, corrected by this task.
- **Suggested wording:** "a test id alone makes a view whose children Fabric hoists out of it; a nativeID forms a stacking context, so the card stays inside".
- The code itself is right.

## What I checked, by the controller's focus

**Today's total, race A and the closed diary (P3).**
- **The rule:** `SavedToastHost.tsx:143-157`.
  - One read.
  - The outbox comes from `latest.current` when the read lands.
  - `openAtStart` is the phase at the toast's first render.

- **A view is one moment.**
  - `refresh` reads the state and the outbox through one serial queue, back to back (`spendDiary.ts:154-157`, `serialDatabase.ts:16-23`). Each `read()` enqueues before its first await, so no write can land between them.

- **A figure, rightly:**

  - the web (probe W1; H5's kill).
- **Unknown though exact:** another device's change applied while the read is out, and a refresh mid-flush that has applied past the read while the command is still in the outbox. Both are rare and safe.
- **A diary never open during the toast** (opening or locked throughout, with an online save; `entrySave.ts:185`, `:197`) shows a figure without that diary's drafts (probes N1, N2).
