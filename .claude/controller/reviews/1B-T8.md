**m-1. A request that reuses the key of a snapshot `pruneSnapshots` deleted brings back a pending row that no Workflow builds. Every later request shares that row until it fails a day later.**

- **Where:**
  - `src/vault/files/snapshots.ts:345` deletes a snapshot read below the watermark. `:81` answers a request only from a row with its id. `:89-91` reuses the open pending row, or inserts one.
  - `src/vault/files/work.ts:195`: the snapshot starter starts the Workflow through `createOnce` (`work.ts:45`, 1B-T6's helper). When `create` finds an instance with that id, the helper counts it as created.
- **Probe D** (`review-probes.test.ts`, output in `probes-run1.log`):
  1. A snapshot is requested and built by SnapshotWorkflow. A purge makes it stale, and `pruneSnapshots` deletes its row.
  2. The same key is sent again. The answer is `202` with the same id and `pending`.
  3. The hand-off's `create` fails with the Workflow binding's `instance.already_exists`. `createOnce` then finds the retained instance with `get`, treats it as started, and `markStarted` stamps the row.
  4. Three seconds later the row is still `pending`, and the instance is still the first run's `complete` one.
  5. A request with a **fresh** key answers the same stuck id. Nothing builds until `pruneSnapshots` fails the row at `SNAPSHOT_PENDING_MS`, a day later.
- **Why it matters:**
  - P11 says a resent request answers its own snapshot whatever its state.
  - The API keeps the job row, so a resent key reads `expired`: `snapshot.repository.ts:64-65`, where `succeeded` with no manifest reads `expired`.
  - The trigger needs the same POST resent after a purge and a prune. The app takes a fresh key for each resync (`apps/app/src/sync/reconcile.ts:25`), so only a transport resend of a lost response can do this. That is unlikely, but the result is a day with no resync for that account.
  - It cannot happen at this commit: nothing calls `pruneSnapshots` until 1B-T11.
- **Fix (1B-T11, before `pruneSnapshots` goes on the alarm):** one of these.
  - Keep a stale snapshot's row, so a resent key reads `expired` as in the API. Release its chunk keys at once, and drop the row with the week-past-expiry rule. `snapshotsDueAt` must then stop answering "now" for a stale row whose keys are already released.
  - Or make the starter notice that the instance named by a pending row's id has already finished, and give that row a run.
  - Probe D is ready to turn into an assertion.

**m-2. The ten-times proof's cursor spy can be bypassed. Reading the entity rows with a spread passes all 35 cases, the memory proof included.**

- **Where:** `test/workers/snapshots.test.ts:136-157`. `watchedSql` refuses `toArray`, `one` and `raw`, but it gives a reader the whole iterator. The loop is at `src/vault/files/snapshots.ts:196`.
- **Mutant X1** changes that loop to `for (const row of [...c.sql.exec<HeadRow>(ENTITY_READ)])`. It SURVIVED: 35 passed (`mutants-run.log`).
  - That mutant holds every row object at once, each with its snapshot JSON string. That is the materialisation B14 exists to exclude ("Large reads iterate the cursor and never call `toArray()`"), and `peakHeldBytes` cannot see it.
  - The plan's own wording ("the test fails on `toArray`") is met. This finding is about what the proof is for.
- **Fix:** yield each row as a revocable proxy, revoked when the next row is pulled. See `streamingOnlySql` in `review-fixes.test.ts`.
  - It passes on `f416f24`, and it kills X1 (`fixes-run.log`: X1F).
  - Use it in `watchedSql`, which serves the ten-times case and `reads every row before the first R2 call`.

**m-3. No case pins the read's own check that the snapshot is still pending.**

- **Where:** `src/vault/files/snapshots.ts:226`, `row.status !== 'pending'` in `prepareSnapshot`. The plan's Step 4 says: "A row that is not `pending`, or an inactive vault, answers `skipped`."
- **Mutant X6** drops that condition. It SURVIVED: 35 passed.

  - Suppose a step is retried after the vault already recorded `ready`, because the RPC answer was lost or the step timed out. The retry would read the whole vault, reserve keys and PUT every chunk again (up to 64 MiB). Only then would it skip, leaving those reservations for the alarm.
- **Fix:** add `fix X6: a build of a snapshot that is no longer pending reads nothing and stores nothing` from `review-fixes.test.ts`. It passes on `f416f24` and kills X6 (X6F).

### 5. P7 and P8, the memory proof: holds as the plan defines it (m-2 aside)

- **What `peakHeldBytes` counts** (`snapshots.ts:303-311`): every chunk's encoded parts, from the read until that chunk's upload, plus the one copy `putConcatenated` joins.
  - The peak is always at the first chunk. So the peak minus the stored bytes is the first chunk's size, at most `chunkBytes` plus the header plus 1.
  - The case's bound is `chunkBytes + longestLine` (593). It holds whenever the header, about 120 bytes, is shorter than the longest line. It does not depend on time or on load.
  - CI's run gives a peak of 20,644,116 against 19,595,807 bytes stored, so the first chunk was 1,048,309 bytes, against a bound of 20,644,976.
- **What it does not count:**
  - The per-row transients: the row object, its parsed and `jsonbOrder`ed snapshot, the change and its JSON string. These live one row at a time.
  - The per-line `Uint8Array` objects (about 33,000 at ten times) and the `parts` arrays. Only their byte lengths are counted.
  - What the runtime copies inside `put` and the digest. That is the named risk.

  So the count bounds the payload the code keeps alive, not the isolate's heap.
- **Against the 128 MB limit:**
  - At ten times the counted peaks are 20.6 MB for the build and 29.7 MB for the export. Those leave room under 128 MB for the uncounted overhead.
  - The 64 MiB cap (`MAX_SNAPSHOT_BYTES`, the API's) is about 3.3 times the ten-times snapshot of 19.6 MB, and nothing proves it fits. A snapshot near the cap would hold about 65 MiB counted, plus the uncounted, in one isolate. See the note for the hosted check below.
- **Nothing is time-based.**
  - Every assertion compares bytes and counts, and the wall times are only logged.
  - The other relative-time assertions have margins of minutes.
  - The counts agree across the implementer's two runs and CI: the same records, chunks, stored bytes and CSV, with the peak within 32 bytes.
- **Mutants:** my reruns of M1, M2 and S32 were KILLED by the ten-times case (M1 also by `reads every row ...`). My X12 (a line's comma not counted) was KILLED by it too.
