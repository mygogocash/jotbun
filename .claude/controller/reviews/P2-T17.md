### Minor

**m1. Today's money out can leave out the very save the toast reports (P6; the controller's race question).**
- **The answer to the race question:** no race counts a save twice; one leaves it out.
  - **Counted once** (probes R2 to R6, all pass): the sync takes the draft mid-read (`sending`); Jotbun acknowledges it between the read and the outbox read, unlisted; committed at or before the read's revision and still `acknowledged` in the outbox; acknowledged and applied at the read's revision (listed, gone from the outbox); an `uncertain` resend whose record is listed. `todayOutMinor` skips every listed id, and with `next_cursor` null the page lists every expense its summary sums. The outbox holds only `transaction.create` commands, one per record (`storage/types.ts:61-73`).
  - **Left out:** the draft is sent, acknowledged **and reconciled** after the vault read the page, but before the toast handles it. The page does not list the record (committed after its revision) and the outbox no longer holds the command, so the save's amount is in neither.
- **PROBE R1** (`probes-final.log`):
  - The setup: the page is read at revision 10 and lists only the ฿82. While it is on its way, the diary applies revision 11 and the draft leaves the outbox.
  - The toast says `บันทึกแล้ว · วันนี้ ฿82`. Right is ฿132, or `บันทึกแล้ว` while that cannot be known.
  - The figure then never moves, by design.
- **Why the path is real:**
  - **The sync starts first.** A device save starts the sync before the toast reads: `saveDraft` refreshes the view, then calls `scheduler.written()` (`spendDiary.ts:279-281`), which flushes at once (`scheduler.ts:92`). Only then does `useEntrySave` call `onSaved` (`entrySave.ts:188-189`).
  - **The command can leave before the read lands.**
    - The flush pulls, sends, then reconciles (`syncEngine.ts:52-58`).
    - Reconcile resolves an acknowledged command once the confirmed state holds its record (`reconcile.ts:62-75`).
    - The view's outbox refreshes when the flush ends (`spendDiary.ts:173-181`).
  - **Where P6 stops.** P6's argument (an unlisted command was not committed at the read's revision, so counting it is exact) holds while the command is still in the outbox. It does not cover the command leaving before the read is handled.
- **How likely:**
  - **Narrow.** The read usually lands after one round trip, the reconcile after about three, so it takes a slow read: a full page on a slow link, or a stalled response.
  - **On the main path when it happens:** a device save with the diary open and synced.
  - **Not reachable yet.** The host is mounted nowhere but the catalogue, so no person meets this before P2-T18.
  - **A rarer sibling:** a device save whose diary is no longer `ready` when the read lands counts no draft (`outbox: []`, `SavedToastHost.tsx:146`). The same guard can treat it as unknown.
- **Fix (one guard in this task's file; proved in scratch, `probes-fix.log`):**
  - **The guard.** When the read lands, leave the total unknown if the open diary has applied past the page's revision:
    ```ts
    const now = latest.current;
    const passed = now.phase === 'ready' && BigInt(now.appliedRevision) > BigInt(page.as_of_revision);
    if (page.next_cursor === null && !passed) setTotal(todayOutMinor({ ... }));
    ```
  - **Proved.** With it, R1 shows `บันทึกแล้ว`, and the task's 16 cases and my other 8 pass (24 of 24).
  - **Exact as a detector.**
    - A command committed after the page's revision can only have left the outbox once the diary applied that revision (`reconcile.ts:62-75`).
    - It is P4's stance for a page with a `next_cursor`: unknown rather than inexact.
    - A needless plain line needs another device's change applied while the read is out: rare and safe.
  - **Pin it** with R1's shape and a mutant that drops the guard.
  - **When:** before P2-T18 mounts the host, in a fix round or as P2-T18's first step.

### Nit

**n1. Where the chip starts is not pinned, and the flight's cases run in a 0 by 0 window.**
- **Unpinned.** My mutant M4 starts the chip from the top of the window (`dy = -to.y`), and all 16 cases pass.
- **Observable.** Probe F1 reads the first frame's style: `translateX(-201px) translateY(-457px) scale(1)`, opacity 1. One assertion would hold the plan's "from the bottom centre".
- **A degenerate window.**
  - `Dimensions.get('window')` is 0 by 0 in these cases (F1).
  - So the landing case pins `left: 217px` and `width: -32px`: the formulas, not a box a phone draws.
  - Giving the window a phone's size in the flight's cases would pin both.

**n2. "Today" for the read is not pinned at a day edge.**
- **Survives now.** M5 reads today in UTC (`new Date().toISOString().slice(0, 10)`) and survives.
  - The cases compute `TODAY` with `todayInBangkok` at the same moment, and at 08:31 Bangkok both dates agree.
  - It would fail only between 00:00 and 07:00 Bangkok.
- **Pin it.** A case with `vi.setSystemTime` at 00:30 Bangkok (17:30 UTC the day before) that checks the read's `from` and `through` would hold the Global Constraints' "Time" rule (Review Focus 5's day edge).

**n3. The chip draws income in ink.**
- **The rule.** Global Constraints (§2): "Income is violet with a plus sign". The chip draws `+฿35,000` with the plus, but in `colors.ink` (`SaveFlight.tsx:132`).
- **The boards.** bw-saved and dk-saved show only a spending chip (`−฿50`, in the default ink), so they do not settle income.
- **Option.** `WalletAmount` has size 13, takes the sign, draws income violet by default and masks itself in private mode, so it would also replace the chip's own mask.
- **Where:** E2-B or P2-T37.
