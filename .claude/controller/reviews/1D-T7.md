### Major

**M1. On a signed-out launch, the early events (P13) are still lost. The controller drops what the install hands it at the first `setAccount(null)`. Onboarding's first step never reaches PostHog, which is exactly what 1D-T6's review m3 point 2 asked this task to fix.**

**The probe:** `probes/zzReviewEarly.render.test.tsx`.

- It uses the real `AnalyticsUpkeep` and the real `installAppAnalytics`:
  - iOS, with a project key;
  - PostHog's client module mocked as a recorder;
  - a server that answers yes.
- Onboarding's `coffee` is tracked while PostHog's module loads. The session has no binding, then the person signs in.
- Expected `['coffee', 'private', 'first_coffee']`; received `['private', 'first_coffee']` (an `AssertionError`).
- The control case in the same file has a session already restored at launch, the scenario of the kit's test. There, `coffee` is sent.

**The path:**

1. `app/index.tsx:11` renders `OnboardingScreen` at `/`; the `account` area is approved. So step `coffee` is tracked in the launch's first commit (`OnboardingScreen.tsx:113-115`).
2. On native with a key, `install()` awaits `import('./posthogClient')` (`appAnalytics.ts:34`). So the event goes to the bus's early list (`bus.ts:44-47`).
3. The install hands the event over (`appAnalytics.ts:61`). The new controller is `loading`, so it holds the event.
4. `AnalyticsUpkeep` sets the account as soon as the instance resolves (`AnalyticsUpkeep.tsx:84`). With no binding, that call is `setAccount(null)` (`:37-41`).
5. In the controller, `undefined` to `null` is not "no account to an account". So `keepHeld` is false and `held.length = 0` runs (`controller.ts:208`, `:215`).
6. Every later step is tracked while signed out, held, and kept across the sign-in. That is why only the first step is lost.

**Why it is a defect:**

- It breaks the plan's own Task 7 row: `onboarding_step_viewed` ... "held until the answer (1D-T1)" (line 733).
- It breaks L4 (line 29). Held events are "dropped on no, an account switch or restart", and the launch learning "signed out" is none of these.
- Task 1's `setAccount` rule says what held events are for: "(they come from the onboarding and the sign-in that led here)" (line 259).
- It contradicts the brief's P13 ("its new controller, which holds them until the answer like any other (L4)"), the comment at `bus.ts:26-31` and the receipt's "Carried" line.
- The bus's early list alone cannot close m3 point 2. Without the list, the same drop still happens: on the web, or on a phone whose install resolves first, the event is held in `loading`, then dropped at the same `setAccount(null)`.

**Why the tests missed it:**

- `appAnalytics.render.test.tsx:62` calls `analytics.setAccount(ACCOUNT)` straight after the install, so it never passes through `AnalyticsUpkeep`'s signed-out start.
- The Onboarding render case runs under `recordAnalytics()`, already signed in with a yes.

**Impact:** this is not a privacy problem. Nothing is sent early, and held events are still sent only on a yes. But once Q5's key is set, the first step of the onboarding funnel is missing from every first launch.

**The fix,** proven in scratch:

- Change `controller.ts:208` to `const keepHeld = accountId === undefined || (accountId === null && id !== null);`.
  - The launch's first answer keeps what is held, whether it says signed out or names an account.
  - A sign-out (an account to null) and an account switch still drop it, so P14 and L4 hold.
  - `reset()` and `stopSessionRecording()` still run at every change.
- With that line:
  - `zzReviewEarly` passes, both cases.
  - `zzReviewHeld` PROBE 1 passes. PROBE 2 (a real sign-out still drops) passes both before and after the fix.
  - Every existing analytics case still passes: `controller`, `bus`, `events` and `neverSent` (46 Node cases), and `appAnalytics`, `AnalyticsUpkeep` and the probe (10 render cases).
- Add the probe as a case through `AnalyticsUpkeep`'s signed-out start, in `AnalyticsUpkeep.render.test.tsx` or `appAnalytics.render.test.tsx`. Add `zzReviewHeld`'s two cases to `controller.test.ts`.

**Reading of the plan:** Task 1's text lists "or to `null`" among the changes that drop held events. Read with its parenthetical and with L4, I take that to mean a sign-out (an account to null), not the launch's first answer. If the controller reads it the other way, this needs a ruling, and the receipt must say that m3 point 2 stays open.

## The focus points

**1. What each event carries.**

- **The allow-list is the boundary on every path.** The bus cleans every event before anything else (`bus.ts:40`), the early list included: an event is cleaned before it is kept.
  - Every rule is an enum, a bool, a bounded count, the `code` pattern or the `screen` pattern.
  - The common properties follow the same rules.
  - No rule takes free text.
- **Record events** carry only:
  - `kind`, an enum;
  - `category_key`, an enum of the built-in keys, the nine pack keys and `custom`.
- **A category name the person typed cannot leave.** `categoryKeyOf` gives `builtin_key ?? packKeyOf(label) ?? 'custom'` (`thaiPack.ts:82-85`), and the record screen's list is every category (`seedBuiltins` returns `listCategories`).
  - So a typed category name can only leave as a pack key (Q18) or as `custom`. Anything else fails the enum.
  - A pack key does say that a custom label matched one of the pack's names; Q18 accepts that.
- **Wallets:** no record event names a wallet. Home's `wallet_added` is `{}`; the Wallets screen's look properties are enums.
- **Sync and permission events:**
  - `sync_failed`'s `reason_code` is the run's `V1Error.code` under the `code` rule: transport, HTTP and server class names, `LOCAL_ERROR` and `CURSOR_MOVED`. It is never text.
  - `permission_denied` carries one of two fixed codes. The prompt's context, the reprompt flag and the Open Settings result no longer leave the phone.
- **Screens** are sent as patterns only. `onDisplay` holds a pattern or null.
- **The render cases check it:** each one checks that its fixture's amount, note and names are absent from the sent JSON. I read Quick add, the record screen, History, Recently deleted, Home, Wallets and Budget.
- **So no property can hold** an amount, a note, a merchant, a wallet name, a category name or typed text.

**2. When an event goes out.**

- **Consent: nothing goes before a yes.**
  - The early list only stores.
  - The install tracks the early events into the controller. The controller holds them while `loading`, `signed_out` or `unanswered`, drops them on a no, and sends them only in `enterYes`.
  - The test sink stays tests-only.
- **The early list:**
  - It is cleaned, and capped at 50 with the oldest dropped first (B3 and B4 killed in the implementer's run, B2 in mine).
  - It is handed over once, by `splice` (B5 killed).
  - Only the app's install takes it, and only when that install's controller is the one installed (`appAnalytics.ts:56-61`).
  - But see M1: on a signed-out start, the controller then drops it.
- **The screen on display:**
  - `onDisplay` is kept whatever the status. It is sent once on entering yes, after the held events (`controller.ts:133`).
  - A refresh while yes sends nothing more (C1 and C2 killed by me; C3 and C4 by the implementer).
  - `AnalyticsUpkeep`'s effects set the screen before the account (screen, then follow), so a launch's yes sends it.
- **The epoch move** (followups line 111, P14), checked in the code:
  - A fresh sign-in goes A, then null, then A (`AnalyticsUpkeep.tsx:44-47`).
  - Events held while the answer is unknown drop at the null, as L4's account change says.
  - With a yes, nothing is held, so nothing is lost.
  - Entering yes again sends the screen on display once more.
  - The diary reopens with a new `createDeviceSync`, so a failure that persists is counted once more per sign-in.
  - All of this is as P14 says. The two-phone check is 1D-T15's. M1's fix keeps it all: `zzReviewHeld` PROBE 2 passes.

**3. The bus guard (P12).**

- **What it covers:**
  - `trackClientEvent` catches anything `analytics.track` throws (`bus.ts:49-54`); B1 is killed.
  - The arguments built at the call sites cannot throw. `recordEventOf` and `categoryKeyOf` read lists that are always arrays: `diaryView.categories` is `[]` in the empty view (`spendDiary.ts:98`). The emitters are pure.
  - The sync report calls the emitters before handing the outcome on, so a failing client can no longer stop the scheduler's timer (`scheduler.ts:69-70`).
- **It hides nothing the person should see:**
  - It wraps only the analytics call, after the rule's own work is done.
  - The controller's `track` does no I/O.
  - A failing client is silent, with no `failureName` log. The plan allows that.
- **What it does not cover, which is fine:** `enterYes`, which now also calls `client.screen`, runs inside `setAccount`, `refresh` and `answer`, and their callers catch.

**4. Once each.**

- **One call per rule:** every emitter has exactly one call in each rule:
  - Quick add's two starts and `finish`;
  - the record screen's edit, "Use yours", delete, and restore or undo;
  - History's delete and undo, and `useRecentlyDeleted`'s restore;
  - Home's two wallet paths and Budget's two paths;
  - Onboarding's effect, the sync reporter and the permission denial.
  - `walletCommands.ts` (the Wallets screen) and Home's form are separate rules.
- **After the acknowledgement or the device commit:** each event goes only then.
  - The render cases pin that an unconfirmed attempt sends nothing, then the resend under the same key sends one. They cover Quick add (through P2-T5), the record screen's edit, delete and undo, History's delete and undo, Recently deleted, Home and Budget.
  - An answer that shows the action already happened sends one: Quick add's own create matched, Home's own wallet met again, a budget with the same figures. A conflict sends none.
- **A lost restore answer:** a restore whose answer was lost, and that a later read no longer lists, sends nothing (`deletedData.ts:168-174`). The phone cannot tell "restored" from "can no longer be restored", so that is right.
- **Undo versus Restore:** the record screen decides by `deleted?.id === target.id` (`recordActions.ts:465`). The Restore button is drawn only when `deleted` is null, so the two cannot mix (RA6 killed). For the not-ready gate, see n1.
- **Sync:** once per entry into the failure set, and once per entry into `resync_pending`, per open diary. See n2 and P14.
- **A save kept on the device** is not counted again when the outbox later syncs it.

**5. `SyncOutcome.reason` (P10) and the sync engine's other callers.**

- **Optional is right:**
  - The engine sets `reason` on every outcome: `summarize` defaults it to null, and `runOnce` passes `run.failed?.code` (`syncEngine.ts:172`, `:270`). Gate refusals give null (E2 killed).
  - The scheduler's fallback for a flush that threw leaves it out (`scheduler.ts:66`). `syncEvents` then sends `LOCAL_ERROR`, as the engine names any unexpected failure.
- **The other callers:**
  - `createDeviceSync` is the only production maker of an engine, and the scheduler is the only path to `onOutcome`.
  - The only other reader of outcomes is `spendDiary`'s view, which reads the status and the counts, never `reason`.
  - The sync test harness (`src/sync/testing/harness.ts:82`) flushes directly, in tests only.
