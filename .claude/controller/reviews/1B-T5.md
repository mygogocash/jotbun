## Findings

### Blocker

None.

### Major

**M-1. A rejected receipt photo loses its issue code: the consumer turns every image-format rejection into `parse_failed`.**
`src/background/parse-consumer.ts:88`, in `checkedParse`:
```ts
if (expectsImage !== (image !== null)) return { record: REJECTED, image: null }
```
This runs on every `parsed` reply. For a JPEG, PNG or WebP upload that the parser rejects, the parse server sends `{ kind: 'parsed', record: <rejected with its code>, image: null }` (`parse-server.ts:141-149` through `previewFromOutcome`). `expectsImage` is true and `image` is null, so the consumer replaces the record with `REJECTED` (`issues: ['parse_failed']`).
The API checks for the image only on a successful result (`parse-outcome.ts:142-146`: `if (!result.ok) return { record: rejected(<code>) }` comes before the `expectsImage` check), so it keeps the code. The plan's Step 5.4 also scopes the re-check to "A `parsed` reply **with an image**". The app has its own words for each lost code (`apps/app/src/spend/v1/redesign/import/importModel.ts:578-582`: "The photo is too large.", "The photo isn't what its name says.", "The photo couldn't be read.", "The file took too long to read."). `image_too_large` is what the image child answers for any photo over 20 MP (`parsers/image.ts:50`), so this is an everyday path. Table formats are not affected.
**Probe** (`scratch/1b-t5-review/review-1b-t5-probes.test.ts`, "parity: a rejected receipt photo keeps its own issue code"): a JPEG upload, with the fake parser answering `serverReply('jpeg', outcome)`. The probe first checks that the reply carries the API's code, then reads the stored preview. It fails 4 of 4 (`probes-2.log`):
```
- "issues": "[\"image_too_large\"]"         + "issues": "[\"parse_failed\"]"
- "issues": "[\"image_format_mismatch\"]"   + "issues": "[\"parse_failed\"]"
  (also parse_timeout and parse_resource_limit)
```
No test covers it: the child-outcome `it.each` in `imports-parse.test.ts` uploads a CSV.
**Fix:** when the reply has no image and its record is `rejected`, keep the record as it is. Keep `REJECTED` for a `ready` image-format record with no image, and for any image on a table format. For example:
```ts
if (image === null) return expectsImage && reply.record.preview.status !== 'rejected' ? { record: REJECTED, image: null } : { record: reply.record, image: null }
if (!expectsImage || image.format !== format) return { record: REJECTED, image: null }
```
Then add an `it.each` over the image codes for a JPEG upload, asserting the stored `issues` equal `serverReply`'s (the probe can be copied), and a mutant that restores the current line and is killed by it.

### Minor

**m-1. P1's security guards on `begin` and `finish` are pinned only by the flag table, not by behaviour.** The code is right. Through `UserVault#call` with a revoked session, `begin` answers 401 and `finish` answers 401, while `reservePart`, `abort`, `discarded` and `bytesRetry` run. With a changed terms version, `begin` and `finish` answer 403 `POLICY_ACCEPTANCE_REQUIRED` and `reservePart` runs. In a `deleting` vault, `reservePart` answers `{ key: null }`, `begin` and `finish` answer 403, `abort` cleans up and `parseSource` skips. With another account's claims, every step is refused (owner mismatch). An erased vault answers 403 to every step. Over HTTP, an upload after sign-out is 401 and records nothing. All of these pass (`probes-1.log`, the 7 P1 cases).
But no test fails when any of these guards goes:
- R2 (the import steps skip `assertPolicyAccepted`, so `begin` and `finish` lose the policy gate) survives 81 of 81. For a Worker route, the vault's `call()` is the only place the `current_policy` acceptance is checked.
- R38 (`begin` alone skips `assertSession`) survives.
- R3 (`reserveUploadPart` ignores the account status, P1's "checks itself that the account is active") survives.
Only M12 and R36 (every step skips both checks) are killed, by the session-ended case.
**Recommendation:** add the probe's first three P1 cases and the HTTP sign-out case as tests (they are written and green).

**m-2. The `ocr` gate on image uploads (P11, plan Step 4) has no test.** R17 (drop `w.gates.assertOpen('ocr')` in `src/v1/files/uploads.ts:79`) survives. A probe shows the route is right today: an image upload while `ocr` is paused answers 503 and records nothing. The API pins it in `operational-safety.spec.ts:331`. Add the probe case.

**m-4. A finish that fails for its parts, not its session, records `session_ended`; the API records `intake_error`.** Any error in a vault call comes back as a problem reply, and `vaultIntakeRepository.step` (`uploads.ts:35`) throws it as a `ProblemException`. `UploadIntake` reads every `ProblemException` from `finish` as "session, account or policy changed" (`upload-intake.ts:265`). The API's `RAISE EXCEPTION`s in `gogospend_finish_import_upload` are plain errors there, so they become `intake_error`.
**Probe:** a 2.5 MiB upload where part 0's reservation is made due just before finish. The answer is 500 (as in the API), and the row is `{ status: 'failed', outcome_code: 'session_ended' }`. The client's answer and a retry's 409 are the same; only the stored code differs.
**Fix:** throw a plain `Error` for a 5xx reply in `step`. The same holds for `reservePart`'s errors, which already become `intake_error`.

### Nits

1. **`recordPreview` binds `amount_minor` through `CAST(? AS INTEGER)`** (`parse.ts:145`). This cuts a non-integer string: probe `'100.9'` is stored as `100` and the record succeeds. The API's `jsonb_to_recordset(... amount_minor bigint)` refuses it. The container's runner validates amounts (`parser-runner.ts:482`), so this is unreachable today, but a check such as `/^[1-9]\d{0,10}$/` would keep "amounts stay exact" true by construction.
2. **`discardUploadParts` tombstones any key under the attempt's prefix, whatever its status** (`intake.ts:375`, through `tombstoneObjects`). The API's discard touches only `deleting` rows. Probe: handed the published part of an accepted upload, it tombstones it, and the alarm would delete the raw file a day later. Only the Worker's own code calls it, with `abort`'s keys, so it is unreachable today. R41 (no prefix filter) also survives.
3. **P17's note is slightly incomplete.** If two deliveries ever overlapped at the third attempt, the duplicate's `parseSource` fails the job `import_unavailable` while the first parse is still running, so a healthy parse is lost (probe). `max_concurrency: 1` rules out overlap, so only the wording in the brief and receipt needs a qualifier.
4. **`vaultById` is called outside the consumer's `try`** (`parse-consumer.ts:121`). A 64-hex string that is not a valid id for the namespace would throw past the handler and retry the batch up to `max_retries`, not ack it as `parse_message_malformed`. Messages come only from the vault, so this is unreachable.
5. **Boundary and defensive mutants that survive:**
   - R39: `finish` accepts at the receive-deadline instant.
   - R42: `recordPreview` records at the raw-expiry instant.
   - R4: `abort` ignores the intake token.
   - R8: `recordPreview` drops the image-prefix guard. A probe shows the guard works.
   - R10: `reserveImageKey` ignores the parse state.
6. **workerd prints `Uncaught (in promise)` with the stack and the SQLite message** when `recordPreview` throws for a CHECK (P14). This is the known 1B-T4 nit. The message is the constraint text (`amount_minor BETWEEN 1 AND 99999999999`), with no values.

## Focus items

1. **P1, the four `anySession` steps.**
   - They match the API: only `begin` and `finish` take the account lock and call `assertActiveSession` and `assertPolicyAccepted` (`import.repository.ts:120-178`, `underLock`). `reservePart`, `abort`, `discarded` and `bytesRetry` run in plain owner transactions.
   - `call()`'s inline change is exactly the brief's: one new line computing `anySession`, plus `if (!anySession) assertSession(c)` and `&& !anySession` on the policy line.
   - `ensureAccount` and the erased check still run for every step.
   - Step ids have no HTTP route; the coverage test checks this. `begin` is always the first call of the request, so the request's charge and session check land on it.
   - Probes: see m-1. No step lets an ended session, another account, a deleting account or an erased vault publish, finish, read or enqueue. The test gap is m-1.
2. **Deadlines and races.**
   - Publish after PUT: parts are published in `imports.finish`, a vault call after the intake's PUTs and `head` checks. The image is published in `recordPreview`, a vault call after `putStream`. Both read the vault clock when they start.
   - `delete_after > now` is in `finishUpload`'s set-based publish (M7 killed). `recordPreview` also checks `created_at + RESERVATION_GRACE_MS > now` (M8 killed).
   - A part due early (abort, stale fail, re-begin) belongs to an upload that is no longer `receiving` under that token, so `finish` refuses before the alarm can race it.
   - Starter: a running parse is never re-sent before `enqueued_at + 1 h` (probe at +0, +15, +59 min and +60 min - 1 ms; M16 and M4 killed). `markStarted` stamps the run's start time, which may be a few seconds older than `parseSource`'s stamp. That is harmless next to a 15-minute consumer limit.
   - Duplicate delivery: M27 killed. Overlapping starts: covered. Overlapping deliveries: nit 3.
   - P5: see m-3.
   - P14: probe, three deliveries of a record the tables refuse are each retried, the fourth fails the job `import_unavailable`, and nothing is written.
3. **Exactness and privacy.**
   - Every size and byte sum leaves SQLite as `CAST(... AS TEXT)` (`intake.ts:61,146,186`, `parse.ts:41,80`). Preview totals are summed in SQL and never read into JS here.
   - Every new log line is `logFailure` with the failure's name only: `parse_message_malformed`, `parse_consumer_failed`, `parse_retry_unrecorded`, `work_start_failed`, plus `vault_call_failed` from `toProblemReply`. `StatementParser` and the upload route log nothing. Thrown messages carry no data.
   - File names are cleared on refusal and abort, on a stale fail, on expiry, and 8 days after acceptance (inclusive, P7). The tests pin M20, M21 and M22.
   - Nit 1 is the only exactness gap.
4. **Parity.** I compared these ports with the API's spec, and each asserts what the API's does: the oversize stream; declared length; accepts a CSV; the refusal `it.each`; Thai names and replay; disabled by default; the 5-in-15, 50 MiB and 10-a-day quotas; another account's 404; the 24-hour expiry; not due yet; the P1 sweep; a client gone mid-stream; session ended; an API that died; 2 at once; the bytes left today; refusals that do not stick (both); 10 under concurrency; registered before PUT; a deadline passed mid-stream; and finish's part checks. Of the preview ports, I compared the lease lost after PUT, network permission, the retryable `it.each`, the memory budget and the gate reopening. Several vault assertions are stronger (three deliveries to `failed` where the API checks one run).
   The six not-applicable cases are honest. The vault has no roles or RLS, Node HTTP timeout, lifecycle generation or cross-account alert. Its analogue of the deleting-account case is covered by background methods skipping a non-active vault, and a probe shows it.
   The one parity break is M-1, which no ported case reaches (the API's integration spec does not test an image rejection either).
5. **Shared files.**
   - Every edit is additive in its named place. The only removed lines are the two deferred routes, the old `WorkerRouteId`, the empty `VAULT_STEP_ROUTES` and its comment, `stepRouteOf`'s return type, and the two `call()` lines the brief names.
