### Minor

**m1. Before any yes, the native SDK runs and can send things that `before_send` never sees. R93 closes one of them. With the crash switch on (Q4's default), two remain. This is for the owner and counsel, before Q5's key.**

What starts:
- The plugin's native `setup()` runs at every launch on iOS and Android with a key. It runs before the controller knows the answer, in both switch positions.
  - With the switch at `0`, `uncaughtExceptions: true` alone brings it up, for the fatal JS hand-off: `_isFatalJsCaptureNativeEnabled()` (`sdk-src/prn/src/posthog-rn.ts:3058-3063`), used at `:3509` and `:3542-3544`.
  - With the switch on, `nativeCrashes` brings it up as well (`:3025-3048`).
- Native events are filtered only by the plugin's own native `beforeSend`. It deduplicates fatal JS reports and restores the values JS approved. It applies no consent and no scrub:
  - iOS: `node_modules/@posthog/react-native-plugin/ios/PosthogReactNativePlugin.swift:371-397`.
  - Android: `android/.../PosthogReactNativePluginModule.kt:175-184` and `:815-826`.

What it can carry, checked against the installed sources:

1. **`$rageclick` (iOS).**
   - Rage clicks are on by default: `PostHogRageClickConfig.enabled` is `@default true` (`dist/types.d.ts`, and `posthog-rn.ts:226-240`).
   - The JS layer passes the config to native only when it is set (`posthog-rn.ts:3387`), and native applies it at `PosthogReactNativePlugin.swift:336-349`.
   - R93's `rageClickConfig: { enabled: false }` stops it, and its reasoning holds. Given "What starts", R93 is needed even when crash reports are consent-only (nit 4).
2. **Native crash reports** (switch on, the default). posthog-ios and posthog-android build and send these, and they never pass through `gateOutgoing`. So the `value` is not reduced to the type, the frames are not trimmed, and `$process_person_profile: false` is not added.
   - On Android, a fatal JS error that PostHog's JS handler did not mark is re-reported natively as a `JavascriptException`, whose `value` is the JS message and stack (`PosthogReactNativePluginModule.kt:815-826`). React render errors bypass that handler (`posthog-react-native/src/error-tracking/index.ts:434-436`).
   - On iOS (new architecture), the JS text may survive in `mechanism.meta.signal.crash_info_message` (`PosthogReactNativePlugin.swift:141-149`).
   - The app has no error boundary (none under `app/` or `src/`), so a render error is fatal in a release build.
   - This answers the receipt's SKIPPED item "whether a native crash report passes through `before_send`": it does not.
   - JS fatals are fine. They pass `before_send` before they are handed to native (`posthog-rn.ts:3687-3700`; `error-tracking/index.ts:477-482` and `:541-548`).
3. **A native `/flags` preload.**
   - When native error tracking is on, the JS layer passes `preloadFeatureFlags: true` to native, because `pushOnlyInit` is false (`posthog-rn.ts:3313`, `:3326`).
   - Native then fetches flags at setup with the distinct id it has stored. After an earlier yes, that is the person's analytics id, sent before the controller's first `reset()`.
   - The JS option `disableRemoteFeatureFlags` does not reach native. So the plan's comment "no /flags traffic at all", and the options test's name ("no ... flag ... traffic"), hold for JavaScript only.
   - The plugin says native needs this preload for the project's exception-autocapture kill switch (`posthog-rn.ts:3308-3312`).

What is not affected:
- The plugin forces native lifecycle events, screen views and deep links off (`PosthogReactNativePlugin.swift:323-324`; `PosthogReactNativePluginModule.kt:161-163`).
- Native surveys are off (`:403`). Push is off, because both push flags are false.
- Native replay starts only from `startSessionRecording`. Its masks and `captureTouches: false` are applied at the first setup (`:406-445`).
- Logs: `captureLog` is false, and the logs pipeline captures nothing by itself.
- On the JavaScript side, only scrubbed `$exception` events leave before a yes. The only other JS request is `GET /array/<token>/config`, which carries no id (`@posthog/core/src/posthog-core-stateless.ts:776`).

Ask:
- The plan left "may not pass through `before_send`" to a device check. The installed source settles it.
- Before Q5, put this to the owner, with Q4's counsel item. Either keep native crash capture without consent, knowing items 2 and 3, or make native capture consent-only (`nativeCrashes` and `androidNdkCrashes` false).
- The option is read once, at launch. So consent-only means native capture is off until the next launch after a yes, or off altogether.
- Record the source answer in the receipt's SKIPPED line.

**m3. Two windows where data is lost rather than held.**

1. **The screen on display when the answer turns yes is never sent.**
   - Probe U4: a controller that is `loading` at mount, then answers yes, sends no `screen`.
   - `AnalyticsUpkeep.tsx:75-77` sends a screen only when the route or the controller instance changes, and `controller.screen` drops anything before a yes, as the plan says.
   - Every launch starts in `loading` (1D-T1). So the first screen of every launch and of every sign-in, usually Home, is never recorded.
   - Fix: subscribe to the controller, and send the current pattern once when it enters yes. The plan's text says "when the segments change", so this needs a ruling.
2. **Events tracked before the controller is installed are dropped.**
   - On iOS and Android with a key, `install()` awaits `import('./posthogClient')` (`appAnalytics.ts:34`) before it calls `setAnalytics`.
   - Events tracked in the effects of the same first commit therefore find no controller, and `trackClientEvent` drops them (`getAnalytics()?.track`). L4 says events tracked before the answer are held.
   - No emitter fires there yet, but 1D-T7's first-screen (onboarding) events will.
   - On the web and without a key, `install()` has no `await` before `setAnalytics`, which is why no test sees this.

**m4. L4's "every request carries `X-GoGoSpend-Analytics: off`" holds for the shared transport only.**
- Four other `createV1Transport` calls pass no `analyticsOff`: `accountServices.ts:22`, `privacyServices.ts:25`, `ImportDeviceParts.tsx:32` and `ReceiptParts.tsx:84`.
- This has no effect under 1D-T11's rules:
  - Person events go only with `transactions.create` and the sync routes, which use the shared transport.
  - Failure counts are anonymous, whatever the header says.
- These four files are also outside this task. So it is not a defect today.
- It matters as soon as a server event joins those routes (spec §7's "slip import finished", in P4). Either pass `analyticsOff` there, or build those resources on `getSharedV1Transport()`.

### Nit

1. `client.ts:345` reads `analyticsOff` once per request. The network resends (`:362-375`) and the 401 resend (`:383-393`) reuse that header, so a no given between two attempts does not reach the resend. Reading it for each attempt is a one-line move.
2. `controller.ts:28` says `setAccount` "rejects when the store or the server fails". But `load` catches every server failure, so only the store can make it reject.
3. `posthogOptions.ts:6-7` says "Every option name and value type is checked". The top level is `satisfies { [K in keyof PostHogOptions]?: unknown }`, so only names are checked there. Values are checked only in the three sub-objects.
4. `posthogOptions.ts:57-58` and the receipt's deviation 1 say crash reports start the native SDK before any yes. It also starts when crash reports are consent-only (m1), so R93 is needed in both positions.
5. `DeviceDiaryProvider.tsx:55-57`: the reflowed JSDoc leaves "next person starts from the defaults. An" on a line of its own.
6. `analyticsServer.ts:39`: the `code === 'NOT_FOUND'` half of the check is unpinned (R3). It is equivalent against today's edge.
7. The brief says `PL/logs/run/` holds the planner's logs. That folder is not in `PL`, and not in `SHA256SUMS` either. The implementer's logs in `scratch/1d-t6-impl/` cover RED, GREEN and the gate.
