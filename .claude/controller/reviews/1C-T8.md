### Major

**M1. The session-ended screen never offers a way to another account when its main button is the email code to the account's own address. On today's build, the account-unavailable variant is a dead end.**

- Where:
  - `SessionEndedScreen.tsx:86-88`: `main` is the account's method when offered, otherwise email; `others` is the build's methods minus `main`.
  - `:112`: the email main button fixes the account's own address.
  - `:223`: ใช้วิธีอื่น is drawn only when `others` is not empty.
  - `EmailCodeScreen.tsx:285`: a fixed address has no เปลี่ยนอีเมล.
  - So when `main` is `email`, no email code to another address is ever offered. When the build offers only email, `others` is empty and ใช้วิธีอื่น is not drawn at all.
- Today's app installs `NO_NATIVE_SIGN_IN` (`auth/betterAuthClient.ts:62`), so every build offers only the email code until 1C-T7 lands. Android stays email-only until Google's development-build check passes (Q1). On such a build, every account's session-ended screen has exactly one button: an email code to its own address.
- Probe `probes/ReviewSessionEndedWays.render.test.tsx` passes at `5e8b70e` and records the buttons each state offers (`logs/probe-session-ended-ways.log`):
  - Email account, account unavailable, email-only build: `['Continue with email']`. Its code step has only the back button and "Send the code".
  - Apple account, account unavailable, email-only build: `['Continue with email']`, to the Apple account's own address.
  - Email account, a build with all three methods: ใช้วิธีอื่น offers Apple and Google, never another email address.
  - Apple account on iOS (Apple and email): ใช้วิธีอื่น offers an email code to any address. This is the only state with an email way to another account.
- Why it bites:
  - `account_unavailable` means the account is deleting, deleted or disabled. The server refuses its sign-in (`betterAuthPort.ts:124`, 403 `ACCOUNT_UNAVAILABLE`), so the only button can never succeed. After it fails, the screen says the records are safe but offers no other way.
  - Task 8's behaviour clause requires one: "Every failure says the records are safe and offers another way, as §5.2 requires" (plan line 1014).
  - D37's other-account path (keep or erase) cannot be reached.
  - 1C-T9's guards send every `ended` session to `/session-ended`. A phone whose account was deleted from another phone then stays on this screen with no way forward.
  - The E2 screenshots will not show it: `signin-session-ended-unavailable` draws an Apple account on a build with all three methods.
- It follows P6 as written ("ใช้วิธีอื่น lists the build's other methods"). P6's own intent was "email there with a free address, to sign in to another account", so the fix amends P6.
- Fix (small):
  - Whenever the main button is the email code to the account's own address, ใช้วิธีอื่น also offers an email code to another address. It needs a new DRAFT label, for example "Use another email" / "ใช้อีเมลอื่น".
  - Draw ใช้วิธีอื่น whenever that list is not empty.
  - For `account_unavailable`, consider leading with that other-account way.
  - Add a render case: an email account on an email-only build reaches an email field with no fixed address, and the unavailable variant has a way forward.
  - Add a catalogue section for an email account, so the owner sees it at E2.

**n2. A new pending version keeps the old tick.** `TermsGate.tsx:73` renders `TermsScreen` without a key, so a re-read that replaces the pending versions keeps `ticked`. Probe `probes/ReviewTermsTick.render.test.tsx` (passes, `logs/probe-terms-tick.log`):

- The person ticks for terms v2.
- A `policy_required` read brings v3.
- Continue accepts `{ kind: 'terms', version: 3 }` with no new tick.

`key={pending.map((p) => `${p.kind}:${p.version}`).join()}` would ask again. The race is rare, since a version would have to be published while the terms show.

**n3. The devices list goes stale after a link or a remove.**

- A fresh sign-in makes a new session and signs this phone's old one out (K14; `credentialProvider.ts:264`).
- `changeMethod` reloads only `linked` (`DevicesScreen.tsx:133-134`).
- So the signed-out session keeps the "This phone" row, and the new session is missing until the screen reloads. Reload devices too, in 1C-T9.

**n4. `maxLength={6}` on the code field (`EmailCodeScreen.tsx:257`).** On a phone, `maxLength` cuts typed or pasted text to six characters before `onCode` strips non-digits. A pasted " 482913" or "482 913" therefore becomes five digits and starts nothing. The digit filter, which the planner's E8 pins, never sees the rest. `onCode` already keeps six digits, so `maxLength` can go, or be wider.

**n5. Small copy points for the owner's pass.**

- The resend label is built by joining strings (`${sc('Send a new code in')} ${clock(wait)}`, `EmailCodeScreen.tsx:281`), not with a `{time}` placeholder, which `useCopy`'s own note asks for. It matches the board, where the time is its own text.
- An iPad or Mac row reads "iPad · This phone" (`DevicesScreen.tsx:242`).
- The port maps every non-429 4xx code answer, an expired or used-up code included, to `WRONG_CODE` (`betterAuthPort.ts:122-126`). An expired code therefore gets "That code isn't right. Type the 6 digits from the newest email." The resend is enabled by then, but the line could mention a new code.
- The device names (iPhone, iPad, Android, Mac, Windows; `DevicesScreen.tsx:55-63`) are the folder's only bare user-facing strings. They are brand names, which is acceptable (P7).
