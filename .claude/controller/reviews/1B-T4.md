## The questions in the brief

### Object registry and tombstones
- **A deleted object is never served again / a tombstone outlives any grant.** T4 has no serve path yet (1B-T6, T8, T9 add the serve functions). A deleted key becomes a `tombstone` row due a day later and is deleted from R2 once more before its row is dropped (`objects.ts:90-118`), so a late PUT is removed (the plan's late-PUT test, both halves). Grants last 5 minutes (`SNAPSHOT_GRANT_MINUTES`, `ATTACHMENT_GRANT_MINUTES`; `SnapshotGrants` caps any grant at 60), well inside the 24-hour tombstone. Whether a serve function refuses a released or deleted record is the serving task's check, not T4's.
- **Deletes are idempotent.** Yes. R2 deletes of absent keys succeed; two overlapping `deleteDueObjects` runs read the same due rows, delete the same keys and write the same tombstones; a due tombstone's row is dropped once.
- **A failed R2 delete is retried, not lost.** Yes: the batch's rows keep their status, move to now plus 60,000 (only rows still due, `AND delete_after <= ?`, line 103), and the failure is logged as `object_delete_failed` with `failureName` only (no key, no message: `{"level":"error","event":"object_delete_failed","failure":"Error"}`). An unbound `OBJECTS` takes the same path, because `v.bucket.delete` is evaluated inside the `try`.
- **Nothing is deleted that another record still references.** Holds for every sequential order I tried, and the schema refuses a non-receipt published without a deadline (probe 7). It does not hold for one interleaving: a publish that lands while the alarm's R2 delete is in flight (minor 1).
- **The erase path still removes everything.** `erase()` is unchanged. Probe 9: after reserving keys in a member's vault and erasing it, `vault_objects` is empty, and `startPendingWork()` answers `{ started: 0, failed: 0, held: false }`. R2 objects of an erased vault are left to 1C's prefix sweep (`purgeVaultObjects`), as B19 says.

### Grants
- **Who mints:** only vault code holding a `VaultContext` (its `digester`); T4 mints none. Keys are derived per purpose under the labels the API and the PostgreSQL edge use (`container.ts:130-131,166`, `exports.module.ts:22`, `sync.module.ts:19`, `attachments.module.ts:27`); the test proves a snapshot grant does not verify as an export or attachment grant and that the labels match.
- **Scope:** the MAC covers the scope string. Snapshot and export grants will be scoped to the account; receipt grants to `${accountId}\u0000${sessionId}` exactly as the plan specifies (the API used `accountId\0bindingId\0sessionGeneration`; the vault's sign-out check covers the generation's role, 1B-T9). A grant for one account cannot verify for another, and in addition the download route reaches only the caller's own vault (`idFromName(claims.accountId)`).
- **Expiry:** 5 minutes, and `issue(..., notAfter)` keeps it inside the file's expiry when the serving task passes it. **Single use:** the plan does not ask for it (neither did the API).
- **Downloads check the grant before R2:** `src/v1/files/downloads.ts` holds only the slots in T4 (`EXPORT_SLOTS` 4 per isolate, `RECEIPT_SLOTS` 8 and 2 per account, matching `EXPORT_DOWNLOADS_PER_PROCESS` and `DEFAULT_ATTACHMENT_LIMITS`). There is no serve function to check yet; that review belongs to 1B-T6, T8 and T9.

### Pending-work starts
- **`starts` on routes:** `startsWork(route, status)` is true only for `starts: true` and 200..299 (tested at 199, 200, 202, 300, 409, and without `starts`). The hand-off runs through `waitUntil` after the reply is built, on the caller's own stub, and never for a public Worker route (no session).
- **Deviation 2 is right under the plan.** The plan's sentence is route-agnostic ("a route with `starts: true` that answers 2xx runs `deps.waitUntil(deps.startWork(stub))`"), 1B-T5's `POST /v1/imports` is `worker: 'import.upload'` with `starts: true`, and 1B-T5's Modify list does not include `handler.ts`. T4 is the only task that can wire it. The Worker path uses `context.vault.stub`, the same `idFromName(claims.accountId)` stub the handler's steps used.
- **Never lost:** a rejected start is caught and logged as `pending_work_unstarted` before `waitUntil` (deviation 3); an item whose `start` threw or answered `unbound` is not marked and is tried on the next run; a `start` that succeeded but whose `markStarted` block failed is counted failed and tried again, which `createOnce` makes harmless. Until 1B-T11 wires the alarm, the next run is only the next `starts` route, which is the plan's lane order (and `WORK_STARTERS` is empty in T4).
- **Double-run:** two overlapping `startPendingWork` runs on one vault start the same item twice (probe 4: `starts 2`, both answers `started: 1`). The `await v.gates()` (KV) and each `await start(...)` open the input gate. This is safe by design only at the target: `createOnce` for Workflows (id = item id) and `parseSource`'s duplicate handling for the parse queue (B6). See nit 4.
- **`work_start_failed`** is logged with `failureName` only.

### SQL
- Every value is bound, `LIMIT` included. No statement in T4 binds more than 5 parameters; every key list (`tombstoneObjects`, the failure update, the success `DELETE` and `UPDATE`) is one `json_each(?)` parameter (R57). ## Findings

### Blocker

### Major

### Minor

**1. A publish that lands while the alarm's R2 delete is in flight loses the published object.** `publishObject` (`objects.ts:44-50`) accepts any `reserved` row, including one past its own deadline: it reads no clock. `deleteDueObjects` reads the due rows, awaits `bucket.delete(keys)` (the input gate is open during R2 I/O), then tombstones every `given` row whose status is not `tombstone` (line 112) with no `delete_after <= now` guard, although the failure path has one (line 103).
- Probe 1: a receipt reserved at `t0` is published an hour after its grace deadline; it succeeds and the row reads `published` with no deadline.
- Probe 2a: during the in-flight delete, the writer PUTs the object and publishes it (no deadline, a held receipt). Afterwards the row is `tombstone` due a day later and R2 has no object.
- Probe 2b: if the delete reaches R2 before the PUT, the object is in R2 but its published row has become a tombstone, so it is deleted a day later.
- The API fenced this twice: `publishIfCurrent` requires a current lease (a reservation's deadline is past the lease's last moment), and the sweep marks rows `deleting` before it deletes from storage (`object-publication.service.ts`). The plan's own test wording, "given up at its deadline", is the same rule.
- Why minor and not major: it needs a writer that publishes more than its grace after reserving, during the few hundred milliseconds of the alarm's delete. No planned caller does that (receipt copies have a 60-second deadline, uploads reserve until their receive deadline plus the grace, and exports and snapshots publish seconds after their PUT), and nothing calls `deleteDueObjects` in production until 1B-T11.
- Fix (small, plan-compatible, and best done before 1B-T6, T8, T9 and T11 build on the contract): in `publishObject` add `AND delete_after > ?` with `c.now.getTime()`, so an expired reservation is given up and the writer fails visibly. Add `AND delete_after <= ?` (the batch's `now`) to the success path's `DELETE` and `UPDATE` (lines 111-112), matching line 103. Add a case with an interleaving bucket like probe 2a, and a mutant that drops the new predicate.

**2. `reserveObject` does not check that a key belongs to this vault.** The schema checks only that the key starts with its purpose (`0001_vault_files.sql`: `substr(key, 1, length(purpose) + 1) = purpose || '/'`). `deleteDueObjects` deletes whatever the registry holds. A later caller that registered a key built from another vault's id, or from request input, would make this vault's alarm delete another person's object. Every key today comes from `vaultObjectKey(purpose, c.vaultId, ...)`, so there is no current path. Hardening that costs one line: in `reserveObject`, refuse a key that does not start with `vaultPrefix(purpose, c.vaultId)` (`ObjectStoreError('invalid_key')`), with a test.

**3. Three behaviours the receipt states as deviations have no test.** Reviewer mutants on `mut/`, each restored afterwards (`run-mutants.sh`, `mut-G*.log`):
- G1, drop the `.catch(...)` in `handOffWork` (deviation 3): survives, 20 passed.
- G2, `break` instead of `continue` after a failed batch (deviation 4): survives, 20 passed.
- G3, `releaseObject` also moves a tombstone's deadline (deviation 6): survives, 20 passed.
- G4, the failure update without its `delete_after <= ?` guard: survives, 20 passed.

Add a case for each survivor: a `startWork` that rejects (the response is still 2xx and `settle()` resolves); a failing bucket with more than 1,000 due keys (the second batch is still tried); `releaseObject` on a tombstone (its deadline stays). G4 is equivalent for any sequential run; minor 1's interleaving test would cover it.

### Nit

1. `putConcatenated` (`objects.ts:128-141`) does not call `assertObjectKey`, which `R2ObjectStore.putStream` does, and it trusts `totalBytes`: `Buffer.concat` zero-fills or truncates to it, while a single part ignores it. Probe 6: parts `[1]` and `[2]` with `totalBytes` 5 stored `[1,2,0,0,0]` and answered `bytes: 5`, under the key `Not A Vault Key/../x`. Callers build keys with `vaultObjectKey` and pass the true total, so this is defence in depth: assert the key, and throw when the parts' total differs from `totalBytes`.
2. A tombstone marked again by `tombstoneObjects` while its second delete is in flight is dropped anyway (probe 8: the row is gone), because the success `DELETE` has no `delete_after <= now` guard. Minor 1's fix covers it.
3. `deleteDueObjects` returns the number of keys sent to R2 (`deleted += keys.length`), but its doc comment says "how many keys R2 deleted". R2 does not report that. Reword the comment.
4. Overlapping `startPendingWork` runs start the same item twice (probe 4). This is acceptable because `createOnce` and B6 make a second start harmless, but neither the code nor the receipt says that `markStarted` is not an at-most-once guard. One sentence in `work.ts` and in the receipt's notes for 1B-T5 would keep the parse starter from relying on it.
5. In `user-vault.ts`, the four new imports sit after the relative imports, and one of them is an `@api` import. This breaks the file's grouping, but it kept the 1A-T8b merge conflict-free, so leave it.
6. `controller/scratch/1b-t4/` keeps the GREEN, mutant and gate logs but not the RED log, so the RED counts (20 failed, all `AssertionError`) rest on the receipt alone. It was probably lost with `/private/tmp`.
