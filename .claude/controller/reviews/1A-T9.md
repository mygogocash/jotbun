**The controller's first read is correct, and I traced it to its source:**

1. The vitest diff pretty-prints both answers with keys sorted. I split `parity-diff.txt` into the four printed blocks (Nest and vault for steps 44 and 45). A line diff shows them identical apart from the `"nest"`/`"vault"` label. The test compares `JSON.stringify(n) === JSON.stringify(v)`, and the bodies are `JSON.parse` output (strings, numbers, booleans, null, arrays, objects). So the only thing that can differ is key order.
2. **Source.** NestJS stores each change's snapshot in `entity_changes.snapshot jsonb` (`apps/api/drizzle/0005_commands.sql:40`, `schema.ts:304`; written by `ChangeWriter.append` through `jsonb_array_elements`). It stores keys shortest first, and keys of equal length bytewise (`lengthCompareJsonbStringValue` in `jsonb_util.c`). `JSON.parse` keeps that order. The vault stores `JSON.stringify(change.snapshot)` as TEXT (`src/vault/commands/change-log.ts`), and `changeOf` in `src/vault/reads/sync.ts:95` hands back `JSON.parse(row.snapshot)`, so it serves the DTO's insertion order. The page, group and change envelopes are built in JS on both sides, in the same order (`groups, next_cursor, has_more` / `revision, command_id, changes` / `entity, id, version, state, snapshot`).
3. This also explains why `parity.db.test.ts` passes: the PostgreSQL edge reads the same jsonb column, so it gets NestJS's order.

## 2. Ruling

**(a) Is key order a real parity requirement? Functionally, no. Under the plan's test, yes.**

No consumer depends on member order:
- `/v1/sync/changes` has no ETag, hash or signature. The only ETag code in `apps/api` is the legacy `spend/`; `apps/edge/src` has none. The cursor encodes account, revision and generation (`encodeSyncCursor(accountId, last, generation)`), not the body.
- The byte budgets (`changeGroupBytes`, the `Buffer.byteLength(JSON.stringify(group))` page check) are the same for any key order.
- The app parses each snapshot (`JSON.parse`), validates it field by field, stores it re-serialized (`diaryRepository.ts:261`) and reads it back with `JSON.parse` or `json_extract`. No raw sync JSON is cached or compared. The app's two `JSON.stringify(a) === JSON.stringify(b)` comparisons are `recordModel.ts:208`, which compares scalars and id pairs, and `importReview.ts:265`, which compares import candidates from one backend, not sync.
- RFC 8259 §4 makes member order insignificant.
- NestJS's order is an artefact of jsonb storage, not a designed contract (see the inconsistency in section 1).

The acceptance test the plan wrote, however, compares bytes (`JSON.stringify(n) === JSON.stringify(v)`). Spec 6.6 asks for "the same answers", and plan Step 4 says: "Fix each listed difference in the vault, never in the session or the normalizer."

**(b) Where the fix belongs: the vault, in `src/vault/reads/sync.ts`.** It should emit jsonb key order for stored snapshots. Do not change the normalizer.
- It stays within the plan (Step 4) and needs no owner decision. A normalizer that compares parsed values (sorted keys) would be semantically harmless, but it is a plan deviation that needs the owner's yes. It would also downgrade all four parity suites (`parity`, `parity-auth`, `parity-files`, `vault-parity`) from byte-level to value-level checks.
- The fix is small and verified (section 3). Byte-identical answers keep the oracle strict, so any future difference listed is a real one.
- 1B needs the same helper anyway. NestJS's full-resync snapshot reads entity heads as `snapshot jsonb` (`0009_jobs_storage.sql:318`), and its import `issues` are jsonb too: `ImportIssue` `{code, source_row_id, field}` comes back from jsonb as `code, field, source_row_id`. The vault's 1B ports should call the same `jsonbOrder` wherever NestJS serves an object out of a jsonb column.

## 3. The exact fix (verified in the probe; ready for a Haiku brief)

Patch: `.claude/controller/scratch/1a-t9-review/jsonb-order-fix.patch`. `git apply --check` is clean on the worktree at `6ed0ed6`. It contains exactly this:

**`apps/edge/src/vault/reads/sync.ts`**
- In `changeOf` (line 95): `const snapshot: unknown = row.snapshot === null ? null : jsonbOrder(JSON.parse(row.snapshot))`.
- Append the exported helper:

```ts
/**
 * A stored snapshot with its keys in the order the API serves them. The API keeps
 * snapshots in a PostgreSQL jsonb column, which stores an object's keys shortest
 * first (in UTF-8 bytes), then bytewise, and node-postgres parses them back in
 * that order. Nested objects are ordered the same way; arrays keep their order.
 */
export function jsonbOrder(value: unknown): unknown {
  if (Array.isArray(value)) return value.map(jsonbOrder)
  if (value === null || typeof value !== 'object') return value
  const keys = Object.keys(value).sort((a, b) => Buffer.byteLength(a) - Buffer.byteLength(b) || Buffer.compare(Buffer.from(a), Buffer.from(b)))
  return Object.fromEntries(keys.map((key) => [key, jsonbOrder((value as Record<string, unknown>)[key])]))
}
```

- The orders it emits are the NestJS column of the table in section 1.
- I applied it at read time, at the one place `/v1/sync/changes` serves a stored change. That point also covers rows stored before the fix. The write path, `change-log.ts`, stays unchanged: `group_bytes` does not depend on key order.

**`apps/edge/test/workers/sync.test.ts`**, in `describe('GET /v1/sync/changes, ...')`, importing `jsonbOrder` next to `syncChanges`. Two cases:
1. `orders keys as jsonb does: shorter first, equal lengths bytewise, nested objects too, arrays kept in order`. It is pure: `jsonbOrder({ bb: 1, list: [{ ccc: 1, d: 2 }, 'x'], a: { zz: 1, y: null }, ab: 2, aa: 3 })` stringifies to `{"a":{"y":null,"zz":1},"aa":3,"ab":2,"bb":1,"list":[{"d":2,"ccc":1},"x"]}`; `null` and `'6500'` pass through unchanged.
2. `serves each snapshot with its keys in the API's order ...`. Through the route: two wallets, the built-ins, an expense with merchant and note, a transfer, and a budget with one category limit. It parses `GET /v1/sync/changes` with `JSON.parse(await res.text())` and asserts `Object.keys` of each entity's snapshot equals the NestJS column of the table above, including `budget.category_limits`.

### Minor

1. **The summary's `category_id` tie-break (`src/vault/reads/summary.ts:43`, `ORDER BY t.type, t.category_id`) is pinned nowhere.**
   - I mutated it to `t.category_id DESC` and the whole Workers suite still passed (21 files, 373 passed including my two probe cases; `tiebreak-mutant.log`).
   - The session has one category per type (steps 34 and 38), and the golden-month case in `test/workers/summary.test.ts:39` uses `expect.arrayContaining`.
   - **Do not add a second category per type to the money session.** Spec 6.6 fixes it at 49 steps, the plan moves it verbatim "with no behaviour change", and it is also `parity.db.test.ts`'s oracle.
   - Instead, make the golden-month assertion exact. It already has two expense categories, `food` and `bills`, so asserting `categories` in `type, category_id` order pins the tie-break with no new data. This is a 1A-T7 follow-up; it need not hold up this PR.
2. **The normalizer can hide a consistent wrong id that echoes a random request value.**
   - Idempotency keys for most commands, and some entity ids, are `randomUUID()` per step, not in `SHARED`. They become `<id:N>` by order of first appearance.
   - So if the vault minted its own `command_id` for, say, the PATCH, archive or budget commands, and used it consistently in the ack and in the sync group, both runs would number it identically and the comparison would pass. Step 14's ack, for example, normalizes to `"command_id": "<id:12>"`.
   - The same bug is caught where keys are shared: `replayKey` (steps 6 and 7), `lunchKey` (step 43).
   - Fix: give every key and id in the session a per-run `SHARED` value. That changes the session, so it is a follow-up for the owner or plan, not this task.
3. **Routes the differential never compares:**
   - `PATCH /v1/categories/:id`, `POST /v1/categories/:id/archive` and `.../unarchive`;
   - the success path of `GET /v1/wallets/:id` (step 20 calls it only with a bad id);
   - page 2 of history, and a sync resume, by following a cursor. Cursors become `<cursor>` and are never followed.
   - These have ported Workers-runtime tests, but no NestJS comparison. Spec 6.6 fixes the session, so this is a follow-up candidate, not a defect of 1A-T9.
4. **The receipt needs a fix-round update:**
   - The CI result.
   - The line "from `020c391` ... the worktree needed no merge" is stale now that `6ed0ed6` merges `c2d6d9d`.

### Nit

1. The normalizer turns any ISO-8601 instant into `<timestamp>`, whatever its precision or offset, so drift in timestamp format would be hidden. The impact is low: every `isInstant` in contracts and the app uses `Date.parse`.
2. Debugging trap: vitest's failure diff sorts keys, so a key-order-only failure prints two identical-looking blocks. If the test is ever reworked, also print the first differing character offset of the two strings. This is not for this task: the test is the plan's code.
3. At the end of the CI job, GitHub terminated 32 orphan processes: 12 workerd, 8 esbuild, 12 node. `startDevWorker`'s `stop` sends SIGTERM to `npx` only. Locally, on macOS, none were left after 8 runs. With no passing baseline of this job in hand I cannot attribute them, and the pattern predates this task. The vault Worker adds one instance.
4. The new `VAULT_PENDING_ROUTES` case is redundant. With `GET /v1/summary` moved from ported to pending, it fails together with the existing enumerated-routes case (`run-m5b.log`). It is harmless, and plan Step 2 requires it.
