### Minor

**m1. A look, order or icon that was never stored drops out of view after the next stored change to the same name, or when the account's first read lands. P3 says it "shows until the app closes".** (data lens m1)
- **Where:**
  - `WalletLooksProvider.tsx:120-122`. When a change's own read succeeds, the provider replaces the whole slot with `change(slot.parse(stored.raw))`. That value is what is stored plus this change. An earlier change that was never written is not in it, so it drops out of view. That covers both a change whose write failed and a change made while its name could not be read.
  - `:112`. The account's first read replaces all three slots. A change made from a child's mount effect is queued ahead of that read, because React runs a child's effects before its parent's.
- **Probes:** the lens's `data/ready-cases/DataLensProbes.render.test.tsx`. I ran it again in `synth/tree/` (log in `synth/probes-provider.log`): `Tests 4 failed | 5 passed (9)`. The same four cases fail as in the lens's `data/probes-provider.log`:
  - **D1:** W1's write fails. W3's change is then stored, and W1 goes back to its derived look.
  - **D2:** the store cannot read `looks` during W1's change, then reads again for W3's change. The result is the same as in D1.
  - **D8:** the store's calls run `get looks` then `set looks`, and only then the first read's three gets. So the change runs before the account's first read, which P3 says it must follow.
  - **D8b:** when that early change's write fails, the first read hides it.
- **What holds:** no stored data is harmed.
  - A name the store cannot read is still never written over. D2 checks the store byte for byte.
  - Every change reads its own name before it writes, so nothing stored is lost.
  - D3 to D7 pass.
- **Why it matters:**
  - P3 (accepted as written) says: "A change to it, or a write that fails, shows until the app closes" and "two quick changes never drop each other".
  - The provider's header (`:14-16`) makes the same claim. So does V4's title (`WalletLooks.render.test.tsx:195`), but V4 checks only right after the failure.
  - So a person who picks a look while the phone's storage is failing sees that look revert at their next change.
- **Why only minor:** the trigger is a failed AsyncStorage read or write, which is rare, and nothing stored is lost.
- **Fix:** keep the session's unstored changes per account in a ref, and lay them over each read: the change's own read and the account's first read. Another way is to fold them into the next write.
  - The lens's mutant RM8 (the first read merges with what is shown) could be one part of that fix. It survives the 27 focused cases.
  - D1, D2 and D8b are the ready cases.
  - Take D8 only if the fix also queues the first read ahead of every change.
- **Carrier:** a follow-up. The setters' first callers are P2-T20 (`setOrder`), P2-T21 (`setLook`) and P2-T29 (`setIcon`).
