### Minor

**m1. A reply whose body stalls past the call's time is recorded `failure: 'other'`, not `timeout`, and the signal that alone ends it is untested.**
- **Where:**
  - `transport.ts:40`: `signal: AbortSignal.timeout(options.timeoutMs)`.
  - `callFailure` at `transport.ts:66-83`.
- **Probe ST** (`review-stall.test.ts`):
  - Setup: the real undici `fetch`, and a loopback server that sends 200 headers and then never ends the body, under `new AiDeadline(2_100)`.
  - The deadline holds: the call rejects at 2.10 s.
  - But it rejects with a raw `DOMException` named `AbortError`.
  - `callFailure` gives `other`, and the trace holds `{ sent: true, failure: 'other', httpStatus: null }`.
  - Probe PB, which uses a fake stream, agrees.
- **Probe ST2:** the SDK's own `timeout` alone leaves the same call pending at 6 s.
  - SDK 1.2.0 clears its timer once the headers arrive (`client.ts:1770-1776`).
  - So the `AbortSignal` is the only guard on the body phase, and mutant R10 (drop it) passes all 52 cases.
  - A refactor that trusts `timeout`, as 1B-T7's sender did, would let a stalled body outlive the route's deadline (Review Focus 2) with no test failing.
- **Against:**
  - The plan's own case name (line 288): "a call that outlives its time fails as a timeout and is recorded".
  - H5: its refund is P3-T7's `shouldRefund` (line 425), which reads `failure` and skips `other`.
  - The code follows the plan's mapping to the letter ("anything else `other`", line 283). The gap is the plan's, which names no DOM abort.
- **Reach:**
  - Not reachable in this PR: nothing reads `failure` until P3-T7 and P3-T10.
  - I could not measure from here how often a gateway reply stalls after its headers.
- **Fix (small):**
  - In `callFailure`, treat a `DOMException` named `AbortError` or `TimeoutError` as `timeout`.
  - Add a unit case with a stalled body. It also kills R10.
- **Carrier: P3-T7**, before `shouldRefund` relies on it, unless a P3-T4 pin comes first.

### Nit

**n1. `parseRetryAfter` (`transport.ts:126-132`) accepts malformed values.**
- Probe PF:
  - `"1.5"` gives 1, and `"40abc"` gives 40.
  - `"0"`, `"3601"` and an HTTP date give null.
- RFC 9110's delay-seconds is digits only, and the plan says "whole seconds".
- Fix: check the value against `/^\d+$/` before parsing it.

**n2. `note` starts its deadline before `consume`, unlike the other routes.**
- `note`: `service.ts:173-175`. Parse, slip and ask start it after `consume`: `:100-102`, `:126-128` and `:201-210`.
- Probe S3: a 24 s `consume` leaves `note` no call (the use is spent and it answers the plain facts), while `parse` still gets its full 25 s.
- Harmless today. P3-T6 should start every route's deadline at the same point.

**n3. `fake-model.ts:24` still has a `send` helper with no callers.** The plan renames `send` to `transport`.

**n4. `handler.ts:130` builds an Anthropic client for every Worker route while AI is on.**
- This includes uploads, downloads and receipts, as the plan's wording asks ("each request's context").
- Probe `probe-ctor/ctor.mjs`: the SDK constructor never throws on a malformed base URL or token.
  - Both fail only at send time, as a `TypeError`, classed `other`.
  - So this costs time on non-AI routes but cannot make them fail.
- If the cost ever shows, build the client lazily.

## The controller's questions

### 1. The wiring the plan's mutants never touched

- **The handler's fallback** (`handler.ts:130`): R5, R6 and R7 are killed.
  - `null` means "no AI", not "ask the env".
  - Absent means the env decides.
  - A transport given in the deps wins.
- **`aiOf`'s `w.transport ?? null`** (`routes.ts:15`): R8 is killed.
  - The `?? null` matters only because the field is optional (planner ruling P2).
  - `runWorker` always sets it.
- **`tracedSend` and `AiDeadline(25_000)` in `service.ts`:** R2 is killed, but R1, R3 and R4 survive (m2).

### 2. The deadline

- **The 25 s cap:** every route sends with 25,000 (S1). No test pins it (R1).
- **The 2 s floor, where no call is made:**
  - Covered by the unit case and by M2.
  - Probe PE, on a fixed clock: 2,000 ms sends; 1,999 ms does not, records `sent: false` and throws `DeadlinePassed`.
- **A child deadline ends at the earlier of its cap and its parent's:** covered by the unit case and by M7.
- **A call that outlives its time:**
  - Before the headers arrive, it fails as `timeout` and is recorded (the unit case, 2.10 s).
  - After the headers arrive, it is recorded `other` (m1).
- **Use accounting:** 1B-T7's rule "every model call costs its use before it is made" holds for a call the floor skips.
  - The use is consumed before `tracedSend` runs.
  - The skipped call is recorded `timeout` with `sent: false`, which P3-T7 can refund.
  - S2 and S3 show one consume and no call.
  - 1B-T7's case for this rule passes in CI.

### 3. Failures

- **`callFailure` follows the plan's mapping:**
  - A 529 is `server_error`, not a rejection (the unit case and M3).
    - Probe PC, through the real transport: one fetch, 1 ms, `httpStatus` 529.
  - A rate limit fails at once with its wait (the unit case and M4: one fetch, under 2 s, a 40 s wait).
  - A fetch that throws is `no_connection` (probe PG).
- **Retries:**
  - SDK 1.2.0's option is `maxRetries` (`client.ts:993`: `validatePositiveInteger('maxRetries', options.maxRetries ?? 2)`). Its source has no `max_retries`.
  - The transport passes `0`, which turns every retry off; M4 (setting it to 1) is killed.
- **What each route answers on each failure** (S4). Every failure kind gives the same answer per route, and each spends one use. The kinds: 429, 529, 500, 400, connection timeout, user abort, no connection, `DeadlinePassed` and other.

  | Route | Answer |
  | --- | --- |
  | parse | 200 `rules` |
  | slip | 503 `AI_PAUSED` (`retryAfterSeconds` 300) |
  | note | 200 `facts` |
  | ask | 503 `AI_PAUSED`, or 200 `facts` once a tool has read figures |

- These are 1B-T7's answers. The one change is intended (B27, A26):
  - With retries off, a 429, a 5xx or a dropped connection falls back at once.
  - 1B-T7's sender retried once first.

### 4. The gateway headers

- **Logging and caching are off on every request:**
  - `defaultHeaders` carry both headers.
  - Probe PA sees `cf-aig-collect-log` and `cf-aig-skip-cache` on the wire.
  - Pinned by M1 and M5.
- **`cf-aig-authorization` is sent only when a token is set:**
  - Covered by the unit case and M6.
  - The env path is untested (m3).
- **SDK 1.2.0 sends `Authorization: Bearer <apiKey>`, never `x-api-key`:**
  - Its `apiKeyAuth` (`src/client.ts:1307-1312`; compiled `client.mjs:452`) builds only that header.
  - Probe PA sees `authorization: Bearer sk-test` and `x-api-key: null`.
  - So the ruled test, which accepts either header, is right for this SDK.
  - 1B-T7's sender used the same SDK, so nothing changes on the wire.

### 5. The trace

- **What a `RecordedCall` holds:** `spanId`, `feature`, `requested`, `model`, `escalated`, `latencyMs`, `sent`, `httpStatus`, `retryAfterSeconds`, `failure`, `stopReason` and `usage`.
  - Probe PH: after a call with a marked prompt, the trace holds neither the prompt nor the reply text.
- **Where it goes:** nowhere.
  - Each route makes its own `newTrace()`, and only `tracedSend` writes to it.
  - Nothing returns, logs, stores or sends it.
- **`logFailure`** prints `failureName` only: the class name, which is `Error` for SDK errors, or `DeadlinePassed` (S4's log lines).
- **The SDK itself:**
  - Its logger defaults to `warn` (`client.ts:806`), and its warn sites print only model names.
  - Its OpenTelemetry spans default to `metadata_only` (`internal/tracing.ts:186`), and are made only when a tracer provider is registered.

### 6. The RED rulings

- **`env.ts` at RED: agreed.**
  - The stub's `transportFromEnv(env: Pick<V1Env, ... 'AI_GATEWAY_TOKEN'>)` cannot compile without that type field.
  - A type-only field is a compile-safe seam, not a missing module.
  - All 9 cases still failed on behaviour.
- **The case that fails by a 5 s timeout: fake timers can replace the real wait.** This is a later pin, not a blocker.
  - Probe FB, using `vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout', 'Date'] })` and `advanceTimersByTimeAsync`:
    - The GREEN call is still pending at 2,099 ms of fake time.
    - Right after, it rejects as `APIConnectionTimeoutError` (`timeout`, latency 2,100).
    - It takes 11 ms of real time.
  - Probe FC: the RED stub's 25 s call is still pending after 3 s of fake time, so the case would fail on an assertion instead of the test timeout.
  - Caution, from probe FA: fake timers do not drive `AbortSignal.timeout`, so a fake-timer case pins only the SDK's own timer. Keep one real-time case for the stalled body (m1's fix), so the signal stays pinned.
