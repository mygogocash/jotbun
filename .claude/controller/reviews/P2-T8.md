The harness (`walletHarness.tsx:117-141`) is plan line 644 word for word. Where it differs from the app, and what each difference changes:
- **Order.** `ThemeProvider` sits above `BunIntensityProvider` and `SafeAreaProvider`; the app has it below them. `SpendV1Provider` sits above the diary and the AI; the app has it below them. None of these providers reads another. My mutants Y1 (the app's root order) and Y2 (the app's spend order) leave the harness test and my cases green, so the plan's order and the app's give the same results. The "nested as the app nests them" wording therefore holds in effect. It follows the plan's own line ("The nesting matches the app's (R58)").

- **No `LocaleUpkeep`, `AnalyticsUpkeep` or `ThemedStatusBar`.**

### Minor

**m-1. Three harness behaviours have no test: E2 and E3 are not equivalent, and X2 survives.**

Protocol step 5 asks for a test for every survivor that is not equivalent. The receipt and ruling P10 call E2 and E3 equivalent, but they are not:
- **E2, no `BunIntensityProvider`** (`walletHarness.tsx:123`).
  - Outside the provider, `setIntensity` throws (`BunIntensityProvider.tsx:20-25`).
  - On the web, the provider reads a stored intensity (`:29-31`), and the default context ignores it.
  - Home's test drives the bun exactly that way: `HomeScreen.render.test.tsx:42` calls `installBrowserStorage()`, line 64 seeds the intensity, and lines 319 to 330 test it. A wallet screen that draws the bun can be tested the same way only because this provider is in the harness.
- **E3, no inner `IntlProvider`** (`:120`). Without it, a language chosen inside the mount (`useLanguage().setPreference`), or stored before the mount, changes the rendered locale. With it, the locale stays the one in the options. P10's "the inner one pins the locale even when a choice is stored" is a real behaviour that no test checks, and it has a cost (m-2).
- **X2, one answer for every ask** (ruling P6(c), `:115`). With `mockReturnValueOnce`, all six cases still pass, but the wallet root gets the wrong answer:
  - A kit part that asks the phone itself (`src/hooks/useReducedMotion.ts`, used by `Sheet.tsx:70`, `UndoBar.tsx:54` and `BunPeek.tsx`) runs its effect before the root's and takes the held answer.
  - The wallet root then gets react-native-web's own answer (false).
  - So `reducedMotion: true` reads `wallet=false app-wide=true`.

These two cases close all three. They are in scratch at `probe/apps/app/src/wallet/testing/suggested.render.test.tsx`, with the test file's imports plus `useLanguage`, `useActiveLocale`, `useBunIntensity`, `useReducedMotion` and `useWalletReducedMotion`. They pass on `47f4b59`; the first fails under E2 and E3, the second under X2, and E1 leaves both green.
```tsx
let choose: (() => void) | null = null;
function Choices() {
  const { preference, setPreference } = useLanguage();
  const { intensity, setIntensity } = useBunIntensity();
  const locale = useActiveLocale();
  choose = () => { setIntensity('quiet'); setPreference('en'); };
  return <Text testID="choices">{`locale=${locale} preference=${preference} bun=${intensity}`}</Text>;
}

test('the bun intensity can change inside the harness, and a language chosen there leaves the mount in its own locale', async () => {
  mountWallet(<Choices />, { locale: 'th' });
  await settle();
  await act(async () => { choose?.(); });
  expect(screen.getByTestId('choices').textContent).toBe('locale=th preference=en bun=quiet');
});

function TwoAskers() {
  return <Text testID="askers">{`wallet=${useWalletReducedMotion()} app-wide=${useReducedMotion()}`}</Text>;
}

test('a part that asks the phone itself gets the answer the root gets', async () => {
  mountWallet(<TwoAskers />, { reducedMotion: true });
  await settle();
  expect(screen.getByTestId('askers').textContent).toBe('wallet=true app-wide=true');
});
```
I rank this minor, as P2-T2's untested `heard` guard was: the code is right, and the plan's own mutant (M1) is killed. The cases can go in now, or with P2-T11, which edits `walletHarness.tsx` next (plan line 764). The receipt's E2 and E3 lines should then say "untested" or name the new case.

**m-2. The inner `IntlProvider` keeps a mounted wallet in its `locale` after a language choice; the app switches.**

`walletHarness.tsx:120` pins the locale below `LanguageProvider`'s own `IntlProvider`.
- In the app, `setPreference('en')` re-renders every screen in English (`LanguageProvider.tsx:60-73`).
- Under `mountWallet`, it changes `useLanguage().preference` but not `useActiveLocale()`. Every wallet string reads `useActiveLocale()` (`useDraftCopy.ts:10`, and `tc()` after P2-T38), and so does `WalletText`'s line height (`WalletText.tsx:19, 29`).
- Probe: `mountWallet(<LocaleProbe />, { locale: 'th' })`, then `setPreference('en')`, reads `locale=th preference=en`. The same probe under `LanguageProvider` alone reads `locale=en preference=en`.

The plan's nesting lists the `IntlProvider`, and the pin keeps mounts deterministic, so this is not a defect by the plan's terms. But neither the harness header nor the receipt states it. P2-T35 builds the two places that choose the language inside the wallet: `LanguageTray` ("ไทย or English through `setPreference`", plan line 1667) and the welcome's language switch (line 1668). A test there that taps English and expects English text will fail under `mountWallet` while the app works.

Fix: add one sentence to the harness header and to the receipt's notes: a language chosen inside the mount changes the preference, not the language drawn; to see English, mount with `locale: 'en'`. P2-T35's brief then chooses between asserting the preference and an opt-out for the pin.

But `CATALOGUE_SECTIONS` has `...COMPANION_SECTIONS` between them (lines 104 to 106). The header never mentioned the companion list, which joined in `b22c41c` (its sections are in the `Screens` group). So the old "comes last" was true, and the new "next" is one word off. Writing "comes after the companion's list", or adding one clause that names it, would fix it.
