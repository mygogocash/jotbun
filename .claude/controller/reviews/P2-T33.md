## Summary

The lock is built as the plan and the brief say, and I found no path that opens the app without a `success`:

- **The fail-closed rules hold.** An unread setting covers the app, and an unreadable one counts as on. A throwing prompt counts as `failed`, and a phone that cannot be read counts as still able to lock.
- **R67's answers are right.** The gate unlocks only on `success`, or when R67's re-read finds that the phone can no longer lock.
- **The cover carries the lock screen (P2).** All its copies share the gate's state and its one in-flight guard.
- **The catalogue list never reaches `expo-router`.**
- **The `index.ts` and `draftText.test.ts` merge proofs still hold** against P2-T14's live PR #407.

I found four minor issues and six nits. Two of the minors are risks that P2-T34 will expose once a real port can lock: Android's `background` during the gate's own prompt, and the first prompt's words at a cold start. With `noLocalAuth`, no person can turn the lock on today. The other two minors are a rare ordering in which an opening never asks by itself, and the turned-off notice's "no timeout" rule, which no test holds. None is a blocker or a major.

## Findings

### Blocker

None.

### Major

None.

### Minor

**m1. Android: a prompt whose own screen pauses the activity loses its answer and asks again, so a passcode entry there never unlocks. This is a risk for P2-T34, not reachable today.**
- **The mechanism.** React Native 0.88 on Android sends `background` from every `onHostPause` and never sends `inactive` (`node_modules/react-native/ReactAndroid/.../appstate/AppStateModule.kt:41-48`). The gate treats every `background` as a new opening (`LockGate.tsx:162-165`) and drops the in-flight prompt's answer (`LockGate.tsx:243`). On `active`, the new opening asks again (`LockGate.tsx:254-258`).
- **When it bites.** Any Android flow that shows the prompt's UI as an activity hits this. I could not verify this on a device. My understanding is that the device-credential (passcode) screen is an activity on Android 10 and earlier, and on a phone with only a passcode.
- **The effect.** A correct passcode is dropped, and the prompt comes back. A biometric lockout says "use the passcode", which is then a dead end.
- **Evidence.** Probe B sends `background`, then the prompt's `success`, then `active`. The app stays locked, and a second prompt is asked (`{ lockedAfterSuccess: true, askedAgain: 2 }`).
- **Why minor.** This is the plan's W18 rule ("background covers and locks") plus the brief's drop rule, which the controller endorses. iOS is fine, since its prompt only makes the app `inactive`. Nothing can turn the lock on until P2-T34.
- **What it needs.** A decision with a phone in hand. Either a `background`/`active` pair that arrives while the gate's own prompt is in flight belongs to that prompt on Android, or the adapter avoids an activity-based credential UI. P19's device list should name this check (see the notes).

**m2. A cold start can ask with the passcode's words on a Face ID or fingerprint phone.**
- **The cause.**
  - The setting read and the phone read start together.
  - When the stored setting answers first, `unlock` builds the prompt from `namedMethod(known.current)` while `known` is still null (`LockGate.tsx:239`, `lockModel.ts:98-100`). So it asks with `lock.linePasscode`: ใส่รหัสผ่านของเครื่องเพื่อเปิดบันทึกของคุณ.
  - The locked screen first draws ปลดล็อกด้วย รหัสผ่าน with no passcode link, then switches to Face ID when the phone answers.
- **Evidence.** Probe C's phone answers after the setting. The prompts are `["ใส่รหัสผ่านของเครื่องเพื่อเปิดบันทึกของคุณ"]`, and the first buttons are `["ปลดล็อกด้วย รหัสผ่าน"]`. After the phone answers they are `["ปลดล็อกด้วย Face ID", "ใช้รหัสผ่าน"]`.
- **Who sees it.** On Android, `promptMessage` is the BiometricPrompt's title, so a fingerprint user reads "enter your phone's passcode". On a real phone, AsyncStorage's single read can easily beat P2-T34's two local-auth reads.
- **The fix.** Hold the first automatic ask until the first phone read has settled. A failed read still asks, with the passcode's words.

**m3. Back in front before an earlier prompt answers: the new opening never asks by itself.**
- **The cause.** The automatic ask marks the opening as asked (`asked.current = opening.current`) even when `unlock` returns early because a prompt is still in flight (`LockGate.tsx:235`, `LockGate.tsx:255-257`). When the late answer is then dropped, nothing asks again until the next trip to the background. The brief's P5 says every return from the background asks once by itself.
- **The effect.** It fails closed. The person sees the locked screen with no prompt and no note, and must press the button.
- **Evidence.**
  - Probe A sends `background` and `active`, then answers the first prompt. It gets one prompt where two are expected.
  - Probe F shows the same with the setup switch's prompt: after the trip away, the app stays locked even though the switch then turned the lock off.
- **The fix.** Let the effect wait while a prompt is up, and only mark an opening as asked when a prompt actually starts. For example, add `busy` to the effect's condition and dependencies. The existing G6 and G34 cases keep the loop guards.

**m4. Nothing holds the turned-off notice's "no timeout" (P6, §4).**
- The code is right, but my mutant M1 survived. It adds `setTimeout(() => setTurnedOff(false), 3000)` in `turnOff`, and all 24 cases still pass (`my-mutant-logs/M1.log`).
- The controller's focus 4 names this rule, and the protocol's mutation step asks for a test for every survivor.
- **The fix.** A case with fake timers: after the lock turns itself off, advance well past any plausible toast time (for example 60 s), and the notice is still there.

### Nit

- **n1. "An app launched behind waits" (P5) has no case.** My mutant M4 (`useState(true)` for `front`) survived. happy-dom's AppState always reads `active` at mount. A case that stubs `AppState.currentState` to `background` before mounting would hold it.
- **n2. The route `app/settings/lock.tsx` has no test.** No render file imports it. `AccountRoutes.render.test.tsx` imports `settings/_layout`, `index` and `privacy` only. M6 (no `Redirect` while the area is off) and M7 (`?setup=1` ignored) both survived. `typecheck:routes` checks only its types.
- **n3. `change()`'s same-state guard has no case.** In `if (asking.current || on === enabled.current) return;` (`LockGate.tsx:261`), dropping the second half (M2) survives. Its only cost would be a redundant prompt.
- **n4. `unlock` resets `asking` only on its normal path (`LockGate.tsx:236-242`).**
  - An answer outside `AuthResult` makes `afterAnswer` return `undefined`, and `answer.step` then throws. That leaves `asking.current` true for good, and every press asks nothing.
  - Probe H shows it: one prompt, then a dead button, still locked. This fails closed, but it is a dead end.
  - A `try/finally` would remove it. P2-T34's mapping must also stay total ("every other code is `failed`").
- **n5. A vacuous assertion.** `Lock.render.test.tsx:210`, `expect(screen.queryByRole('heading', { name: '฿12,480' })).toBeNull()`, can never fail: `Below` draws no heading. The real check is `unseen(below)` on the line above.
- **n6. A store that cannot be read gives a false "turned off" notice.**
  - With `noLocalAuth`, an unreadable setting counts as on, then `unavailable`, then `canLock: false`. The person is told the lock was turned off because the phone no longer has a passcode, though it was never on.
  - On a browser that blocks storage, AsyncStorage's web `getItem` rejects at every launch, so the notice comes back each time.
  - This is an edge case: such a browser can barely run the app anyway.
