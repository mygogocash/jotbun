### Minor

**m1. A salt fetch still in flight during the sign-out erase writes the salt back after the erase deleted it** (privacy lens, PV1).
- Where: the hasher's load, `slipRefs.ts:97-103` (read, `salt()`, write), checks for neither an erase nor a session change.
- Why the transport does not catch it:
  - The session epoch moves only when `services.signOut()` runs (`credentialProvider.ts:296-298`, `signOutFlow`).
  - `SettingsScreen.tsx:200-211` calls that after `diary.eraseForSignOut()` (`spendDiary.ts:308-313`, which calls `eraseWithDiary`, `DeviceDiaryProvider.tsx:70`).
  - So a salt answer that arrives during the erase is still current for the transport's `stillCurrent()` check (`client.ts:332-391`).
- Probe `privacy/privacyProbe.test.ts`, case P4 (rerun in `synth/`): start a load, run `store.forget(A)`, then deliver the answer. `jotbun.slip-salt.<A>` is back in the keychain. Against S16 (plan line 39: kept "until the sign-out erase").
- Not reachable in this PR: no app code builds a hasher yet.
- **Carrier: P4-T14.** Its `beforeErase` and `dropSlipEngines` (plan lines 777, 802) must wait for each engine's in-flight hash, or give the hasher a drop that skips its write, before `eraseWithDiary` deletes the salt. P4-T16b's single-read hasher needs the same.

**m2. The hasher keeps whatever salt the server returns, under the account it was built for, for as long as it lives** (privacy lens, PV2).
- Where: `slipRefs.ts:95-112`.
  - `createSlipHasher` fixes `accountId` when it is made.
  - It writes whatever `resources.salt()` returns under `jotbun.slip-salt.<accountId>` and holds it in memory.
  - That call goes over the shared transport, which answers for whichever session is current. `SlipSaltDto` names no account (`packages/contracts/src/v1/slips.ts:89`), and the salt never rotates, so nothing ever re-checks it.
- Probes (`privacyProbe.test.ts`, rerun in `synth/`):
  - P3, right: the transport drops an answer to a request sent under an older epoch (`SESSION_CHANGED`, nothing kept).
  - P5, the gap: a hasher for A called after the session moved to B stores B's salt under A's key, and a later hasher for A uses it without fetching.
  - P8: a hasher still held after the erase keeps hashing with A's salt.
- The receipt's note ("one hasher per signed-in account") states the rule, but nothing in the core enforces it.
- **Carrier: P4-T14.** `appSlipDeps`, `slipEngineFor` and `SlipsProvider` (plan lines 800 to 802, 814) must build the hasher for the open diary's account and never call an old hasher once the session or the diary moves, with a test for it.

**m3. The slip read accepts an answer that is not about the batch it sent** (contract lens, C2).
- Where: `slipResources.ts:87` checks only `isSlipBatchResult`. P4-T6 answers with one result per slip, in the request's order (plan line 445, handler step 6).
- Probe `contract/tree/apps/app/src/slips/review-probes/read-answer-correlation.test.ts` (rerun in `synth/`, same result): for a batch of hashes A and B, the client accepts `[]`, `[A]`, `[A, C]`, `[A, B, C]` and `[B, A]`.
- Brief P3 holds every other answer to what it named: an ack to its command and entity, the account update to its account (mutant R19). The read has no such check. `sharedSlipResources.render.test.tsx:23` even answers `results: []` to a one-slip batch.
- Consequence once P4-T14 maps outcomes by index: a short or reordered answer marks the wrong photo as known, and that slip is never sent.
- **Carrier: P4-T14** (match results to the batch by `ref_hash`, and treat a slip with no result as paused), or a follow-up that adds the length and order check to `read`'s `validate`. The second puts the rule at the boundary, where P3 puts the others.

## What was checked and found right

**1. The wire contract** (contract lens, `contract/`).
- Method, path and query of all twelve calls match P4-T2 (plan line 204), P4-T3 (283 to 285), P4-T5 (386), P4-T6 (444) and P4-T7 (507 to 511). No slip path collides with an existing edge or API route.
- Headers:
  - `application/json` on every JSON body, `application/octet-stream` on the batch, no `Content-Type` on a GET.
  - `Idempotency-Key` and `X-GoGoSpend-Command-Schema: 1` go only on confirm, dismiss and the account update.
  - `If-Match` goes only on the update, as `"<n>"` (`commandHeaders`' `IF_MATCH`). Confirm and dismiss send none, as P4-T7's `forbidden` rule requires.
- Bodies match the parsers the routes run: confirm `{ drafts }`, dismiss `{}` (as archive and restore), the update `{ wallet_id }`, refs `{ ref_hash, transaction_id }`, devices the `DeviceRegistration`.
- Acks: `inboxAck` (`slipResources.ts:68-69`) requires the caller's `command_id` and `entity_id` `SLIP_INBOX_ID`. That is exactly what `runCommand` acknowledges for P4-T7's payload.
- The account update: a new UUID command, used only to carry `If-Match`. The answer must be the account it named (`:107`, mutant R19). A 409 `VERSION_CONFLICT` reaches the caller with `current` (test case 3). The UUID pattern is lowercase only, so the id comparison cannot fail on case.
- `recordRef` and `registerDevice`: no command. The edge writes no body for a 204, the transport reads it as null, and any body is refused (R21).
- The read: no command, so `client.ts:375` never resends it; a dropped connection is one fetch; `timeoutMs` is 90,000. The 401-refresh resend can happen only before the handler runs, because `authenticate` comes before `runWorker` in `handler.ts`.
- R102: `readJsonBody` parses only `application/json`, so an octet-stream body reaches a `body: 'stream'` route as `w.stream`. The bytes sent equal `slipBatchBytes` (m6's probe). The array starts at offset 0, and its buffer holds exactly the body. P4-T6's note is in followups.md ("P4-T12 planner notes").
- UUID guards (P5): `dismiss` and `updateAccount` refuse a non-UUID id with `INVALID_ID` and send nothing, before expo-crypto loads. These are the only ids in paths.
- The fake's four brief rules hold (m4 is about everything beyond them):
  - with slip import closed, exactly the six calls behind the release flag answer 404, while the salt, refs, albums and devices answer;
  - a confirm naming a gone draft is 409 and takes nothing out; a dismiss of a gone draft is 404;
  - the update is 404 for an unknown id and 409 with `current` for a stale version, and moves the version by one;
  - its acks pass `isCommandAck` with P4-T7's outcomes, and `FAKE_SLIP_SALT` passes `isSlipSaltDto`.

**2. Privacy and the keychain** (privacy lens, `privacy/`).
- The salt store: one item per account, `jotbun.slip-salt.<id>`, holding 64 lowercase hex digits. `keychainAccessible: WHEN_UNLOCKED_THIS_DEVICE_ONLY`, plus `accessGroup` when one is given, sit in one options object for get, set and delete (`slipRefs.ts:45`). The option names match expo-secure-store 58.0.2 (the planner's H1, the class weakened to `WHEN_UNLOCKED`, is killed). A kept value that is not a salt reads as none. A read rejects while the iOS keychain is locked.
- The hasher:
  - it normalizes before asking for any salt (P-X3 killed);
  - the base64url salt is decoded with the padding added back (probe P2: 200 random salts, exact under a strict `atob`);
  - the digest gets a fresh copy (`:77`);
  - one load serves every hash, concurrent ones included, and a failed load is not held (probe P6);
  - a locked keychain fetches nothing (the planner's H13, rerun and killed).
- The plan's vector `c4f3b6c8f15a0e588cfdb0a59d02f281e28eae69f0a3f8b22d6bda69f7ec1493` matches an independent computation from P3-T1's `004` slip, with no app code (probe P1).
- Account switch: a salt request in flight when the session epoch moves is dropped by the shared transport with `SESSION_CHANGED`, and nothing is kept (probe P3, on the real `createV1Transport`). One salt shared by every hasher (P-X7) is killed.
