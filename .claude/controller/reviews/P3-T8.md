## The controller's focus, point by point

### Refunds and billing (P11)

- **`giveBack` before the 503:**
  - `service.ts:162-165` logs, awaits `giveBack(s, use, trace)`, then throws `paused()`.
  - `giveBack` refunds only when `shouldRefund(trace.calls, false)` holds (`service.ts:302`): the request's last recorded call failed with `rate_limited`, `server_error`, `timeout` or `no_connection` (`uses.ts:8-19`).
- **A 400 spends the use:** `callFailure` reads it as `rejected` (`transport.ts:88-91`), which `GIVES_BACK` leaves out. Pinned through the route (`slip-read.test.ts:286`: 503, Haiku only, `remaining.slip` 9) and directly (`:463`, `failure: 'rejected'`).
- **Does any path refund a use after a billed call that should spend? No path refunds where the plan says spend.** Every refund that follows a call Anthropic may bill is one the plan prescribes:
  1. **Haiku cut at its 20 s cap.** Haiku's call is sent and cut, so its outcome is `failed` (timeout) and the read throws `SlipNotRead` (`slip-read.ts:89`). The use is refunded and Opus is not asked (H7).
  2. **Haiku answered with nothing usable, then Opus failed.** Haiku declined, answered unusably or found no draft; Opus then failed with a 429, a 5xx, a timeout or no connection. The read throws `SlipNotRead(opus.failure)` (`slip-read.ts:95`) and the use is refunded.
     - Review Focus 3 prescribes this for a decline and an unusable answer; the plan's Interfaces ("else `unreadable` when Opus answered, or `SlipNotRead`") prescribe it for an answer with no draft.
     - When Opus timed out after its request went out, that is two calls Anthropic may bill for one use given back (n3).
  3. **The same, with Opus never sent.** The 2 s floor stops the Opus call, which takes more than 23 s of vault steps (45 - 20 - 2). The use is refunded after one billed Haiku call.
     - This is the shape of R116, which is Ask Bun's ruling. P18 leaves the slip's `shouldRefund` unchanged, and that holds up: a slip has no person-paced turns before Opus.
     - Probe PF pins the read's side: `SlipNotRead('timeout')`, with the Opus call recorded `sent: false`.
  - Where Haiku had a draft, an Opus failure spends the use and shows Haiku's draft (A14; `slip-read.ts:94`; pinned at `slip-read.test.ts:239`).
- **The Haiku read past `HAIKU_SLIP_CAP_MS`: an acceptable known risk under the owner's refund-caps item, not a defect of this task.**
  - H3 and P3-T6's 20 s constant set the cap; H5 gives a timeout's use back; H7 says "an outage (429, 5xx, timeout) never escalates, for slips too". The receipt states the risk, as the P3-T7 carry asked.
  - Two things the owner item should weigh:
    - the cap turns a slow but working Haiku read (20 to 43 s) into a refunded 503 with about 25 s left, where before this task Haiku had the whole 45 s;
    - refunds are uncapped, so photos that reliably take Haiku past 20 s (a long receipt) can be retried as billed reads that never spend a use.
  - The owner's refund cap (per feature per account per day, or counting sent timeouts toward P4's per-account cap) is the right guard. P3-T22 should measure Haiku's slip latency against the cap.
- **One request refunds once, on every route.**
  - `service.ts:164` is the slip route's only refund. `readSlipImage` neither counts nor refunds a use (its header, `slip-read.ts:14-20`, and no vault step in the module).
  - `ai-uses.test.ts:230` pins it on all four routes with seeded rows. M6, re-run: killed.
- **A refund the vault fails never changes the 503 and is logged before the answer.**
  - `giveBack` catches the failure and logs `ai_refund_failed` by class name (`service.ts:303-307`), and it is awaited before the throw.
  - `ai-uses.test.ts:207` pins it through this task's new path (a Haiku decline, then an Opus 529), reading the log as soon as the answer arrives. RV5, re-run: killed.
