**m2. Google's own SDK keeps the person's Google sign-in, its ID token included, on the phone after every Google sign-in and after a sign-out of Jotbun: nothing calls `GoogleSignin.signOut()`.**

- 16.1.5 keeps the signed-in user so that `signInSilently`, `hasPreviousSignIn` and `getCurrentUser` work across launches (`src/signIn/GoogleSignin.ts:128-139` answers `noSavedCredentialFound` only when nothing is saved; `:149-155`), and its `User` carries `idToken` (`src/types.ts:106-119`). Only `signOut()` or `revokeAccess()` clears it (`:141-147`). `nativeModules.ts` uses only `configure`, `hasPlayServices` and `signIn`.
- So once Google is on, the Google ID token reaches storage beyond what 1C-T5's port keeps (the SDK's own store), against P12 as the controller words it, and it outlives a sign-out of Jotbun.
- The same saved state is the likely answer to P15's open question about a second sign-in. 16.1.5's Android `signIn` starts the legacy `GoogleSignInClient.getSignInIntent()` (`android/.../RNGoogleSigninModule.java:177-194`), which is widely reported to hand back the saved account without the chooser until `signOut()`. Then a person who signed out of Jotbun could not pick another Google account.
- Not live in this build: the ids are unset, so Google is never offered and its module never loads.
- Fix, before the owner sets the ids: in `nativeModules.ts`, sign out of Google's SDK right after a successful `signIn()` has given the token (through the same memoized loader; a failed sign-out should not fail the sign-in), and pin it in the render test (the fake records `google:signOut` after `google:signIn`). The device check then confirms the chooser shows on a second sign-in.

**m3. The nonce's last hop to Better Auth is unpinned.**

- `betterAuthClient.ts:41-47` (`idTokenOf`, 1C-T5's code) is the only place the nonce goes to Better Auth's client. No test runner can load that file (P10), and the source case pins only the wiring (`nativeSignIn.test.ts:249-256`).
- Better Auth checks Apple's nonce only when one is sent: `@better-auth/core` `dist/social-providers/apple.mjs:69`, `if (nonce && !await nonceMatches(jwtClaims.nonce, nonce)) return false`. Dropping it would keep Apple sign-in working and silently lose the replay check P8 exists for.
- R6 (the nonce spread deleted from `idTokenOf`) survives all 43 focused cases.
- Fix (ready): the third case of `probes/reviewProbePrivacy.test.ts`, a source pin in P10's style, kills R6. Better: 1C-T13, which works on this path for the authorization code, moves `idTokenOf` where Node can load it and tests it.

**m4. On iOS, Google can be offered without its URL scheme, and a release build then ends the app when the person taps it.**

- The app offers Google on iOS from two variables (`nativeSignIn.ts:76-77`, `env.ts:11-13`). The URL scheme comes from a third, which only `app.config.js:11-12` reads, at native build time. Nothing ties them together (the plan's design, M18).
- GoogleSignIn-iOS raises an exception when the reversed client id is not a registered URL scheme. 16.1.5 calls its sign-in inside `dispatch_async` on the main queue and catches that exception only `#if DEBUG` (`ios/RNGoogleSignin.mm:126-146`; its own message names "Your app is missing support for the following URL schemes..."). In a release build the exception is uncaught and the app terminates; in a development build the sign-in only rejects.
- So Q1's development-build check cannot see this mistake: the same configuration fails gently in the development client and crashes in TestFlight. It would also follow a JS update that sets the ids for a binary built without the scheme.
- Not live in this build: all three variables are unset.
- Options, each a change to the plan's text and so the controller's or the owner's call: derive the scheme in `app.config.js` from `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` (one source of truth), or also require the scheme before Google is offered on iOS. At the least, D33 sets all three together, with the scheme equal to the iOS client id reversed, and tries Google once in a release build.

### Nits

**n1. "Google's module never loads at launch" is pinned only inside `nativeModules.ts`.** N10 and N15 pin that file. A static import of Google's package added anywhere else on the launch path (`betterAuthClient.ts`, `appAuth.ts`) passes every focused test (my R5): the render suite resolves `betterAuthClient.web.ts`, Node cannot load `betterAuthClient.ts`, and the source case checks only that two lines are present. That is the likeliest next edit if m2 is fixed outside `nativeModules.ts`. The second case of `probes/reviewProbePrivacy.test.ts` (only `nativeModules.ts` names the package, and only through `import(`) kills R5.

**n2. The receipt leaves out three things the brief asked for or the controller asked about.**

- Brief Step 6.6, "The receipt records both lists": the receipt names the planner's files instead (`receipts/1C-T7.md:37`).
- P15's consequence: the Google package is autolinked into every native build, so if the development build fails on it, leaving the ids unset is not enough (the plan's Step 6 says it is). The receipt's SKIPPED line (`:52`) does not say so.
- `CFBundleAllowMixedLocalizations: true`, from Apple's config plugin, is app-wide: every system sheet and permission prompt follows the phone's language from now on. That is probably what a Thai-first app wants, but it is not a sign-in-only change.

**n3. A new import cycle, `betterAuthPort.ts` and `nativeSignIn.ts` (P11).** It is safe, since each uses the other's exports only inside functions, and Babel keeps local imports eager (`babel-preset-expo/build/configs/module-transforms.js:38-50`), so it is walked at launch. Expo's development runtime then prints "Require cycle: ..." (`@expo/cli/build/metro-require/require.js:106-111`): its ignore list defaults to `node_modules` only (`:119-131`, `metro-config/src/defaults/index.js:72`), and the app has no `metro.config.js`. Moving `AuthCancelled` and `AuthRefused` (or `idTokenSubject`) into a module of their own would end it; that touches 1C-T5's files, so later.

**n4. "A build made without the package still starts" (`nativeModules.ts:10-11`) and P15's "The JavaScript needs nothing" hold for a build without Google's native half, not for one without the npm package.** They are right for a development client built before this change or a build that excludes the package from autolinking. Metro resolves `import()` targets when it bundles, and `tsc` reads the `typeof import(...)` type (`nativeModules.ts:20, 34`), so removing the package also needs Google's loader removed. Worth saying in the owner question P15 raises.

**n5. P15's device check expects "an iPhone without an Apple ID (a refusal)".** On iOS, `isAvailableAsync()` always answers true (`expo-apple-authentication/ios/AppleAuthenticationModule.swift:12-14`). The refusal branch fires only where Apple's native half is missing, such as a development client built before this change: the JS fallback module answers false (`build/ExpoAppleAuthentication.js`). An iPhone without an Apple ID goes on to Apple's own sheet, and the outcome is Apple's error code: `AuthCancelled` for `ERR_REQUEST_CANCELED`, a failed sign-in otherwise. Expect that at the device check.

## Focus items

### 1. Tokens, nonce and code (P8, P12)

- By reading: nothing under `src/auth` (`betterAuthPort`, `credentialProvider`, `betterAuthClient`, `appAuth`, `nativeModules`, `nativeSignIn`) calls `console`, analytics or a crash reporter. `nativeSignIn.ts` and `nativeModules.ts` keep nothing but the two client ids (`settings`) and the module's promise. The token, the nonce and the code go only to the port. `idTokenOf` sends `token` and `nonce` and drops the code until 1C-T13. Better Auth's Expo client keeps only the session cookie and the `/get-session` answer in SecureStore (`@better-auth/expo/dist/client.js:265-266, 324-338`), never the request body that carries the ID token.
- One fresh nonce per Apple sign-in: `nativeSignIn.ts:60` draws it inside the returned function, after the availability check, and the same variable goes to `signInAsync` (`:63`) and back in both returns (`:69-70`).
  - expo-apple-authentication passes it to Apple unchanged (`ios/AppleAuthenticationRequest.swift:37`), so the token's claim is the raw UUID, which M13's raw match accepts.
  - The source is expo-crypto's `Crypto.randomUUID()` (`nativeModules.ts:64`), which the Hermes guard allows (my run: 1 of 1).
  - A5 and A6, N6 and N8 pin it (A5 in my sample).
- The gaps are m1, m2 and m3.

### 2. Apple (P5)

- iOS only, and only with its module (`nativeSignIn.ts:57`): A1 and A2 killed (A1 in my sample).
- `isAvailableAsync()` false gives `AuthRefused('REFUSED')` before any nonce or sheet (`:59`); its case asserts the sheet was never asked. Where the native half is missing, Expo's JS fallback module answers false; on iOS the real module always answers true (n5).
- The email scope only: `[apple.EMAIL_SCOPE]`, which is `AppleAuthenticationScope.EMAIL` = 1 in 58.0.2 (`build/AppleAuthentication.types.js:12-13`). A8 and N7 pin it.
- A closed sheet is `AuthCancelled`. `ERR_REQUEST_CANCELED` is ExpoModulesCore's code for `RequestCanceledException`, which 58.0.2 raises for `ASAuthorizationError.canceled` (`ios/AppleAuthenticationExceptions.swift:16-20, 68`), as `signInAsync`'s docs say (`build/AppleAuthentication.js:31`). Any other failure passes through (A12 and A13 killed, A13 in my sample).
- The null-token refusal is defensive, as P5 says: `signInAsync` already throws `ERR_REQUEST_FAILED` when the token, the code or the user is missing (`build/AppleAuthentication.js:42-44`).
- Importing Apple's module at launch is safe everywhere. It loads through `requireOptionalNativeModule` with a pretend module, and its button's `requireNativeView` (iOS only) reads the view config lazily and only warns when it is missing (`expo-modules-core/src/NativeViewManagerAdapter.native.tsx:60-70`).
