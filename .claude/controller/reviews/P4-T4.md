### Minor

- **m1. Two of the sanitizer's stated rules have no case that holds them.** The code is right; a later edit could drop either and all 48 cases would still pass.
  - **The time's start anchor** (`slip-import.ts:74`, the plan's `/^([01][0-9]|2[0-3]):[0-5][0-9]$/`): my mutant R1 drops `^` and the file passes `48 passed (48)`. The time table (`slip-read-import.test.ts:418-430`) has no value with text before a valid time, so "at 18:40", "เวลา 18:40" or "118:40" would be kept whole as `occurred_time`. P4-T3's `slip_drafts` CHECK (`0006_slips.sql:28`: length 5 and `[0-2][0-9]:[0-5][0-9]`) would then refuse that row at P4-T6's write, instead of the sanitizer dropping the time.
  - **The dot in the long-number rule** (`slip-import.ts:82`, `[ .-]`; ruling P7: "a single space, dot or dash between two digits does not break the row"): my mutant R3 drops the dot and the file passes `48 passed (48)`. The name table (`:454-477`) has a space row and a dash row but no dot row, so "ร้าน 081.234.5678" would keep its phone number.
  - **The fix (test only):** add `['118:40', null]` and `['at 18:40', null]` to the time table, and `['ร้าน 081.234.5678', null]` to the name table. Probe G holds all three on the code as it is.

### Nits

- **n1. No case shows a flagged read leaving `readSlipImage`.** Every flow case shows `flags: []`; only the sanitizer's own table sees `amount_unclear` and `date_guessed`. My mutant R4 (`slip-read.ts:138`, `import: { ...read, flags: [] }`) passes `48 passed (48)`. The receipt's note for P3-T22 and P4-T23 ("an import read that ended without a day carries `date_guessed`") rests on that pass-through. Probe H holds it: a Haiku read with no amount and a Buddhist-era day, kept after Opus could not start (21.999 s), shows `import.flags` as `['amount_unclear', 'date_guessed']`. One flow row would pin it, for example the 21.999 s deadline row with Haiku missing its amount instead of the receiver's name.
- **n2. `SlipNotRead`'s default wait is unpinned.** The plan says "default null" (`slip-read.ts:53`). All four throw sites pass `lastWait`, so my mutant R5 (a default of 30) passes all 48 and is equivalent today; P4-T6's fakes may build `new SlipNotRead('rate_limited')` and read its wait. One line pins it (probe H): `expect(new SlipNotRead('timeout').retryAfterSeconds).toBeNull()`.
- **n3. The long-number rule, beyond the plan, still lets common separators through, and the module's header overstates it.** The plan's rule ("seven or more digits in a row") holds, and ruling P7 widens it to one space, dot or dash. Probe G shows a full ten-digit phone number kept in a name when it is split by an en dash (U+2013), a no-break space, a slash, a spaced dash (`081 - 234 - 5678`) or two spaces. Names also keep six digits in a row by design (a branch code). Yet `slip-import.ts:6-8` says an import read holds "never ... more than four digits of any number". A name stays in the vault's draft columns, so this is data minimisation, not an anti-goal breach. Either widen the rule, for example `/\p{Nd}(?:[\p{Zs}\p{Pd}./]{0,3}\p{Nd}){6,}/u` (checked: it drops all nine phone-number spellings above and keeps "ร้าน 7-11 สาขา 123456" and "นาย กานต์ ใจดี"), or reword the header to say what the rule does, or record it as accepted.
