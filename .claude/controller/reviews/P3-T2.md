## 1. The migration (P1, P2, B2)

- `0005_transaction_source.sql` is one `ALTER TABLE transactions ADD COLUMN source TEXT CHECK (source IN (<the seven>))`. No rebuild, so neither child action fires: `transaction_attachments` (`ON DELETE CASCADE`, `0001_vault_files.sql:293`) and `import_row_progress` (`ON DELETE SET NULL`, line 238). `transactions` is `STRICT`, and TEXT is a valid strict type.
- Journal: idx 5, tag `0005_transaction_source`, `when` 1761782400000, one day after 0004's 1761696000000; `m0005` is registered. `vault-schema.test.ts` pins the tags, the idx order, the keys and an increasing `when` (M11 killed).
- A vault that slept through it: `a vault the previous release wrote gains the column in place` seeds a 0004-shaped vault (two records, an import link, a receipt link), wakes it, and compares rowids, every column, both link sets, the `attachment_checks` count and `PRAGMA foreign_key_check`, then wakes it again. M10 (a rebuild's cascade, simulated) is killed.
- Older records stay NULL: the same case expects every old row to gain `source: null`, and `a row without a source reads as before, with its receipt link` reads one without the key, its `attachment_id` intact.
- The CHECK on existing rows: SQLite (3.37 and later) tests an added CHECK against every existing row when it adds the column. The new column is NULL on each, and `NULL IN (...)` is NULL, which a CHECK lets through. My probe in workerd: `ADD COLUMN ... CHECK` on a table with rows is ok; the same with `DEFAULT 'manual'` fails "CHECK constraint failed"; with `DEFAULT 'manual'` on an empty table it is ok. So workerd does check existing rows, and the shipped NULL-default column passes. (workerd's authorizer refuses `sqlite_version()`, so the version is read from that behaviour.)
- The previous release's statements still run: they never name `source` (the spec's rule that a migration stays readable by the previous release holds).

## 2. Set once (H9, P6)

## 3. Idempotency (P7)

The digested payload is `draft` when the source is absent or null, else `{ ...draft, source }` (`transactions.ts:258`). The case `a create without a source is digested as the release before gave it` checks that the stored digest equals `CommandDigester`'s digest of the pre-P3 payload (the same ten fields), so a create queued before P3 replays. My replay probe: made without a source, a replay with `source: null` returns the same 201 body and one naming `typed` is 409 `IDEMPOTENCY_MISMATCH`; made with `photo`, the same body replays, and both no key and `null` are 409. My R6 (digest a null but not an absent key) is killed by the absent-then-null replay in the 409 case.

## Notes for later tasks

- **Phone senders (P3-T13, T17, T18; P6A's Siri and share):** put `source` in a create only with a value, and leave the key out for none. The outbox accepts `null` but `CreateEntryInput` does not, and the vault never answers with `null`; the app's fake sync server copies a create's payload into its snapshot (`apps/app/src/sync/testing/fakeServer.ts:64`), so a queued `source: null` there becomes a snapshot that `isTransactionSnapshot` refuses.
- **`editPending`** (`diaryRepository.ts:467`) replaces an unsent draft whole and accepts any source. The first task that edits a queued draft keeps its source (H9: a Tell Bun draft edited before it is sent stays `tell_bun`).
- **Imports:** today an import's records have no source; P4-T11 sets `statement` in `confirmation.ts`, and P4's slip confirmation sets `slip_import` or `share_extension`.
- **Release (P6C):** raise the client minimum to at least 0.2.0 in the release whose app first sends a source (C5), and deploy the vault before that build. A vault rolled back below P3-T2 answers a queued create naming a source with 422 `UNKNOWN_FIELD`.
- **The seven are fixed in the table:** SQLite changes a CHECK only by rebuilding the table, and the plan never rebuilds `transactions` (the rebuild's drop would delete receipt links and clear import links). An eighth source would need a rebuild that carries `transaction_attachments` and `import_row_progress` across, or a new column: an owner call before anyone plans one.
- **Shared tests:** `vault-schema.test.ts` now pins the full tag list (each later vault migration adds its tag), and `currency-migration.test.ts` requires every key to `wallets`, a later migration's too (P4's `slip_accounts`), to be `ON DELETE NO ACTION`.
- **Index name:** `transactions_source_idx` is already `source_wallet_id`'s (`0000_vault_core.sql:151`); an index on the new column needs another name.
