## Summary

- **How it works:**
  - A use is still counted before the first call, and `ai.consume` now answers the Bangkok day it counted, on the vault's clock.
  - Each route's catch path asks `shouldRefund(trace.calls, false)`. For a rate limit, a 5xx, a timeout or no connection, it calls the new `ai.refund` step with that day before it answers.
  - A decline, an unusable or ungrounded answer, a 400 and any other failure spend the use.
- **Who can refund:** only the service. `ai.refund` is a step id with no HTTP route (pinned by `route-coverage.test.ts`; my RV3 is killed). One request refunds at most once, and a day's count never goes below zero.
- **Gaming:** a phone that hangs up cannot cut the model call short.
  - In workerd the call ran on to the server's own deadline after a hang-up at 600 ms: through Miniflare's proxy and on workerd's own socket, with and without a pending `waitUntil` (probes C to J).
  - Every `AbortError` on the model call comes from the SDK's own timer or the call's `AbortSignal.timeout`.
  - What a person can do is make the model slow. That is H5's accepted risk, plus one variant the receipt does not record (m2).
- **The day:** the refund takes the day `ai.consume` answered, across midnight and with two requests in flight (the committed cases, and my PR1 and PR2).
- **P9 in workerd:** a stalled body rejects there with a DOMException named `AbortError`, which now reads as `timeout` (probes B and G). The receipt left this to P6C's hosted test; local workerd agrees.
- **The kit:** all 12 files are byte-identical to the planner's `real/`. The receipt's RED, GREEN and mutant counts match the implementer's logs.
- **CI:** all nine jobs pass on attempt 1.
- **Findings:** no blocker and no major.
  - Two minors. m1: Ask Bun's 503 refund has no case (one case fixes it). m2: a refund after billed Ask Bun turns, which the receipt's risk note does not cover.
  - One nit.

## The controller's focus, item by item

1. **Who can cause a refund (P2).**
   - **Reachability:**
     - `ai.refund` is only in `VAULT_STEP_ROUTES` (`v1/routes.ts:175`), with its handler at `vault/routes.ts:213-218`.
     - The front door matches only `VAULT_V1_ROUTES` (`handler.ts:104`) and calls only a matched route's `vault` id (`:142-144`). A Worker route reaches the vault only through its own handler.
     - The only caller of `ai.refund` is `VaultAiService.giveBack` (`service.ts:304-311`), and no app file names it.
     - `route-coverage.test.ts:142-145` pins that no step id is an HTTP route's vault call; RV3 (an HTTP route for it) is killed.
   - **One refund per request:**
     - The body comes from this request's own `ai.consume` reply (`service.ts:290-293`), never from the request.
     - Each catch calls `giveBack` once, and a catch runs at most once.
     - A use is refunded only after it was counted. Parse, slip and ask count it before their `try` (`:118`, `:144`, `:221`); the note refunds only when `use` was set (`:210`).
   - **Never below what was spent:**
     - `refundAi` (`vault/ai.ts:116-117`) is one `UPDATE ... AND uses > 0` on the `(day, feature)` key, so it never goes below zero. V2 is killed, and the table's CHECK holds it too.
     - With one refund per counted use, a day's count never falls below the uses its requests spent (PR1, PR2).
   - **What `anySession` skips:** only the session and policy checks.
     - The vault still refuses an erased vault and runs `ensureAccount` first (`user-vault.ts:196`, `:218-222`).
     - The refund is never a session's first call, so it is charged as a `step` and costs no budget.
     - S1 is killed.
2. **Can a person game the quota (P9).**
   - **The sources of an `AbortError` on the model call:**
     - The request's controller is aborted only by `_makeAbort` (`@anthropic-ai/sdk` 1.2.0, `client.ts:1744-1777`, `:2034`). It fires from the SDK's own timer before the headers, and from the caller's signal.
     - The SDK's other `abort()` calls are in its streaming code, and `linkAbort` is used only by its environments poller and session tool runner. Neither is on the path of a non-streaming `messages.create`.
     - The caller's signal is `AbortSignal.timeout(options.timeoutMs)` (`transport.ts:40`), the call's own time.
     - Nothing passes `request.signal` on (no use under `apps/edge/src`), and the AI routes hold no `waitUntil` while a call is out.
   - **The phone hanging up:** probes C to J.
     - After a hang-up at 600 ms, the model call stayed open and ended at the server's own 2.5 s deadline, exactly as for a phone that waited. The catch saw the same `timeout`.
     - In production, a hang-up may instead cancel the invocation (Cloudflare's Workers limits, as `files/slots.ts:11-16` records). Then no catch runs, and the use stays spent.
     - Either way, a hang-up cannot earn a refund that a waiting phone would not get.
   - **Any other client action:**
     - A person cannot abort a call. They can only try to make the model slow enough to reach the deadline, within the inputs' bounds: 200 characters to parse, 300 for a question, 1.2 MB for a slip.
     - A sent call that times out may already be billed, though its use comes back. That is H5 as written, and the receipt records it.
     - PR4 shows a variant the receipt does not record (m2).
3. **The day (P5).**
   - `consumeAi` answers `bangkokDate(c.now)` on the vault's clock (`vault/ai.ts:97`, `:108`).
   - The service keeps `{ feature, day }` from the step (`service.ts:290-293`).
   - The step refunds the body's day, after `parseAiDate` (`vault/routes.ts:213-218`). Nothing reads the Worker's clock or "today".
   - Pinned by the plan's direct case (`ai-uses.test.ts:128`), the front-door midnight case (`:156`), and V1, V5, R1, R2 and G8 (V1, R2 and G8 rerun here).
   - My PR2 adds two requests in flight across midnight, and PR1 two on one day.
4. **P3: a failed refund.**
   - `giveBack` catches every error from the step and logs `{ level: 'warn', event: 'ai_refund_failed', feature, failure: failureName(error) }` (`service.ts:309`).
   - `failureName` gives the class name (with only a safe `code`), never a message (`apps/api/src/common/operational-metrics.ts:76-87`). Nothing else in `giveBack` can throw.
   - It rightly does not go through the service's `logFailure` (`service.ts:334-337`), which rethrows a refusing problem: a 401 or 403 from the refund would then change the answer.
   - G6 and G7 are killed (G6 rerun here), and CI shows exactly the one expected line.
5. **P4: the catch paths.**
   - Every `tracedSend` sits inside a `try` whose `catch` calls `giveBack` after `logFailure` and before the answer:
     - parse (`:134`, then the rules);
     - slip (`:169`, then 503);
     - the note (`:210`, then the plain facts);
     - ask (`:264`, then the figures or 503).
   - A model failure never reaches `logFailure`'s rethrow, since no transport throws a `ProblemException`. The note's early `return plain` (`:207`) catches only problems, which are not model failures.
   - Every answer outside a catch follows a call that answered. Its last call's `failure` is null, so `shouldRefund` is false there.
   - I found no path in this task that ends without a model answer after a refundable failure and does not refund.
     - The known one is P3-T9's `askWithEscalation`, which the receipt carries.

### Minor

**m1. Ask Bun's 503 path gives the use back, but no case pins it (RV1 survives).**
- **Where:** `service.ts:262-266`. Ask Bun's only refund case (`ai-uses.test.ts:110`) fails the second turn after a figure, so that request answers from the figures.
- **Evidence:**
  - RV1 moves the refund inside `if (figures.length > 0)`, so an Ask Bun whose first call fails answers 503 with the use spent.
  - RV1 passes all 62 focused cases. `ai-routing.test.ts`'s hang case reaches this path but counts no uses.
- **Why it matters:**
  - Review Focus 2 says every AI route gives the use back when the model never answers. For Ask Bun, that is usually this path: a first-turn outage or hang.
  - P3-T9 rewrites exactly this catch into `askWithEscalation`'s `{ paused: true }`, and none of its planned cases counts uses there either.
- **Fix** (one case, test only): my PR3, "an Ask Bun whose first Haiku call fails is 503 AI_PAUSED and gives the use back".
  - `model.push(apiFailure(529))`; expect 503 `AI_PAUSED` and `remaining.ask` 20.
  - It passes on the commit and kills RV1.

**m2. A billed Ask Bun turn followed by a turn the deadline never lets start gives the use back, and the receipt's risk note does not cover it.**
- **Where:**
  - `tracedSend` records a call it never sends as `failure: 'timeout'` with `sent: false` (P3-T4, `transport.ts:154-169`).
  - `shouldRefund` reads only the last call's `failure` (`uses.ts:19`).
- **Evidence:** PR4.
  - The first turn answers `tool_use`: it was sent, so it is billed.
  - The second turn cannot start with under 2 s left.
  - The route answers from the figures, and `remaining.ask` is back to 20.
  - RV4 (a `sent: false` timeout spends) survives the 62 committed cases and is killed by PR4.
- **Reading:**
  - This is H5 as written ("its last call failed with ... a timeout"), so the code is right for this task.
  - But B5's words are "a failed model call", and here every call that ran answered.
  - The receipt's risk note ("a call that times out on the server may still be billed") covers only a call that was sent and then timed out.
  - In Ask Bun, a person can stretch a question over slow tool turns until the 25 s child deadline, and still get the use back.
  - The same reading applies on any route whose vault steps use up its time before the first call. There no call is billed, so the refund is plainly right.
- **Fix:** no code change in this PR.
  - Record it in the receipt's risk note.
  - Let the controller or P3-T9 decide whether a `no_answer` ended by `DeadlinePassed` after answered turns spends (like the turn limit) or refunds (as now).
  - PR4 is a ready case either way.

### Nit

**n1. The `await` before the answer is held only on parse, and only through log timing.**
- RV2 (parse's refund not awaited) is killed only because "a refund the vault fails..." reads the log right after the response.
- RV5 (the slip's) survives, and Ask Bun's and the note's would too: in the test isolate, the step lands before the next request either way.
- In production, work not awaited after the response may be cancelled, so the refund could be lost. The code awaits on every path, so nothing is wrong today.
- **Fix, if wanted:** a slip twin of the refund-failure case, with its log check right after the 503.
