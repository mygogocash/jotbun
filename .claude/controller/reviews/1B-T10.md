### 2. Confirmation correctness: holds

- **Batches of 500:** `parseConfirmBody` caps a batch at 500, and 501 rows answer 422. `a confirmation batch of 500 rows commits as one command under one revision` sees 500 records and 500 progress rows in one revision group of 501 changes. M2 (a command per row) fails 15 cases.
- **Idempotent steps:**
  - A replay with the same key returns the stored ack, and the outcome is read again from durable progress.
  - A resent receipt batch prepares nothing, because `prepareReceipt` finds the command in `command_receipts` and answers `none`.
  - Probe `P2`: a resend of a committed receipt batch after its selection went stale replays `[200, first body]` and keeps one published copy. The prepare step refuses, the command step replays, and that is the API's `receiptAllowed` contract.
  - Probe `C`: two receipt confirmations of one image row at once both answer 200, with one receipt, one published copy and one record.
- **Exact amounts:**
  - Candidates, frozen rows and records move as `INTEGER` inside SQL.
  - Corrections write `CAST(? AS INTEGER)` from `parseMinor(...).toString()`.
  - Totals and duplicate-advice keys leave SQLite as `CAST(... AS TEXT)`, and records come back through `COLUMNS` (`CAST(amount_minor AS TEXT)`).
  - The ported 5,000-row cases reconcile wallet and category totals with `BigInt`.
- **Partial failure:**
  - A batch is one `runCommand` inside one `transactionSync`, so any throw rolls back all of it. The over-budget batch case answers 413 with no receipt row, and smaller batches with new keys then save the rows.
  - A row that cannot be saved now is reported in `conflicted`, never written. The rest commit, and `remaining` lists what the next batch can take.
  - A copy the command did not use is released in `confirmRoute`'s `finally`. W1 and `a copy the confirmation did not use is due at once` pin this.
  - Probe `P4`: an unsupported schema with a receipt answers 422 `COMMAND_SCHEMA_UNSUPPORTED`. Its copy is `reserved` and due now, and nothing is saved, as P4 says.
- **Duplicates:** as in the API, duplicate advice is advice only. The record id is derived per import row, and any id already in `entity_heads` is conflicted, never rewritten. That includes a purged id and one a client created by hand. C27 and the ported "never written again" case pin it.
- **P1, the two steps:** reading the outcome inside the command's block cannot roll a fresh command back.
  - `confirmIn`'s `openSelection` has just checked the selection and its job in the same block.
  - The ack names the batch's selection.
  - A replay mutates nothing, so a 404 or 409 there only discards a read.
- **P2, `refused`:** the change is justified and every caller is safe.
  - Without it, a batch whose image row became savable between the steps would reach `ready(..., null)` and answer 422 `attachment_expired`. The API answers 503 with a one-second retry. C32 and W3 pin the difference.
  - `PreparedCopy` itself is unchanged. `ConfirmPrepared` widens only the confirmation's step.
  - `attachments.prepare` still answers `prepareReceipt`, which never answers `refused`, so `withReceipt` maps a value it cannot receive.
  - The one shared loop now sends `params: {}` where it sent none. `vaultSession.call` already defaulted to `{}`, so nothing changes.
  - The only users of these types are `receipts.ts`, `confirmation.ts`, `attachments.ts` and `vault/routes.ts` (grep).
  - All 52 of 1B-T9's cases pass, in my run and in CI (`attachments.test.ts (52 tests)`).

### 4. Retention (P10): holds

- **Inclusive due times:**
  - Previews expire at `expires_at <= at`, and selections are deleted at `expires_at <= at`.
  - Records are purged at `committed_at <= now - 30 days`, where the API has `<` (P10).
  - Q20 and the R37 case pin this.
- **`importsDueAt` is never early:**
  - A review record's term is `max(committed_at + 30 days, its preview's expires_at)`, and `recordsDue` purges it exactly when the preview has `expires_at <= now` and the record is 30 days old. A selection record's term works the same way, using its selection.
  - `coalesce(..., '')` keeps a record whose preview or selection is already gone due at its own 30 days.
  - Q23 to Q25 pin the live case.
  - My probe `R37` covers the cascade path. `pruneUploads` drops the upload row, taking the preview and the selection with it. `importsDueAt` then names the records at or before now, one `pruneImports` purges both, and the next `importsDueAt` is null.
