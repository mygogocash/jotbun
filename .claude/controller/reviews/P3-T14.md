### Minor

**m1. No case pins that a change the server never took leaves the common `ai_enabled` alone (privacy path, ruling P6).**
- **The code is right.** `aiConsent.ts:37-39` sets `ai_enabled` only after `await update(...)` resolves.
- **No case holds it.** My mutant RV1 adds `getAnalytics()?.setCommon({ ai_enabled: on })` before the `update` call and keeps the line after it, so it differs only when the change fails. It survives both focused files, unfiltered (`logs/rmutants.out`).
  - `AiConsent.render.test.tsx:203` ("a turn-on that fails says so and stays off") checks only that no `ai_consent_changed` goes out.
  - `WalletAiSettings.render.test.tsx:265` does the same for a turn-off.
- **Impact if it regresses:** after a failed turn-on, every later event would say `ai_enabled: true` while AI help is off. The provider's own effect would not correct it, because `enabled` never changed.
- **Fix:** add the check from probe P1 (`probes/ReviewProbes.render.test.tsx`). After the failed turn-on, send any event and assert that its `ai_enabled` is still `false`. P1 passes on the real code and kills RV1 by assertion (`logs/rmutants-probes.out`).

**m2. No case pins that the details link's flag is cleared, so a tray that is reused could open Privacy and data a second time (ruling P3, R69).**
- **The code is right.** `AiConsentTray.tsx:65-67` clears `detailsNext` before it pushes `/settings/privacy`.
- **No case holds it.** My mutant RV2 drops the clear on line 66. It survives both files. "อ่านรายละเอียด closes the tray, then opens Privacy and data once it has gone" closes the tray only once.
- **Why it is reachable:** the settings screen keeps one tray for both สิ่งที่ AI เห็น and the consent (`WalletAiSettingsScreen.tsx:348`). Without the clear, this happens:
  1. The person opens Privacy and data from the read-only tray.
  2. They come back.
  3. They open the consent from the switch and press ไม่ใช่ตอนนี้.
  4. Privacy and data opens again.
- **Fix:** add probe P2. It runs that path on the screen and asserts that `router.push` is called once. It passes on the real code and kills RV2.

**m3. The keep line promises more than B3 and Q1's default will deliver once photos can be attached. This is for counsel (Q11); the Thai is the plan's.**
- **The line:** `drafts.ts:30-33`, `bunai.consentKeepLine`: "Jotbun ไม่เก็บสิ่งที่ส่งไปอ่าน ยกเว้นรูปใบเสร็จที่คุณแนบไว้กับรายการ **ไม่เก็บรูปสลิป** และไม่ถูกนำไปฝึก AI". The English draft is "...**Slip photos are never kept**, and nothing is used to train AI."
- **The gap:** Q1's default (plan line 43) and B3 (boundaries line 155) accept that a slip attached without asking Bun to read it is kept as a receipt until P3-T12's QR decoder lands.
  - P3-T15's rows (plan line 773) also let a person turn the read off after a failed read, and then keep the photo. That photo may be a slip.
  - From P3-T15 until the decoder ships, "slip photos are never kept" is therefore not true for attached slips.
- **Today:** nothing at this commit contradicts the line, because no photo can be attached yet. The Thai is fixed verbatim by the plan, and the English "never" is stronger than the Thai "ไม่เก็บ".
- **Not a defect of this PR:** the copy is a draft behind an area that is off.
  - It needs a ruling before P3-T15 merges, or before P3-T24 approves the copy: scope the clause ("a slip Bun reads is not kept"), or say what happens to a slip attached without a read.
  - Everything else in the consent is accurate; see "The words" below.

**m4. With the `bunai` area on and `companion` off, `/settings/ai` offers a consent that can never succeed, and blames the network.**
- **The code:**
  - `CompanionBoundary.tsx:11` mounts no `AiCompanionProvider` while `companion` is off. `useAiCompanion()` then returns its default: `preferences: null`, and an `update` that throws (`AiCompanionProvider.tsx:21-29`).
  - Settings still shows the บันและ AI row, because `SettingsScreen.tsx:298` depends only on `bunAi`. The companion card that held the cashback tips is gone (`:299`).
  - On `/settings/ai`, the AI switch reads off and opens the consent. Every เปิดใช้ then fails with "เปิดตัวช่วย AI ไม่ได้ตอนนี้ ลองอีกครั้งเมื่อต่อเน็ต" ("try again when you're online").
- **Probe P5** (`probes/ReviewProbesNoCompanion.render.test.tsx`) shows this on the real code.
- **Effect:** it fails closed, so nothing is sent. But the line is untrue, and `-companion` is the documented switch for all of the companion (`featureFlags.ts:27`, the companion paragraph). `all,-companion` is a plausible configuration.
- **Needs a ruling:** should `bunAiAreaOn()` also need `companion`? The plan defines it as `wallet && bunai`. Or should the AI card hide its switch when no provider is mounted? The answer matters for every later entry point that reads `useBunAiArea()` (P3-T15 to P3-T21).
