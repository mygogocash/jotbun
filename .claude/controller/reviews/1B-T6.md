## Findings

### Major

**M-1. A HEAD on `GET /v1/export-files/:grant` takes a download slot and never gives it back.**

- Where:
  - The front door serves HEAD from the GET route (`src/v1/match.ts:15`) and runs the Worker handler. Then `headOf` (`src/v1/handler.ts:202-204`) answers `new Response(null, ...)` and drops the handler's response without cancelling its body.
  - `serveExportFile` (`src/v1/files/downloads.ts:53-67`) takes `EXPORT_SLOTS.take()` (line 58). It returns the slot only when its body stream ends or is cancelled (`bodyStream(chunks, release)`, line 62). A dropped body larger than what the pipe drains on its own is never read to the end and never cancelled, so `release()` never runs. The R2 read behind it is never finished or cancelled either.
  - `EXPORT_SLOTS` is one `DownloadSlots(4)` per isolate, with no per-account limit. So four HEADs refuse every member's export downloads in that isolate with 503 `SERVICE_UNAVAILABLE`, until the isolate is recycled.
  - Any signed-in member can do this with their own export: one request and one Workflow run. A client or proxy that sends HEAD before a download would trip it in normal use.
  - Both references avoid it:
    - The PostgreSQL edge's dispatcher cancels a HEAD response's body (`src/server/app/dispatch.ts:82-84`, `await response.body?.cancel()`).
    - The API returns the slot on the response's `close` (`apps/api/src/exports/exports.controller.ts:94-95`).
  - `headOf` predates this task. This is the first GET (so HEAD-able) route whose response body holds a slot, so 1B-T6 is what makes the defect reachable.
- Evidence, on the scratch copy of 34798c8. The probes are `tree/apps/edge/test/workers/review-probes.test.ts` and `tree/apps/edge/test/review-head.test.ts`.
  - **Real requests.** This ran under `wrangler dev` on the built vault Worker (the `test/support/vault-worker.ts` harness), where every HTTP request is its own stateless request.
    - The export ran on the local `ExportWorkflow` and became ready (233,886 bytes).
    - Four HEADs answered `[200, 200, 200, 200]`. The next GET answered 503 `SERVICE_UNAVAILABLE`, and again 10 seconds later.
    - Another member's ready export in the same Worker also answered 503 (`mutants/probe-wrangler2.log`).
  - **Workers test runtime.** Two probes fail on 34798c8 with `expected [ 503, 'SERVICE_UNAVAILABLE' ] to deeply equal [ 200, null ]`:
    - `H2`: one request context, an export over 200 KB.
    - `H3`: each HEAD inside its own Durable Object request.

    `H1` (a one-chunk file) passes: a small body drains into the pipe and returns its slot by itself. That is why no existing case sees this.
  - **Fix check.** With `headOf` cancelling the dropped body, `H2` and `H3` pass (`mutants/probe-head-fixed.log`). The change was:

    ```ts
    if (method !== 'HEAD') return response
    void response.body?.cancel()
    return new Response(null, { status: response.status, headers: response.headers })
    ```

    `handler.ts` was restored byte for byte afterwards.
- **Fix:**
  - Cancel the body in `headOf`, as the PostgreSQL dispatcher does.
  - Add a case to `exports.test.ts`: four HEADs on a multi-chunk export's grant each answer 200 with the recorded `content-length`, then a GET answers 200. The `H2` probe is that case. A one-chunk export does not reproduce the leak.
  - `src/v1/handler.ts` is not in this task's file list, so the controller has to add it to the fix round (one line).
  - The alternative inside the task's files is a HEAD branch in `serveExportFile` that releases the slot and cancels the R2 body before answering. The front-door fix also covers 1B-T8's and 1B-T9's downloads.

### Minor

**m-1. The read-time "vault is active" check in `writeExport` has no test.**

- `prepareExport` skips an inactive vault (`src/vault/files/exports.ts:233`). P5 says the write skips "at the read and again at the publish", but M4 pins only the publish (line 259). Both Review Focus cases make the vault `deleting` inside the bucket's `put`, after the read.
- My mutant X2 drops `|| !v.active(c)` at line 233. It passes all 33 workers cases and the Node file.
- X2 is not equivalent. Under it, an export Workflow that runs after deletion began reads the whole ledger and PUTs a fresh copy of it to R2. The copy is never published and is left for 1C's purge and final sweep.
- Probe `X2` passes on 34798c8 and fails under X2: the vault is set to `deleting`, then `writeExport` answers `skipped` with no `put`, no reserved key and no object.
- This is also the vault's nearest analogue of the not-applicable API case `an export cancelled by an account lifecycle transition mid-read publishes nothing`, as a transition just before the one-pass read.

**m-2. A failed download's slot release has no test.**

- `serveExportFile` returns its slot in its `catch` (`downloads.ts:63-66`). That runs when `matchingObject` answers 404 for a missing or changed object, or when `getStream` throws.
- My mutant X3 removes `release()` from that `catch`, and it passes every case. The tampered-file case makes only one failed download, and later downloads in the file still find a free slot.
- Under X3, every 404 or R2 failure keeps a slot, and four of them close downloads in the isolate.
- Probe `X3` passes on 34798c8 and fails under X3: five downloads of a swapped object are 404, then a good export downloads with 200.

## What holds

### 1. Security and access

- **Fresh sign-in.** `assertFreshSignIn` runs inside `runCommand`'s mutation, after the receipt lookup and the open cap (`exports.ts:86-89`). That is the order B7 and the API use (cap, then `authorizePurpose`), and a resent export replays without it. M1 and M2 were killed in my sample. The route keeps `recent_proof`, the `jobs` gate and status 202, which `vault-route-coverage.test.ts` pins against the legacy table.
- **Other accounts.** A route reaches only `idFromName(claims.accountId)`, and the grant's MAC covers the account id. The ownership case gives the same 404 for a foreign export, grant and download.
- **Ended sessions, a deleting account, an erased vault.** All three export routes and the `exports.file` step run `assertSession` (`'exports.file': {}`, not `anySession`). My mutant X1 (`anySession: true`) is killed by the deleting-account case. Probe `S1` checks the rest:
  - After `POST /v1/me/logout`, the status, grant and download are each 401 `SESSION_REQUIRED`, while another session of the same person still works.
  - After `erase()`, all three are 403 `ACCOUNT_UNAVAILABLE`, and `writeExport` answers `skipped`.
- **Grants.** A grant:
  - lasts five minutes and is capped at the file's expiry (M13 killed);
  - is bound to the export id (index 0) under export-only keys;
  - is refused from its expiry second (`grants last five minutes ...`).

  `exportFile` also requires `status = 'ready' AND expires_at > now` (M12 killed).
- **Only the published object.** `exportFile` names the `object_key` set in the same block that published it. `matchingObject` refuses a size or recorded-digest mismatch before streaming (M14 killed). As in the API and the PostgreSQL edge, a same-size object whose metadata digest still matches would fail only at the end of the stream (`verifiedChunks` without `holdLast`); the client checks the digest.

### 2. The write path

- **P1.** The publish block runs on `v.context()`, read after `putConcatenated` resolves (`exports.ts:295-297`). M7 killed.
- **P3.** Past `created_at + RESERVATION_GRACE_MS` the publish throws (line 262), so the step retries under a fresh key. `publishObject` still checks `delete_after > now`. M8 killed.
- **A failed write** leaves its reserved key due at its deadline, and `deleteDueObjects` removes the object (`a write retried after its file was stored ...`). After its retries the Workflow records `failed` (`error`) (M11 killed). `pruneExports` fails a pending export a day after its request.
- **P4.** `createOnce` runs under the export id, and the publish rechecks `pending`. M10 killed.
- **`pruneExports` and `exportsDueAt`:**
  - due times are inclusive (R37, as 1A-T8b ruled); the API's rule is strict (`<`), and inclusive is the accepted deviation;
  - ids bind as one JSON parameter (R57);
  - the purge goes through 1A-T8b's `purgeEntities` in its own blocks, in batches of 1,000 for at most 100 passes.

  The later-or-null case passes. M17 killed.

### 3. Parity with the API's ExportService

  - the vault's read is one synchronous pass, so there is no mid-read point, and the transitions before and after it are covered (see m-1);
