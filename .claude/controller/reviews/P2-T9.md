## Focus 3: the builder test reads `getAnimationAndConfig()` and `getReduceMotion()` (P3)

- Both are public instance methods in 4.7.1's shipped types (`ComplexAnimationBuilder.d.ts:131`, `BaseAnimationBuilder.d.ts:55`). Neither is `private` or `protected`, and the folder has no `@internal` tag.
- Neither appears in Reanimated's documentation. In the 4.7.1 docs (Context7) the modifiers are documented and these two getters are not.
- Reanimated itself depends on both:
  - Every preset's `build()` calls `getAnimationAndConfig()` (for example `Fade.ts:36` and `LinearTransition.ts:32`).
  - `getDelayFunction()` calls `getReduceMotion()` (`BaseAnimationBuilder.ts:143`).
  - Reanimated's own Jest mock implements both (`src/mock.ts:341-347`).
- My judgement: public by type, undocumented, and load-bearing. An upgrade that renames or reshapes them fails this file loudly (a `TypeError`, `driver: 'other'`, or a `toEqual` on the config); it cannot pass by accident. SDK 58 pins Reanimated at 4.7.1. I accept the choice. See Notes for one quirk.

### Minor

**m-1. GrowBar's growing path, the default for most people, leaves three of its rules unpinned.**

Apart from colour and radius, every committed check of the fill's shape, the clamp and the decision at mount runs only on the still path. At full motion:
- **No height (R2).** The full-motion case checks the width, colour and radius (`GrowBar.render.test.tsx:96-97`), but not the height. Without `height: '100%'`, the fill is an empty View in a column, so it is 0 pt high and the bar draws nothing at full motion. All 12 cases pass.
- **No clamp (R3).** `the fill never passes the track` runs only under `reducedMotion: true` (`:68-80`). If the growing fill gets the raw fraction, 1.4 grows to `140%`. The track has no `overflow: hidden` (ruling P8d), so the fill runs past its end. Over budget is an everyday state for a budget bar.
- **Decided at mount, full to reduced (R1).** The pending case (`:59-66`) pins one direction only. If Reduce Motion turns on while a bar grows, R1 snaps the bar to `62%`. The plan's rule (line 684, W6) is to decide at mount, so the bar should keep growing.
- **Two smaller gaps:**
  - The screen-reader case runs only the growing path (`:82-89`), so `aria-hidden` on the still bar is unpinned (R4). The impact is low, because an empty View is not focusable.
  - A move to a new value is checked only at its end (`:103-105`), so a restart from 0 passes (R9). The component's header says "and on to a new value".

The code is right on all five, so I rank this minor, as P2-T8's m-1 was. The four cases can go in now, or with the next PR that touches `GrowBar` (P2-T24 or P2-T30). Those screens' own tests will not catch these gaps, because a bar mounted in a test's first render is still (R66).

The two that matter most:
```tsx
test('at full motion the growing fill is as tall as the track and stops at its end', async () => {
  const view = mountWallet(<Text>before</Text>);
  await settle();
  vi.useFakeTimers();
  view.rerender(bar(1.4));
  expect(fill().style.height).toBe('100%');
  act(() => { vi.advanceTimersByTime(320); });
  expect(fill().style.width).toBe('100%');
});

test('a growing bar keeps growing when Reduce Motion turns on part-way (decided at mount)', async () => {
  const listen = vi.spyOn(AccessibilityInfo, 'addEventListener');
  const view = mountWallet(<Text>before</Text>);
  await settle();
  const changed = listen.mock.calls.filter(([name]) => name === 'reduceMotionChanged');
  expect(changed).toHaveLength(1);
  const tell = changed[0][1] as (reduced: boolean) => void;
  vi.useFakeTimers();
  view.rerender(bar(0.62));
  act(() => { vi.advanceTimersByTime(160); });
  act(() => { tell(true); });
  const width = Number.parseFloat(fill().style.width);
  expect(width > 0 && width < 62, `${width}% just after the change`).toBe(true);
  act(() => { vi.advanceTimersByTime(160); });
  expect(fill().style.width).toBe('62%');
});
```

The R4 and R9 cases are in the probe file:
- R4: mount with `reducedMotion: true`, then check `aria-hidden`.
- R9: grow to 62, rerender at 0.8, and expect a width between 62 and 80 at 160 ms.

**m-2. The own-animation case checks two of the six builders.**

`each call builds its own animation` (`useWalletMotion.render.test.tsx:99-103`) checks `trayEntering` (both answers) and `stepEntering`. R5 to R8 make `trayExiting`, `toastEntering`, `walletAddedEntering` or `stepLayout(false)` return one shared animation, and all 12 cases pass.

Ruling P7(b) gives the reason for a new animation per call: "the next tray to close (R69)". That is `trayExiting`, exactly the builder the case leaves out, and P2-T13 is the first task to chain onto it. The code is right: every builder builds a new animation per call. One loop closes the gap:
```ts
for (const reduced of [false, true]) {
  expect(trayEntering(reduced)).not.toBe(trayEntering(reduced));
  expect(trayExiting(reduced)).not.toBe(trayExiting(reduced));
  expect(toastEntering(reduced)).not.toBe(toastEntering(reduced));
  expect(walletAddedEntering(reduced)).not.toBe(walletAddedEntering(reduced));
}
expect(stepEntering()).not.toBe(stepEntering());
expect(stepLayout(false)).not.toBe(stepLayout(false));
```

### Nit

**n-1. `motionFor` hands out the table's own objects** (`walletMotion.ts:79-82`). `TABLE` is `Readonly` only one level deep, and `MotionSpec`'s fields are mutable.
- Probe (Node, on the scratch copy): a caller that sets `durationMs = 0` on its `budgetBar` plan changes every later answer. `motionFor('budgetBar', false)` then answers `{"motion":{"kind":"grow","durationMs":0},"haptic":null}`, and `Object.isFrozen` is false.
- No caller does this today; `GrowBar` keeps the object in state and reads it.
- `Object.freeze` on the rows, or `readonly` fields on `MotionSpec`, would make the one table the only source.

**n-2. The receipt keeps the default fade curve, but does not say which curve or carry it to E2-D.**
- Ruling P7f says the curve is for the E2-D reduced-motion captures, but the receipt's notes have no E2-D line.
- On a phone the curve is ease-in-out (quad), not the board's ease-out.
- If `.easing()` is added later, `getAnimationAndConfig()` puts `easing` into a timing builder's config (`ComplexAnimationBuilder.ts:292`). The five fade expectations in `useWalletMotion.render.test.tsx` then change with it.
