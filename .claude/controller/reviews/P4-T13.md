### Minor

**m1. The server-facing type and alphabet guards in `pickerShrink` are not pinned byte by byte; seven mutants of them survive all 18 tests.**
- Where: `imageShrink.ts:20` (the alphabet), `:29` to `:31` (the three signatures); the tests are `imageShrink.test.ts:79` to `:97`.
- Evidence (my mutants, run alone against `imageShrink.test.ts`, which stays 6 of 6 green for each):
  - R1: the JPEG signature read as `FF D8` only (the server needs `FF D8 FF`).
  - R2 and R3: the PNG signature read as 4 bytes, or without its last two bytes (the brief's P9 says the whole 8-byte signature).
  - R4 and R5: the WebP tag read as `WEB`, and the RIFF tag as `RIF`.
  - R6 and R8: the base64 alphabet admitting `=` anywhere, and three `=` of padding.
- The production code is right. Probe A compared `pickerShrink` with the contract's `parseSlipBatchRequest` plus the plan's first-bytes rule (P4-T6, plan line 445) over 1,500 random heads, sizes and base64 variants, plus every size from 1,199,996 to 1,200,004: everything the phone sent, the server took; the only cases where the phone sent null and the server would have taken the image were PNG heads with just the first 4 bytes right, which P9 refuses on purpose. So this is test strength only. It still matters because it is the one guard whose weakening makes a whole batch fail on every run (the controller's focus 1), and the protocol's mutation step says every survivor gets a test or an explanation.
- Fix (verified in the scratch copy: all pass on the committed code and kill R1 to R6 and R8). Extend the table in `only a JPEG, a PNG or a WebP is sent ...` with files that must give `null`, using the test's own `image()` helper:
  ```ts
  [uri('i.jpg')]: image([0xff, 0xd8, 0x00, 0x00], 900),                      // JPEG needs FF D8 FF
  [uri('j.png')]: image([0x89, 0x50, 0x4e, 0x47, 0, 0, 0, 0], 900),          // PNG needs its whole signature
  [uri('k.png')]: image([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0, 0], 900),
  [uri('l.webp')]: image([...Buffer.from('RIFF'), 0x24, 0x10, 0, 0, ...Buffer.from('WEBX')], 900),
  [uri('m.webp')]: image([...Buffer.from('RIFX'), 0x24, 0x10, 0, 0, ...Buffer.from('WEBP')], 900),
  [uri('n.jpg')]: `${good.slice(0, 8)}=${good.slice(9)}`,                      // '=' in the middle
  [uri('o.jpg')]: `${good.slice(0, -4)}A===`,                                  // three '=' of padding
  ```
  (`good` = `image(JPEG, 900)`.) The full text is `scratch/p4-t13-review/probes/zzprobe_gaps.test.ts`.
- Where it goes: a one-commit addition to this branch if the controller wants it before merge, otherwise `followups.md` under P4-T14.

**m2. The album's NFC is not pinned to run before the 60-character cut.**

### Nits

**n1. `pick(limit)` passes the limit through unvalidated.** `photoLibrary.ts:64` to `:70`. Probe D2: `selectionLimit` sent is 0, -1, 1, 20 for `pick(0)`, `pick(-1)`, `pick(1)`, `pick(20)`. The installed typings say 0 "sets the selection limit to the maximum that the system supports", so a limit that reaches 0 (a "slots left" sum) opens an unlimited picker, while the fake's `pick(0)` returns `[]`. Nothing calls it yet. A guard (`limit < 1` returns `[]` or clamps to 1) would make fake and real agree. Followup under P4-T18.

**n2. `slipBatchRequest` spreads the header, so a runtime extra key reaches the wire.** `slipBatches.ts:33`. `tsc` accepts a header variable with one more property than the type names (probe, `tsc` exit 0), and the contract's `assertKnownFields` then refuses the whole batch (probe E1: `UNKNOWN_FIELD`). Copying the four named keys would make that impossible. Today's only caller shape (P4-T14: `{ purpose, last, today, locale }`) is fine. Followup under P4-T14: build the header with exactly those four keys.

**n3. The fake library's `request()` cannot change state.** `fakePhotos.ts:43` to `:46`. It answers the configured `access` exactly as `access()` does, so a test cannot show "undetermined, then asked, then granted". Harmless under Q1's default (the picker needs no permission); P4-T18's permission screens will need the fake to take a `requestResult` option if they ask. (My mutant R23, `request()` turning `undetermined` into `all`, survives for the same reason.)

**n4. The claim that `fakeShrunkImage` is accepted by the contract's parser has no committed test.** The brief and the doc comment say so. I ran it (probe D1: five varied uris, including spaces, Thai letters and `%`, in one batch through `parseSlipBatchRequest`; it holds). ## Notes for later tasks

- **P4-T14: window the work.** `buildSlipBatches` needs every `ReadySlip` it is given in memory, and each holds up to 1.6 million characters of base64. Shrink and batch a page of pending photos at a time, not the whole backlog.
- **P4-T14: send through `slipBatchRequest`** (the receipt says so) and build the header with exactly `purpose`, `last`, `today`, `locale` (n2). Also, the builder does not check that `ref_hash` is distinct within a batch, or the pairing of `purpose` and `origin` (backfill with `album`; live with `share` or `photo`); the server refuses a whole batch for either, so the engine must guarantee both (its `ref_hash UNIQUE` and A1 do).
- **P4-T14: the same photo picked twice.** `PhotoAsset.id` is `assetId ?? uri`. iOS fills `assetId` from the picker result, and Android's `MediaHandler` fills it from the MediaStore when it can, so a re-pick of one photo can give the same id with a new copy uri. The plan's case `a slip picked again while pending is sent from the new copy, and the old copy is released` should use the same id with two uris, so that `slip_pending.asset_id` (primary key) and `ref_hash` (unique) both collide on one row. Check that `addPending`'s upsert handles it.
- **P4-T14 and P4-T18: `pick()` can reject.** A picker module that will not load, or an OS refusal, rejects (probe D4); `TellBunSheet.tsx`'s own picker maps these to `denied` and `unavailable`. The port does not, so the engine or the screen must catch.
- **P4-T18: never gate the picker on `access()`.** From Android 13 the module asks for no media permission (`getMediaLibraryPermissions` returns an empty list, `ImagePickerModule.kt:258`) and its response builder reads an empty list as granted with `accessPrivileges: all` (`:138` to `:160`), so `access()` answers `all` there whatever the app declares (Q12's default declares none). `src/lib/openAppSettings.ts` is the app's shared denied-recovery helper; the port's `openSettings()` reaches the same React Native call through `expo-linking`, so pick one path for the denied screen.
- **Q2's default risk** (a photo over 1,200,000 bytes after the picker's 0.7, a PNG screenshot above all, stays unread) is as the plan and receipt say; nothing here changes it.
