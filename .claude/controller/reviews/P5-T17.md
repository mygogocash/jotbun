## 2. The controller's focus questions

### The conditional reads (`client.ts:377`, `:414-421`, `:445-446`)

- **The 304:**
  - If-None-Match is sent exactly when `ifNoneMatch` is given (`:377`).
  - A 304 becomes `NOT_MODIFIED` only for such a read (`:417`). A 304 to any other read falls through to the refusal branch (`invalid`, status 304). A validator that does not take `NOT_MODIFIED` refuses it (`invalid_response`).
  - The 304 branch comes after `stillCurrent()` (`:414`), so a 304 that arrives after sign-out or an account switch is dropped like any other answer (probe PA6; m2: no test holds this).
- **The ETag:**
  - `etag` hears only the final answer's header, and only on a JSON success whose body passed `validate` (`:445-446`). It never hears a 304's, a refused body's, or a text or bytes read's.
  - `ratesToday` keeps it in a `heard` made fresh for each call (`resources.ts:289-296`), so the set and its ETag always come from the same response. The cache writes the two together, as one value under one key.
- **Could a stale or forged ETag make the phone keep wrong rates?** Not through this client.
  - **A stale ETag** (one the server no longer holds) gets P5-T6's 200 with the current set and its own ETag, and that replaces the cache at once. In probe PA, ETag `e2` was replaced by `e3` after the server moved.
  - **A forged ETag** can only come from the device store, and only `refreshRates` writes that store, from a validated 200. A wrong but sendable ETag heals at the next refresh (probe PB, second half). A 304 needs the server's own current ETag, so it can only keep a set the server says is still current. The cache never pairs a 304 with a set it did not get from that ETag's 200.
  - **An ETag that cannot be sent as a header** is the one way to get stuck (n1). Every refresh then fails before it leaves the phone, and the phone keeps its old set until sign-out. Getting there needs a damaged or edited store, because the server's ETag is 16 hex digits in quotes.
  - **Two transient cases** sit outside this client, and both heal at the next refresh (notes, section 6):
    - Workers KV is eventually consistent, so for up to about a minute after the Cron, another location can answer the older set. P7 takes it, since the cache does not compare `as_of`.
    - Cloudflare may weaken or drop a strong ETag when it compresses a response.

    Neither touches a saved amount: the vault freezes every home amount at save (Review Focus 2).
- **iOS's own URL cache** (P15) can turn a 304 into a 200 with its cached body. P15's answer holds: the same set is stored again.

### `refreshRates` never rejects and never overwrites (`ratesCache.ts:42-58`)

- **It never rejects:**
  - `readCachedRates` catches an unreadable store and bad JSON, and its shape check cannot throw: inside `isRatesTodayDto`, `isDate` catches its own errors and `canonicalQuote` returns null.
  - `ratesToday` and `store.set` each sit in their own `try`. A synchronous throw inside `ratesToday` lands in the same `catch`.
- **It never writes on a failure or on `'unchanged'`:** both paths return `cached` before the only `store.set` (`:45-50`). The plan's mutant K1, and K7, die on `a 304 or a failure keeps the cache` (my sample, section 4).
- **`'unchanged'` never answers a missing cache.** It can only follow a read that sent an ETag. With no cache, `ratesToday(undefined)` sends no If-None-Match, and a 304 to that read is refused. In probe PA's last step, that refresh answers null and stores nothing.
- **Two overlapping refreshes** can store in either order. The next refresh repairs this: the stored ETag no longer matches, so a 200 replaces it. The effect is transient and touches estimates only.

### `setHomeCurrency` (`resources.ts:301-302`, `ackForCommand` at `:214`)

- **What it sends and accepts:**
  - If-Match is sent exactly when `version` is not null (`version ?? undefined`), and the body is `{ currency }`.
  - The acknowledgement must carry this command's id. Its entity is the server's derived settings id, so it is not compared, as with a new budget (`setBudget`).
  - Mutants R20 to R22 die on its case (R20 and R22 are in my sample).
- **Could a lost answer, a resend or a conflict leave the phone and the server on different home currencies?** Not through this client.
  - **A lost answer:** the transport resends the same key with the same serialized body, up to two resends (`client.ts:239`, `:382-396`). The vault looks up the receipt first and replays the first acknowledgement, so a resend never makes a second change.
  - **Every resend lost:** the call rejects as `network`. The phone does not know the outcome, but `commandStatus([key])`, or a resend with the same key, will tell it.
  - **A new key with the old version** cannot overwrite. P5-T13 refuses a stale If-Match (409 with the current settings). It also refuses a missing If-Match once a settings row exists ("absent only while no settings row exists, otherwise required").
  - **A conflict** carries `current`, and the transport passes it through.
  - **No second copy:** the client keeps no home currency of its own. The phone's copy is the synced `settings` entity (X5), and C8 raises `pruned_through`, so after a change every phone resyncs to the server's settings.
  - What remains is a screen's choice for P5-T26 (notes): take the home currency from sync, adopt `current` on a 409, and never write a local copy before the acknowledgement.

### Minor

- **m1. The fake's `updateTrip` keeps a key whose value is `undefined`; the wire drops it.** (`fakeResources.ts:433`)
  - **The defect:** `const next = { ...trip, ...changes, version: trip.version + 1 }` copies an own `undefined` onto the trip. The transport sends `JSON.stringify(changes)`, which drops that key, so the vault leaves the field as it was. The next line's field choice (`:435`) already treats `starts_on: undefined` as absent; the merge does not.
  - **Probe PD:**
    - `updateTrip(JAPAN, 1, { name: 'ทริปโตเกียว', budget_minor: undefined })` leaves the fake's trip with `budget_minor: undefined`, which fails `isTripSnapshot`. The wire body is `{"name":"ทริปโตเกียว"}`, so the vault keeps `'120000'`.
    - `{ starts_on: undefined, ends_on: '2026-11-09' }`, with Korea starting on `2026-11-09`, is `updated` in the fake: the start becomes `undefined`, so no overlap comparison holds. Sent as the wire carries it, the same edit is refused with `trip_overlap` on `ends_on`.
  - **Why it matters:** P5-T24 tests editing and ending trips on this fake ("ending, editing and deleting go through the trip commands"). Suppose a form writes `budget_minor: undefined` for a cleared budget, which TypeScript allows because `exactOptionalPropertyTypes` is off. The test passes on the fake, which shows no budget, while the server keeps the old one. Vitest's `toEqual` would not catch it on the call log either.
  - **Fix:** merge what the wire would carry, e.g. `const sent: UpdateTripRequest = JSON.parse(JSON.stringify(changes))`. Use `sent` in the merge and in the field choice, and add PD's two cases as the test.
  - The older `updateTransaction`, `updateCategory` and `updateWallet` merges have the same shape. They are outside this task.

- **m2. A 304 that arrives after the session changed is dropped, but no test holds it.** (`client.ts:414-421`)
  - **Evidence:** my mutant RV1 answers a conditional read's 304 before `stillCurrent()`. It survives all five focused files (exit 0). It dies on my probe PA6, where the server moves the session epoch and then answers 304: the read must reject with `session_changed`, never answer `'unchanged'`.
  - **Not equivalent:** the transport promises that a response arriving after sign-out or an account switch is dropped (`client.ts:256-258`), and the existing session cases send only 200s. Today's caller reads public rates, but `NOT_MODIFIED` belongs to the transport and will serve any later conditional read.
  - **Test to add:** PA6 (`scratch/p5-t17-review/tree/apps/app/src/spend/v1/reviewProbe.test.ts`), next to the conditional case in `client.test.ts`.

- **m3. Two rules the fake keeps are not pinned by any test.**
  - **RV2:** listing the rates used from expenses only (`fakeResources.ts:462`, `tagged` changed to `expenses`) survives `fakeResources.test.ts`, because the fixture's income and exchange add no new rate.
    - Why it matters: P5-T12 lists the rates "of a tagged record" of any type. An exchange of leftover yen back to baht is such a record (a JPY transfer at its exchange rate, X15), and it belongs in tc-trip-summary's "เรทที่ใช้".
    - Probe PH (that exchange, tagged with the trip) kills it.
  - **RV3:** checking the version before the deleted state (`fakeResources.ts:139-140`, swapped) survives, because the only deleted-trip edit in the test uses the trip's current version.
    - Why it matters: a trip deleted on another phone is edited with the version held before the delete. The vault answers `ENTITY_DELETED` first (`transactions.ts:138-142`, the order P5-T9 inherits), which P5-T24 shows as `travel.tripNotFound`.
    - Probe PG kills it.
  - Each survivor dies on my probe alone, by one assertion (`scratch/p5-t17-review/rv-mutants-2.out`). Protocol Procedure 5 requires a test for each survivor.

### Nit

- **n1. An ETag that cannot be sent as a header keeps the phone on its old set until sign-out.** (`ratesCache.ts:18-22`)
  - **What happens:** `isCachedRates` accepts any text as the ETag. One with a character above U+00FF, or a CR, LF or NUL inside it, still reads as a good cache. Every refresh then fails before it leaves the phone (in Node's fetch, as `network NETWORK_ERROR`; I did not test the phones' HTTP stacks), so `refreshRates` keeps answering the old set.
  - **Probe PB:** a cache of `{ etag: '"r฿"', rates: <2 Nov> }` answers 2 Nov three times while the server holds 3 Nov, and the server sees no request.
  - **Exposure:** only a damaged or edited store gets here, since the server's ETag is 16 hex digits in quotes, and saved amounts are not affected.
  - **Suggested fix:** read such an ETag as null and keep the rates. (Treating it as damage would throw away a good offline set.) The next refresh then asks without If-None-Match and heals.

## 6. Notes for later tasks

- **P5-T6 (the route):**
  - RFC 9110, section 13.1.2, compares If-None-Match with the weak function. [Cloudflare's ETag docs](https://developers.cloudflare.com/cache/reference/etag-headers/) say compression can turn a strong ETag weak (`W/"..."`) or drop it, unless Respect Strong ETags is on.
  - If the Worker's JSON is compressed on the way out, "304 when If-None-Match equals it" never matches, and every refresh is a 200. That is safe, since this client stores and resends the header verbatim, but it loses the 304.
  - Compare with a leading `W/` stripped, and add a case for it.
- **P5-T6 and P5-T18c:**
  - [Workers KV is eventually consistent](https://developers.cloudflare.com/kv/concepts/how-kv-works/): for up to about a minute after the 06:00 Cron (X12), another location may still answer the older set.
  - P7 stores whatever 200 comes back, so a phone can step back to the older set until its next refresh.
  - This is harmless for money (estimates only), but a screen that shows the set's date may briefly show the older one.
- **P5-T9 and the fake:** the fake reads "on `ends_on` when only it moves" by key presence. In probe PE, an unchanged `starts_on` sent with a new `ends_on` names `starts_on`. If the vault compares values instead, change the fake in the same commit.
- **P5-T13 and the fake:** settle these in P5-T13 and keep the fake in step:
  - In the fake, an If-Match while no settings row exists is a 409 with `current: null`. `putBudget`'s precedent is a 404 for a replace with nothing to replace.
  - The order of the same-currency and version checks when both fail. The fake answers the 409 first.
  - An unknown currency: the vault refuses it with 422 on `currency`, and the fake accepts it (probe PF).
- **P5-T21, P5-T23, P5-T24:**
  - A reference-rate record the phone creates through the fake keeps only the keys sent: no `rate`, `rate_source`, `rate_date` or `home_amount_minor`. So it fails `isTransactionSnapshot`.
  - Once such a record is tagged with a trip, the fake's `tripSummary` throws a TypeError (`BigInt(undefined)`, probe PC).
  - Seed summary tests with records as the vault stores them (`goldenTripRecords()`, P5-T18a), or let the fake resolve the money keys from the set given to `setRates`.
- **The next task that renders foreign records on the fake (P5-T18b, T21 or T25):**
  - The fake's `balance()`, its `history()` totals and its `summary()` still add `amount_minor` whatever the currency.
  - P5-T10 and T11 move a wallet by `wallet_amount_minor` and total `home_amount_minor`.
  - This is the same gap the P5-T2 followups name for `recomputeTotals` and `pendingTotals.ts`.
- **P5-T26:** take the home currency from the synced settings, adopt the 409's `current`, and do not write a local copy before the acknowledgement. With that, section 2's answer holds end to end.
- **The followups' flip:** the receipt's notes have it right:
  - P5-T18a flips the two draft refusals to positive cases when it widens `ENTRY_KEYS`.
  - The first task whose edits send a money key flips the two choice refusals when it widens `CHANGE_RULES`.
