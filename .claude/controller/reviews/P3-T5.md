## 3. The tally's queue

- 300 `addDraftOutcome` calls made at once on a store with random 0 to 3 ms delays: every count lands.
- A reset among 40 adds and 7 adds made at once keeps call order: the result is the 7 only.
- One write in three failing: exactly those calls reject (40 of 120), and the stored counts equal the adds that resolved.
- A store whose `getItem` throws synchronously: that call rejects, the queue goes on.
- In the real development wiring (render suite, scratch-only file `zzReviewerProbe.render.test.tsx`, `probe-render-failing-store.log`, 1/1 pass): an AsyncStorage that throws, then rejects, then holds broken JSON never makes a review throw or wait; each event is sent at once and first; later counts land; there are no unhandled rejections.
- A tally that never settles does not hold the review.

So a corrupt or failing **store** never breaks a review. A custom **tally function** that throws synchronously does (minor m1).

### Minor

- **m1. A tally that throws synchronously escapes `reviewDraft`.**
  - Where: `apps/app/src/spend/v1/ai/draftReview.ts:36`. `Promise.resolve(tally(...))` evaluates `tally(...)` first, so a synchronous throw is never wrapped.
  - Probe: `reviewDraft(p, () => { throw new Error('tally threw before any promise') })` throws that error to the caller. The event has already gone (log: `PROBE sync-throwing tally: reviewDraft threw "tally threw before any promise"`).
  - Why it matters: the module's own contract (`draftReview.ts:8-9`: "a tally that fails is dropped: a count never fails a review") and the plan's `tally?: (...) => void` signature, which invites synchronous tallies.
  - Today's exposure: none. The only tally passed today (`useDraftReview.ts:23-26`) is an `import().then(...)` arrow, which cannot throw synchronously.
  - Fix: wrap line 36 in `try { ... } catch { /* a count never fails a review */ }`. Keep the call synchronous: the "then tallies once" test checks the tally ran before `reviewDraft` returns. Add a case "a tally that throws at once never fails the review".
- **m2. Nothing in the repo or CI holds the release guard, and the receipt does not say so.**
  - F1 and F2 are counted among "44 mutants, all killed" (receipt line 17), but only the planner's scratch tool `release-fold.cjs` kills them, not a repo test.
  - My M2 (guard removed entirely) passes every repo test: in Node the tally's `import('@mobile/dev/draftTally')` rejects and is swallowed.
  - Protocol step 5 asks for a test for every survivor, or a reason. P3-T22's `check-export.mjs` is the planned guard, but P3-T13 will import `useDraftReview` first, and between those merges CI would ship a regressed guard silently.
  - Fix: say in the receipt that F1 and F2 are killed by the out-of-repo fold probe only, and carry the note below to P3-T13 and P3-T22. No code change is needed for this task.
- **m3. The receipt names the wrong task for the `AiModelName` alias.**
  - Receipt line 23 (and the brief's P7) says "P3-T6: replaces `AiModelName` with `AiModel` from contracts".
  - The plan gives that edit to **P3-T18**: line 876 ("`src/analytics/events.ts` (`AiModelName = AiModel`)"), lines 893-894 and 1106. P3-T6's file list (line 363) does not include `events.ts`.
  - The code's own comment (`events.ts:125`) agrees with the plan.
  - Why it matters: `events.ts` is a shared file whose edits are named in their task, so a P3-T6 brief that follows this receipt would edit it outside its task.
  - Fix: change the note to P3-T18.
