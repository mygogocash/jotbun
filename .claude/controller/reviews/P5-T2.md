### Minor

- **m1. Two new amount guards have no test: if either is dropped, a JSON number passes.**
  - `hasRecordMoney` checks `typeof record.home_amount_minor === "string"` (`packages/contracts/src/v1/transactions.ts:204`) and `typeof charged === "string"` for `wallet_amount_minor` and `to_amount_minor` (`:206`). Without these checks the regex alone decides, and `RegExp.prototype.test` converts its argument to text, so the number `106814` passes as `'106814'`.
  - My mutants M4 (drop the home amount's `typeof`) and M5 (drop it on the charged amount) both survive `shapes.test.ts` and the API's contract spec, exit 0 in both (`own-mutants.out`).
  - They are not equivalent. A number is what a vault `toDto` that forgets `CAST(... AS TEXT)` would send (Global Constraints, section 6.2). The vault checks every change it writes against these validators (`apps/edge/src/vault/commands/change-log.ts:88`), so this guard is what keeps a number out of the change log and off the phones.
  - The planner's 57 mutants cover the regexes (R12 to R17, R24) and the null cases, but not the `typeof`. Protocol Procedure 5 says each survivor needs a test.
  - Fix: add `{ ...yen, home_amount_minor: 106814 }`, `{ ...yen, wallet_amount_minor: 106814 }` and `{ ...exchange, to_amount_minor: 43000 }` to the `refused` list of `each money field is checked` (`apps/edge/test/contracts/shapes.test.ts:145`).
- **m2. The release note names the build that accepts phase 5 money, not the one that shows it right.**
  - `auth.ts:100` calls `0.3.0` "the oldest app build that reads phase 5's contract". The receipt's release bullets (`docs/implementation/receipts/P5-T2.md`, lines 39 to 44) tell the owner to raise the server's minimum to "at least 0.3.0".
  - A 0.3.0 build at this commit accepts the money keys but still treats `amount_minor` as the wallet's money. `recomputeTotals` (`apps/app/src/storage/diaryRepository.ts:238`, `:253`) adds `amount_minor` and never reads `wallet_amount_minor` or `to_amount_minor`, and no screen reads `currency`.
  - My probe (`tree2/apps/app/src/storage/reviewProbe.test.ts`, `probe-balances.log`) runs through the real diary store. It applies a ¥4,620 charge to a baht wallet (`wallet_amount_minor` ฿1,068.14) and an exchange of ฿10,000 into ¥43,000. The store accepts both. It shows the baht wallet at `995380` and the yen wallet at `1000000`; the right balances are `893186` and `43000`.
  - P5-T18a fixes `recomputeTotals` (plan lines 785 to 815), and T18b to T18e fix the amounts on screen. But `app.json` stays at `0.3.0` through all of them, so a server minimum of 0.3.0 cannot tell a build that shows foreign money right from one cut today.
  - This is X20's choice, and nothing sends a money key yet, so it does not block the merge. But the owner action as written is not enough on its own.
  - Fix: in the receipt's release bullet and the `auth.ts` comment, say that 0.3.0 is only the floor for reading the keys. The phase 5 server's minimum must also exclude builds cut before P5-T18a to T18e, which needs a version bump after those tasks. P6B-T10's bump to `0.4.0` does that only if it lands after them. The controller should carry this rule to `followups.md` or P6C's release checklist (see Notes).

## 2. Backward and forward reading

- **The new validators accept everything the old ones did.**
  - `scratch/p5-t2-review/diff/superset.mjs` imports the base contracts (`54e889b5`) and the head's (`f4041406`). For each kind (wallet, category, entry, transfer) it checks 200,000 generated shapes: a valid older shape with one to four keys changed, drawn from pools of valid, phase 5 and wrong values.
  - Shapes the old validators accepted: 31,601, 44,970, 45,662 and 39,938. Shapes the old ones accepted and the new ones refuse: **0** (`superset.out`).
  - Shapes only the new ones accept: 149 wallets and 1,204 categories (the new shapes). For records it is 0, because changing at most four keys cannot add all seven money keys; `shapes.test.ts` covers the record's new branch.
  - The code says the same. Each validator only adds an alternative:
    - wallets: `keys === WALLET_KEYS ? THB : the look shape`;
    - categories: `keys === CATEGORY_KEYS || the icon shape`;
    - records: one with no money key returns `true` from `hasRecordMoney` and is otherwise checked as before;
    - totals: `isTotals` adds `currency` to the expected keys only when it is present.
  - This matters beyond the phones. The vault re-checks every stored change against these validators when it serves a sync page (`apps/edge/src/vault/reads/sync.ts:103` throws "A stored ... change no longer matches its persisted DTO."). A stricter validator would break sync on the server for change rows already stored.

## 3. The bounds (P4, P5) against the vault's columns

| Field | Contract (snapshot) | Vault column (`0002_currencies_trips.sql`) | Where they differ |
| --- | --- | --- | --- |
| `home_amount_minor` | text, `0` to `99999999999`, never null | INTEGER, NULL or 0 to the cap | NULL (a row from the previous release): coalesce it (P5-T10) |
| `wallet_amount_minor` | entries only; null or `0` to the cap | NULL or 0 to the cap, never on a transfer | SQL allows NULL on a transfer, but the key must be absent from a transfer's snapshot |
| `to_amount_minor` | transfers only; null or `1` to the cap | NULL or 1 to the cap, transfers only | the same rule, the other way round |
| `rate` | canonical positive decimal, at most 12 significant digits | 1 to 40 characters of digits and dots | both ways. Only the column takes `'1.0'`, `'01'`, `'0'`, `'.5'`, `'1.'`, `'0.0'` and a 13-digit rate. Only `parseRate` takes a 1 followed by 50 zeros, or `0.` with 45 zeros and a 1 |
| `rate_date` | real date, 1970 to 9999 (P4) | `date(rate_date) IS rate_date` | only the column takes a day before 1970; the feed never writes one |
| `currency` | in the ISO table | `[A-Z][A-Z][A-Z]` | only the column takes `XAU` or `XXX` |
| `trip_id` | null, or a lower-case UUID of version 1 to 8 | TEXT, no check | only the column takes upper case or the nil UUID |
| looks, `icon`, `pack_key` | exact lists (X6) | `[a-z_]{1,32}`; a pack key is never on a built-in | only the column takes `ewallet` or `boat` (X6's design) |

- **The cap.** Each amount is checked in its own currency's minor units, with no scale, as the Global Constraints say. `opening_minor` keeps `^(0|[1-9][0-9]{0,10})$`.
- **Null versus 0** follows Q10's default: a home amount of 0 is kept and is never null; a wallet amount is null or from 0; an exchanged amount is null or from 1.
- **Values only the column takes** make the vault's own write fail, not the phones' sync: `change-log.ts:88` checks each change against these validators and throws before storing it.
  - P5-T13's in-place rewrite (X3) skips that write check. The sync read re-checks the rewritten rows (`reads/sync.ts:103`), so a bad rewrite would then fail for every device. See Notes.
- **Values only `parseRate` takes** reach the column only through a request: an own or exchange rate the person sends. `parseRate` accepts `0.` with 45 zeros and a 1, and the INSERT then fails its CHECK as a 500 (P5-T10, see Notes).
- **Evidence:** `tree2/apps/edge/test/contracts/reviewProbe.test.ts`, `probe-contract.log` (4/4).

## 4. No rule across fields (P6), and what reaches the screen

The missing rules do not let a wrong amount reach the screen through the snapshot check:

1. Today's server sends no money key, so the check decides nothing new.
2. Every rule P6 leaves out either needs another entity, or is wrong by design. The home currency lives in `settings`, and the wallet's currency in the wallet. An own rate keeps its charged amount (X9), so "home equals the amount converted at the rate" is not a valid rule.
   - My probe shows the check accepts: a baht record at rate 1 whose home amount is not its amount; a reference rate dated after the record; a wallet amount on a same-currency record; and a reference rate with no day (`probe-contract.log`, "cross-field").
   - Those are the vault's rules (P5-T10). The vault's own write check cannot catch them either, so P5-T10's tests are what hold them.

A wrong amount does reach the screen by another path: the phone reads `amount_minor` as the wallet's money until P5-T18a. That is m2.

## Notes for later tasks

- **P5-T5 (wallets and categories).**
  - Send every wallet with its three look keys, null where none was chosen. A seven-key wallet must be THB (X7).
  - Send every category with both `icon` and `pack_key`; a category with only one of them is refused.
  - Check the currency with `isCurrencyCode`, and looks, icons and pack keys against the contract's lists. The columns check only their shape (X6), and the change-log write throws on anything else.
- **P5-T10 (`toDto` and the create).**
  - Put `wallet_amount_minor` only on entries and `to_amount_minor` only on transfers, even when null: my probe shows `{ ...transfer, wallet_amount_minor: null }` and `{ ...entry, to_amount_minor: null }` are refused.
  - Send amounts as `CAST(... AS TEXT)` (m1).
  - Store `rate` as `parseRate`'s output: the column also takes `'1.0'`, `'0'` and up to 40 characters.
  - Limit the length of an own or exchange rate the person sends. `parseRate` accepts a 48-character rate that the column refuses with a constraint error (a 500).
- **P5-T13 (C8, X3).** A change row rewritten in place skips the change-log write check, and the sync read re-checks it (`reads/sync.ts:103`). A rewritten snapshot that the contract refuses would break that page for every device, so check each rewrite with `isTransactionSnapshot`.
- **P5-T14.**
  - In the vault's header, `amount`, `amount_minor` and `currency` are in the record's own currency. `EXPORT_CSV_COLUMNS`' comment (`privacy.ts:69` to `76`, "integer satang ... baht") stays true only for apps/api, so say so where the vault fills the columns.
  - Treat `trip_name` as text and give it the formula prefix.
- **P5-T18a to T18e, P6B-T10 and P6C (m2).**
  - `app.json` stays `0.3.0` through the app's currency work, and a 0.3.0 build cut before P5-T18a shows wrong wallet balances for foreign records (the probe in m2).
