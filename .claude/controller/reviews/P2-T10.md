### Minor

**m1. A store that cannot be read shows every amount, so a person who hid them can see them (P5's fail-open).**
- Where: `PrivateModeProvider.tsx:46-47` (`read` turns a rejection into `null`) and `:70` (`hidden: mode === '1'`, so `null` means shown); pinned by V6, `PrivateMode.render.test.tsx:218-220` ("a store that cannot answer shows them").
- Probe: a `PrivateModeProvider` over a store whose `get` rejects draws `฿12,480` with digits in `textContent`.
- Why it matters: it is the one path where an amount renders without the setting having been read, which the controller asked about. W10 says private mode "stays on until the eye is tapped again", and Review Focus 2 lists "Private mode leaks a number". P5 itself takes R66's rule for the unread case (an unknown answer reads as the safe one), then takes the opposite rule when the read fails.
- Why only minor: the trigger is a failed AsyncStorage read, which is rare on both platforms (`getItem` wraps every error in its promise, `async-storage/src/AsyncStorage.native.ts:59-61`). Failing closed also has a cost: a phone whose store cannot be read masks amounts at every launch, and the eye's write fails too, so it only works for the session. The plan says nothing about read failures, and the controller accepted P5.
- Fix, if taken: on a failed read of `private-mode`, publish `hidden: true, ready: true`. One line: `read`'s catch answers `'1'` for `PRIVATE_MODE_NAME`.
- Blast radius: R10 fails only V6, first at line 220. Its broken-store block (`PrivateMode.render.test.tsx:218-225`) would then read: masked at launch with the tip, and the eye shows the amounts for the session.

**m2. The tip shows again and again until it is closed. The plan says it shows the first time only.**
- Where: `PrivateModeProvider.tsx:89-92` stores `private-tip-seen` only in `dismissTip`, and `PrivateTip.tsx:22` shows the tip whenever amounts are hidden and the mark is missing. V3 pins the reading at `PrivateMode.render.test.tsx:148-152`: "Hidden but never closed: the tip is still there at the next launch".
- The plan's test name is `the tip shows the first time only`, and its store name is `private-tip-seen`, not "closed". Under P6, a person who never taps ปิดคำแนะนำ sees the tip after every hide and at every launch while amounts are hidden. §2's anti-goal says nothing nags.
- Suggestion: mark the tip seen when amounts are next shown (in `toggle`, when `hidden` goes from true to false), as well as on close, so it covers one stretch of private mode and never returns. Or mark it seen when it first appears.
- This is a product reading for E2-A as much as a defect. If the controller keeps P6, record it for E2-A beside P9's board calls.

### Nit

**n1. The eye does not say it is waiting.**
- Before the setting is read, the eye is labelled แสดงยอดเงิน, but a tap does nothing (`PrivateEyeButton.tsx:37` never reads `ready`).
- The window is normally a few milliseconds. But nothing bounds it: the probe's read that never settles leaves the eye dead indefinitely, with no feedback.
- `IconButton` already has `disabled`. `disabled={!ready}` would make VoiceOver say "dimmed" and keep the controller's "the label says what a tap will do" true in that window.

**n2. P8's default drops a negative's minus.**
- `sign` defaults to `'none'` (`WalletAmount.tsx:41`), which draws a negative as its size (`walletMoney.ts:35`). This is pinned by `walletMoney.test.ts:35` and `WalletAmount.render.test.tsx:82,93`.
- I agree it is the coherent reading of the plan's four signs. If `'none'` kept the minus, it would equal `'balance'`. It also serves P2-T11's credit card (ใช้ไป with the size, plan line 796).
- But one later caller that forgets `sign="balance"` would draw a debt as money left. `budgetPace().leftMinor` goes below zero once over (`budgetPace.ts:141`), and a cash wallet's balance can too. Carry it into the briefs (Notes below).

**n3. Claims and order no committed test pins.**
- R4: the comment "two taps before React renders still flip twice" (`PrivateModeProvider.tsx:57`) is true, but only my probe proves it. A three-line case would pin it.
- R9: `WalletRoot`'s order matches plan line 1584 (area off), but nothing holds it until P2-T33's source test.
- R2 and R5 guard paths that are unreachable or redundant today.
