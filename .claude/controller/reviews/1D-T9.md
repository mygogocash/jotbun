## Findings

### Major

**M1. Resolving a choice flashes today's `ConflictPanel`, with a live "Apply my change" that bypasses the choice flow.**

- **Where:** `recordActions.ts:389-394` (`useServer`: `await dropOpen()` before `cancelEditing()`) and `recordActions.ts:351-355` (`sendYours`'s acknowledged branch: `await dropOpen()` before `setEditing(null)`). `dropOpen` (`:218-222`) clears `open` synchronously and then awaits `diary.dropChoice`. Until that await returns, `editing.conflict` is still set but `open` is null, so `choicePanel` is null (`:501`). `RecordScreen.tsx` then falls through to its `editing?.conflict` branch (`:171-177`) and draws today's `ConflictPanel`.
- **How long:** for the whole diary write. The real `spendDiary.dropChoice` (`spendDiary.ts:299-302`) runs a SQLite delete and then `refresh` (three reads) before it resolves. On a phone that is at least a frame, on every resolution.
- **Probe A** (`probe-on.txt`): the diary's `dropChoice` is held. I refused an edit, chose the server's card and pressed "Use the server's".
  - `todays ConflictPanel shown = true ; Apply my change button = true`.
  - I pressed "Apply my change" in that window, then released the drop. `updateTransaction` calls: `[RENT,1,{amount_minor:"1200000"}]` (the refusal) and **`[RENT,2,{amount_minor:"1200000"}]`**.
  - So the person's change was sent after they chose the server's version. It went through `submitEdit`'s ordinary path under an `edit:` key, because `openRef` was already null. `useServer` sets no `acting` guard, and the old panel's buttons are not busy in this branch.
- **Probe B:** the same window after "Use yours" is acknowledged: `todays ConflictPanel shown = true`. Its buttons are busy there, so this one is a visible flash only.
- **Why major:** the plan's flow says that with the area on, the choice replaces today's panel ("with it off, today's `ConflictPanel` with Apply and Reload stays"). The probe also breaks focus item 1 ("Use the server's sends nothing"; "nothing is sent twice"). The 30 mutants and 91 focused tests cannot catch it, because `createFakeDiary`'s `dropChoice` resolves at once.
- **Fix (small):**
  - In `useServer`, call `cancelEditing()` before `await dropOpen()`. `cancelEditing` still sees `editing.conflict`, so P2-T6's notice rule holds; then `void load()` after the drop as now.
  - In `sendYours`, move `setEditing(null); setNotice(null);` above `await dropOpen()`.
  - Add a render test with a diary whose `dropChoice` is held, asserting that `queryByTestId('conflict')` stays null and no second `updateTransaction` is sent. Probe A is a ready template.
  - The planner's mutant U3 pattern will need its text updated after the reorder.
  - A related window, in a server-misbehaviour path only: `sendYours`'s "conflict without a usable record" branch (`:372-375`) sets `editing` to null and reloads. Until the read lands, the old receipt shows with live Edit and Delete, and the reload then replaces any edit begun there with the panel. Worth the same care if it is cheap.

### Minor

**m1. A choice kept in the diary is missed when the record screen loads before the diary is ready. After the person's next save, the stale choice comes back with "Yours" preselected.**

- **Cause:** `load` reads the stored choice once, at call time (`storedChoice()`, `:198-201`, `:229`). Nothing re-runs `load` when the diary turns `ready`, because `load`'s deps never change (deliberately, P2). Drafts do not have this problem: `fromDevice` is derived on every render.
- **Probe E:** a fake diary in phase `opening` holds a choice.
  - The screen shows the receipt. Then the diary turns ready: `panel shown = false ; Edit offered = true`.
  - The person edits the amount to ฿9,900 and saves. The save is acknowledged, and its reload finds the old choice. The panel now shows "Yours ... ฿12,000.00, Differs" against "On the server ... ฿9,900.00", with "Yours" chosen and "Use yours" as the main button. Pressing it would replace the save just made with the older refused change.
- **When it happens:** a cold start straight into the record route, or a locked diary unlocked while the screen is open. Rare, but the default action is the harmful one.
- **Fix:** re-run `load` once when the diary becomes ready while no choice is open. A `diaryView.phase === 'ready'` boolean in the effect's deps does not flip on keep or drop, so it cannot loop. Alternatively, have an acknowledged ordinary edit drop a stored choice for the same record.

**m2. When the diary fails to drop or to re-keep, "Use the server's" lands straight back in the same panel.**

- **Cause:** `useServer` calls `dropOpen` and then `load`.
  - If `dropChoice` rejects (swallowed, P7), the diary still holds the choice.
  - If a reopened choice could not be re-kept (`kept: false`, while the diary still holds the earlier copy), `dropOpen` skips the diary altogether (`:221`).
  - Either way, the reload's `storedChoice()` adopts the copy again.
- **Probes C and D:**
  - C: `after Use the server's: diary still holds = 1 ; panel on screen = true`, and the reopen offers it again.
  - D: `panel back at once = true`.
  - In C the panel has no Decide later and no Back (`kept: false`), so the person can only use theirs or leave by the system gesture.
- **The ruling:** P7 promised "the next open finds it settled or offers it again", not the same screen at once. Diary write failures are rare.
- **Fix:** `dropOpen` always asks a ready diary to drop. My mutant R13 shows that no test depends on the `kept` check there. `useServer`'s reload should not re-adopt a choice it was just asked to drop (for example, a per-screen "dropped" ref).

**m3. Behaviour the plan or the rulings name is unpinned (my mutants survive; current behaviour is right, as probes I to L show).**

- **R6:** `sendYours`'s gone branch disabled. Probe I: "Use yours" meeting a record deleted elsewhere correctly shows Restore and Discard my change with the choice kept, but no test covers it. Review Focus 5 ("offer Restore or Discard when the record is gone") is pinned only for the reopen path.
- **R11:** no Discard my change on a missing record (`not_found` load error, P5). Probe J shows it offered; no test.
- **R7:** `conflict_shown` not sent when "Use yours" meets another change (P8 rules it is). The "yet another change" test does not record analytics.
- **R4:** `unavailable` (503) not treated as offline (P6 names `network` or `unavailable`). Probe K shows the offline panel; only `network` is tested.
- **R9:** the choice path not consuming `autoEdit`. Probe L shows that History's Edit (`mode="edit"`) on a record with a choice lands on the receipt after "Use the server's". With the mutant, it opens the edit form instead.
- **Fix:** five short cases in `RecordScreen.render.test.tsx`, most of them reusing `keptChoice()`.

**m4. Plan ambiguity: an edit refused because the record was deleted elsewhere keeps nothing.**

- **What happens:** `submitEdit` handles `conflict` with a deleted snapshot as gone (`:314-317`) before the choice branch.
- **Probe H:** `kept = 0 ; Discard my change = false ; Restore = true`. After Restore, the person's change is gone (today's behaviour).
- **The plan reads both ways:**
  - Its first bullet keeps a choice only "with a usable current record".
  - Its deleted bullet ("the deleted notice and Restore as today, plus Discard my change") and C16's spec line ("an online edit ... refused with VERSION_CONFLICT is kept") read broader.
- **Ask:** the controller should rule. As built is defensible; if the broader reading is wanted, keep the choice on that refusal so that Restore leads back to the panel.
