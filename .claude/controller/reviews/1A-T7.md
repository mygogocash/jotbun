## What was checked and holds

### Exactness against the API, route by route

**GET /v1/history** (`reads/history.ts`)
- Parser, cursor and DTO are the API's own (`parseHistoryRequest`, `encodeCursor`/`decodeCursor`, `toDto`); the vault reads rows with the same `COLUMNS` as `getTransaction` (now exported from `domain/transactions.ts`, the way the API's history imports `RECORD_COLUMNS`).
- `scopeOf`: same clauses and order as the API's `$1..$6` form. A filter that is absent adds no clause; the API's `$n IS NULL OR ...` is true for it, so the rows are identical. `parseHistoryRequest` only sets `wallet_id`, `category_id`, `type`, `query` when present and non-empty (`query` after NFC and trim), so `!== undefined` is the exact test. Probe P5: `query=` and `query=%20%20` return every row, as the API does.
- Text search: same escaping regex as the API (`/[\\%_]/g` to `\\$&`), with `ESCAPE '\'` standing in for PostgreSQL's default backslash escape. Probe P1 confirms a literal `50%`, `a_b` and `\` each match only themselves, `50` matches both notes, and `AXB` matches `axb` (ASCII fold).
- Keyset `(occurred_on, id)` with `<` for `date_desc` and `>` for `date_asc`, order `occurred_on, id` in the same direction, look-ahead `limit + 1`, `next_cursor` from the last kept row, `chainRevision = position?.revision ?? revision`, `refresh_suggested = position !== null && position.revision !== revision`. Identical to `HistoryQuery.list`. `id` is TEXT (BINARY) and every id is a lower-case UUID (`isUuid` regex `^[0-9a-f]{8}-...$`), so text order equals PostgreSQL's uuid (byte) order. `occurred_on` has `CHECK (date(occurred_on) IS occurred_on ...)`, so BETWEEN on text is BETWEEN on dates.
- `scopedTotals`: same three-branch UNION for `by_wallet`, same `FILTER (WHERE ...)` sums, `count(*)`, `ORDER BY x.wallet`; every sum is `CAST(... AS TEXT)`. `accountRevision` is `CAST(revision AS TEXT)`. Response key order matches (`items, next_cursor, as_of_revision, refresh_suggested, summary`).
- Bound parameters: at most 12 for the page and 27 for the `by_wallet` query, well under Durable Object SQLite's 100.

**GET /v1/history/deleted** (`reads/deleted-history.ts`), looked at first as asked
- `DELETED_KEY = substr(t.deleted_at, 1, 23) || '000Z'`. The only writer of `deleted_at` is `deleteTransaction` (`domain/transactions.ts:291`, `c.now.toISOString()`, always 24 characters `YYYY-MM-DDTHH:MM:SS.mmmZ`), so the key is always `YYYY-MM-DDTHH:MM:SS.mmm000Z`, the exact shape of the API's `to_char(... 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')` and the only shape `decodeDeletedCursor` accepts (`DELETED_INSTANT`). Fixed-width keys compare as text in time order, so `(key, id) < (?, ?)` against a cursor with any six-digit fraction pages as PostgreSQL's timestamptz comparison does; the added case `a cursor with microseconds pages as PostgreSQL compares instants` proves it, and M6/M7 show the raw millisecond text would fail.
- Window: `t.deleted_at >= since` with `since = toISOString(now - 30 * 86_400_000)` is the API's `deleted_at >= now() - make_interval(days => 30)`; inclusive at exactly 30 days. The vault's restore (`transactions.ts:310-311`) refuses `deleted_at < cutoff` with the same cutoff, so the listing and restore agree at the boundary, as the API's do. `exactly 30 days after its deletion ...` pins the vault clock and proves both sides (M5).
- Order `deleted_at DESC, id DESC`, look-ahead, chain revision and `refresh_suggested` identical to `DeletedHistoryQuery.list`. Response keys match (the ported case asserts the exact key set).

**GET /v1/summary** (`reads/summary.ts`)
- Query check is the controller's own (`parseMonth(assertKnownFields({ ...query }, ['month']).month)`), so `UNKNOWN_FIELD`, a missing month and `2026-13` answer as the API does.
- Month bounds in JS: `Date.UTC(year, monthNumber, 0)` is the last day of the month (1-based month used as the 0-based next month, day 0). `parseMonth` refuses anything before `1970-01`, so `Date.UTC`'s two-digit-year mapping never applies. With the `occurred_on` CHECK, `BETWEEN first AND last` equals the API's `>= first AND < first + interval '1 month'`.
- Same SQL as `SummaryQuery.month` for totals, categories (`GROUP BY category_id, type ORDER BY type, category_id`, `t.type <> 'transfer'`) and budget usage. The capped ids bind as one JSON parameter through `json_each(?)` (R57). `readBudget` is Task 6's port (same `ORDER BY category_id`, amounts as text). Remaining amounts are BigInt. Response key order matches. `SummaryQuery` is not imported because it pulls `budgets.service` (and `DatabaseService`); keeping its SQL is the right call.

**Totals beyond `Number.MAX_SAFE_INTEGER`.** The added exactness case inserts 90,100 rows of 99,999,999,999 (total 9,009,999,999,909,900, above 2^53 and far below SQLite's int64 limit) and checks summary totals, `by_wallet`, categories, budget usage and history totals as exact strings. M4 kills it. SQLite's `sum()` would raise on int64 overflow where PostgreSQL's numeric would not, but that needs over 92 million maximum-size records in one vault; not a practical difference.

**Case folding (accepted deviation, 28 October).** Nothing else depends on it: UUID filters, cursor ids, `type`, `sort` and `month` are validated exactly by the shared parsers and compared byte-wise against lower-case stored values; no column has a collation (`grep -i collate` in the vault migrations is empty); the filter key in cursors is computed from the parsed filter. Thai search is unaffected (probe P2). No existing parity step searches text (`apps/edge/test/parity.db.test.ts:97-107`).

**SQL injection.** Every value is bound: dates, ids, type, the LIKE pattern, `since`, cursor positions, `limit + 1`, month bounds, the JSON id list. The only interpolations are module constants (`COLUMNS`, `DELETED_KEY`, `MONTH_SCOPE`), clause strings built from constants, and `ASC`/`DESC` from a boolean.

**Error codes.** Every refusal comes from the API's own parsers and cursor decoders, thrown inside the handler and mapped by `toProblemReply`; the ported `it.each` cases check status 422 and the field for each. R41 does not apply (reads take no command headers).

### Minor 1. The `ESCAPE '\'` clause, the vault-specific half of the API's escaping, has no test

`apps/edge/src/vault/reads/history.ts:40`. PostgreSQL's ILIKE escapes with backslash by default; SQLite has no default escape, so this clause is what makes the copied escaping mean anything. Mutant MA (drop it, keep the escaping) passes all 42 committed cases: the only escaping assertion, `query=%` returns `[]` (`history.test.ts:147`), also holds when `%\%%` is matched literally, because no golden note contains a backslash. The receipt's M9 only proves the escaping regex. Probe P1 shows the correct behaviour (`50%`, `a_b`, `\` each match only their own record) and kills MA. Add a case like P1 (one value in `merchant`, which also closes MF below).

### Minor 2. Four more lines survive mutation; the receipt's "No survivor" covers only its 13 chosen mutants

All four are faithful to the API, whose integration suites have the same gaps, so this is test strength, not a port error:
- MB and MD: `chainRevision = position?.revision ?? revision` in `history.ts:121` and `deleted-history.ts:53`. No case follows a cursor issued after a change, so "a cursor carries its first page's revision" is unproven in both reads (P3 covers history only).
- MF: the merchant half of the search (`history.ts:40`). The golden diary has no merchant (`apps/api/src/transactions/fixtures/golden-diary.ts:13-16`).
- MC: summary category order (`summary.ts:43`). The ported cases use `arrayContaining`/`toContainEqual`. Task 9's parity session compares normalized bodies with `toEqual` (plan Task 9 Step 1), so order matters there; pinning it here is cheap.
Either add a case each (P1 to P4 are ready to lift) or record them in the receipt as known equivalents of the API's gaps.

### Nit 2. Recently deleted orders by `deleted_at` but keys by `DELETED_KEY`, and only an unwritten invariant ties them

`deleted-history.ts:43` (ORDER BY) vs `:37` (keyset). They agree only while every `deleted_at` is exactly `toISOString()` (MG is equivalent today). `deleted_at TEXT` has no format CHECK (`0000_vault_core.sql:137`). A stored value with microseconds or without milliseconds would make the key disagree with the order (rows can be skipped) or produce a next cursor that `decodeDeletedCursor` refuses. Ordering by `deleted_key` costs nothing; a CHECK belongs to a later migration if anything ever writes `deleted_at` another way. Related: the API has `transactions_deleted_idx` (`apps/api/drizzle/0015_privacy.sql:136`) and the vault has no index on `deleted_at`, so each page scans the table; fine at one person's scale, worth a line for 8b's purge.

### Nit 3. The restore cutoff is computed in three places

`deleted-history.ts:15,36`, `domain/transactions.ts:37,310`, `reads/balances.ts:5,42`, each with its own `DAY_MS`. The listing and restore agree at the boundary by duplication; the exactly-30-days case guards it. A shared `restoreCutoff(c)` would make it structural. Optional.

### Nit 4. `COLUMNS` comment names only `reads/history.ts`

`domain/transactions.ts:63`: `reads/deleted-history.ts` imports it too.
