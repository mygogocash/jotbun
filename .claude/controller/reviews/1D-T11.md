## The controller's questions

### Consent: no person event without the caller's own yes
- Events go under the analytics id only when all three hold (`handler.ts:217-232`): the vault read `consent: 'yes'` after the block, the request is not marked off, and `ANALYTICS_ID_KEY` is set. The consent is read only when `account_state` holds the caller's account (`vault/analytics.ts:74`, P3).
- Before an answer and after a no: nothing (the task's "nothing is sent for a person who said no…" covers never asked, no, and off in two cases; H3 killed).
- Another account: each vault is named by the verified account id (`handler.ts:147`), so the only cross-account case is a vault holding another account. `ensureAccount` refuses it (500, `VaultOwnerMismatch`) and the consent read is skipped; the task's owner-mismatch case pins it (A15 killed). There is no shared vault in this code.
- A deleted account: an erased instance answers 403 with `consent: 'unasked'` before any read (`user-vault.ts:206`); after it wakes, the marker row's empty account id never matches. A `deleting` account is refused by `assertSession`. RP1 and RP2: both routes answer 403 `ACCOUNT_UNAVAILABLE` and nothing is sent.
- Worker routes (imports, AI, attachments) call `stub.call`, which drops the analytics, so no person event comes from them; the import case pins it. Only `POST /v1/transactions` reaches `transactions.create`.
- The off header: `off` in any case stops person events (H1, H2 killed). One gap: a request whose header arrives as a list (`off, off`) is not read as off (RP8, nit 1). The app sends it once, through the shared transport, which the outbox's creates and `sync.changes` use (`deviceSync.ts` imports `getSharedSyncRemote`; `sharedV1.ts:54` sets `analyticsOff`), so the receipt's m4 note holds.
- By the plan's rule, anonymous `$exception` counts go whatever the consent and the header (Notes 4).

### What each event carries
- `record_saved`: `kind`, plus `category_key` (a built-in key or `custom`) except for a transfer, read from the change log by a two-parameter revision range (`vault/analytics.ts:44-55`). 1D-T3's allow-list then keeps only those keys and values and adds `origin: 'server'`; `capture` refuses any distinct id that is not 64 hex characters. The task's case checks that no amount, note, merchant, wallet, record id or user id reaches a message; a category of the person's own goes as `custom` with its Thai label absent.
- `resync_required` and `sync_failed`: `reason_code` only.
- `$exception`: the type is the class name when it matches `^[A-Za-z][A-Za-z0-9_]{0,63}$`, else `Error`; a fresh UUID distinct id; `$process_person_profile: false`. U2 (the message as the failure) killed. A Thai message with an amount appears in neither the message nor the logs (task case).

### Failure counting (P5)

I agree with P5's reading of "not a `ProblemException`" through L6.

### Nit

1. **A repeated off header is not read as off.** `analyticsOff` compares the whole value (`handler.ts:208`); a request with two `X-GoGoSpend-Analytics: off` lines reaches the Worker as `off, off`, and RP8 sees a `record_saved` sent for a person whose phone said off. The app sends one value, so nothing does this today. Failing closed costs one line: treat the request as off when any comma-separated token, trimmed and lower-cased, is `off`.
2. **P8 is not pinned.** M4 (build the client for every call, with or without something to send) passes the task's tests; RP7 (count the `analytics` dep's calls: 0 after the setup and a read, 1 after a create) kills it. The cost is CPU only.
