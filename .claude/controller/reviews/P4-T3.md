## The focus list

### The release check (P8; `handler.ts:117`)

- **Placement:** right after `const { route, params } = match` (`handler.ts:115`), before `readRouteBody` (119), the config read, the gates, the client check and the token. Planner mutants H6 and H8 (the release after the body, after the token) are killed (my rerun).
- **Same answer:** both paths return `problemResponse(404, 'NOT_FOUND', requestId)`. My probe compares status, every header but `x-request-id` and the body but `request_id`, for seven pairs (a missing path against the unreleased route): GET without a token, a trailing slash, the path in capitals, HEAD, PUT with a malformed body, and signed in, GET and PUT with command headers. All identical. `matchRoute` has no 405 (a known path with another method matches nothing), and in production the `/v1/$` catch-all (`src/routes/v1/$.ts`) sends every /v1 path to `handleVaultV1`, so both answers come from the same function there too.
- **No I/O on either path:** with a recording env and recording deps, a missing path reads nothing from `env`, an unreleased one reads only `SLIP_IMPORT_ENABLED`; neither reads the body (`bodyUsed` stays false), the config, the verifier or analytics. Released, the same request reads the body and the config (the recording works).
- **Timing:** in the Worker, 12,000 requests each: 197 ms for the missing path, 206 ms for the unreleased route (about 16 to 17 microseconds each, measured across KV reads between batches, since the Workers clock moves only on I/O). With no I/O on either path, nothing a client could tell from network jitter.
- **`flag()`:** `value === '1' || value === 'true'` (`src/server/env.ts:53`). My probe: `TRUE`, `True`, ` true`, `true `, `yes`, `on`, `2`, `01`, the empty string, `false` and `0` all stay 404.
- **The salt has no `release`, by design:** plan line 283 ("`GET /v1/slips/salt` (`bound_session`, `slips.salt`, without `release`, S13)") and S13 ("except the salt read and `POST /v1/slips/refs`, which a single read's slip ref needs before slip import opens"). The route table and `route-coverage.test.ts:172-185` pin it so; planner mutant H1 (the salt behind the release) is killed.

### The salt (P14)

- **Made once, inside the call's block:** `callWithAnalytics` runs the handler inside `ctx.storage.transactionSync`, after `ensureAccount` and `assertSession` (`user-vault.ts:232-238`); `slipSalt` reads, then inserts the one row (`salt.ts:19-24`; `id = 1` CHECK); a vault's calls run one at a time. Planner mutant A1 (a new salt per read) is killed.
- **Never logged or sent:** no log call in `salt.ts`; server events carry only `analytics.events` and reply-derived reason codes (`handler.ts` `sendServerEvents`; `analyticsAfterCall` never reads the reply); the probe run's log lines hold no salt. The answer carries `cache-control: no-store` (`BASE_HEADERS`; probe), so no shared or device cache can serve one account's salt to another.
- **Another account's session:** the Worker names the vault by `idFromName(claims.accountId)` from the verified token (`handler.ts:150`), and the vault refuses claims for another account (`session.ts:29-33`, `VaultOwnerMismatch`). Probe: calling the owner's vault stub directly with another account's claims is refused, the salt is not in the reply, and the vault still holds one salt row.
- **Erase:** `UserVault#erase` cancels the alarm, `deleteAll()`s and re-migrates (`user-vault.ts:109-121`): the task's erase case shows no salt, reference, account, draft, lease or use left, and an erased vault answers 403 `ACCOUNT_UNAVAILABLE` before any handler, so it never makes a salt again.
- **Restore or snapshot:** snapshots read only `entity_heads` and `entity_changes` (`files/snapshots.ts:160-162`), so at most the inbox count travels; no code outside `src/vault/slips` reads a slip table (exports included); there is no vault copy, merge or account restore (the only "restore" is a deleted record's). A storage restore would bring the salt back into the same account's vault (same `idFromName`), where 1C's erasure registry re-erases a deleted account. No path carries it to another account.

### Minor

- **m1. Four slip-account guards are correct in the code but unheld by the task's tests** (O5, O2 to O4, O1 above; each survives all 13 cases).
  - O5: a mapping that writes every account (`accounts.ts:89`) passes, because the mapping case has one account. A regression would silently remap and re-version every slip account of the person.
  - O2, O3, O4: the R41 order the plan and the controller name (If-Match, the id, the body, the version, the wallet) passes in any order, because the mapping case never sends two faults at once.
  - O1: counting a draft per side (`accounts.ts:18-20`) passes, because the list case has no draft whose two sides are one account (P9: "counts each draft once").
  - **Fix:** in `slips-vault.test.ts`, add a second account to the mapping case and check its row stays version 1 and unmapped; send the two-fault requests (no If-Match with an unknown field, and with a non-UUID id: 422 on `if_match`; a non-UUID id with an unknown field: 404; stale with `wallet_id: 'cash'`: 422 on `wallet_id`; stale with an archived wallet: 409; an unknown account with an unknown wallet: 404); and count a `kbank 1234` to `kbank 1234` draft once. The probe file holds each as a ready case.
- **m2. "As if it did not exist" is pinned on status and code only.** The unreleased case compares `{ status, code }` with a missing path's (`shape()` in `slips-vault.test.ts`), so O8 (`problemResponse(404, 'NOT_FOUND', requestId, { retryAfterSeconds: 30 })`, whose `retry-after` header and `retry_after_seconds` field would tell the route exists) passes all 13 cases. Today the answers are identical (probe). **Fix:** compare whole responses, minus `x-request-id` and `request_id`, as the probe's first case does.
