- **Deviations** (each for the reviewer):
  1. `posthogOptions` also sets `rageClickConfig: { enabled: false }`. posthog-ios detects rage taps and sends `$rageclick` from the native SDK, outside `before_send`, whenever the native SDK runs, and crash reports without consent start it before any yes; on the keypad a repeated tap is an amount. Without it, the plan's exact options break "nothing analytic is sent before yes" and "never tap positions". Android has no native rage-click detection.
  2. `controller.ts` changes (1D-T1's review notes, carried by the controller's brief): `AccountChangedError` (exported; message unchanged) for a yes refused after an account change; a no is written to the store at the call as well as in the queue, and the queue waits for that write before its own writes and the server call, so a no given while a refresh or another answer is on its way survives the app being closed (1D-T1's receipt, "Risks"). Three controller tests are new, and `a yes waiting behind another call is refused…` now asserts the class.
  3. The session-change signal is the session epoch (1C-T5, R86). When the epoch moves with a binding present, `AnalyticsUpkeep` calls `setAccount(null)` at once and only then reads `/v1/me`, so a yes queued for the previous account cannot be sent under the new session. The first session it sees is not a change (the plan's restored-session case expects one reset, then one identify). Within one epoch the account is read once; a foreground re-reads it only if that read failed, then always calls `refresh()`.
  4. The analytics answer and the consent answer are validated as exact objects (no extra keys), as the transport's validators are.
  5. `appAnalytics` makes the shared transport at the first server call, not at install, and sets `app_version` and `platform` from `v1ClientVersion()` (both only on iOS and Android with a valid version); `posthogClient` drops refusals from `screen` and the replay calls, which answer promises the controller does not wait for.
