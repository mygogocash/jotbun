- **M-1, the fix (R96):** for a HEAD, `headOf` in `src/v1/handler.ts` now reads the dropped GET body to its end (`pipeTo` a discarding `WritableStream`) before it answers.
  - Before, a HEAD on `GET /v1/export-files/:grant` kept its download slot. `serveExportFile` returns a slot only when its body ends or is cancelled, and a dropped body of more than one chunk did neither.
  - So four HEADs (`EXPORT_SLOTS`, per isolate and shared by every account) turned every later export download in that isolate into 503 `SERVICE_UNAVAILABLE`.
  - The fix is at the front door, so 1B-T8's and 1B-T9's downloads are covered too.
- **Why it reads the body instead of cancelling it:** the fix planner tried a cancel in the real Workers runtime (`wrangler dev` on the built vault Worker, one stateless request per HEAD).
  - With a cancel, `response.body.cancel()` resolves, but it does not reach the stream that holds the slot before the request ends; that stream sits behind the download's `FixedLengthStream`. Four HEADs, then the GET answered 503.
  - With the body read to its end, the GET answered 200, and so did another member's download in the same Worker.
  - In the Workers test runtime a cancel does reach that stream, because a test's request context lives on. So the new case checks that each HEAD reads the file to its end.
